## 1. `progress.js` — persistent player progress

### 1.1 Storage

- **Key**: `'birdy-progress'` (`progress.js:4`), a single JSON blob in
  `localStorage`. A native `Storage`/`ProgressRepository` port should use one
  key (e.g. a single `SharedPreferences` String entry, or a small file) whose
  value is the same JSON shape below serialized with `kotlinx.serialization`.
- A second, older, standalone key `'birdy-best'` (a bare integer string) is
  read once at load time for a one-way migration (`progress.js:142-144`):
  `data.best = max(data.best, Number(localStorage.getItem('birdy-best')) || 0)`.
  A native migration importing WebView `localStorage` (see the harness's
  "Migration" section) must read **both** keys and apply the same `max()`.
- Other bare keys referenced in localStorage by *other* modules (verify
  against those modules' own specs, listed here for the migration step since
  they live in the same origin): `birdy-best`, `birdy-muted`, `birdy-lang`
  (`i18n.js:187`, see §3.1), `birdy-quality`. `progress.js` itself only reads
  `birdy-progress` and `birdy-best`.

### 1.2 Persisted JSON shape (after `load()`'s defaulting/migration)

```jsonc
{
  "coins": 0,                    // int, wallet balance
  "best": 0,                     // int, lifetime best score (see also achievements' bestScore == this)
  "runs": 0,                     // int, lifetime run counter
  "owned": ["sunny"],            // LEGACY (pre-shop) skin ids; still read for migration, not written to by new code paths except by being copied into items.skin
  "skin": "sunny",               // LEGACY equipped skin id
  "missions": null,              // null, or { date: "Y-M-D", list: [ {id,goal,progress,reward,done}, ... ] } (3 entries)
  "gift": { "last": "", "streak": 0 },       // last = dayKey string of last claim, "" = never
  "rewardedAds": { "day": "", "count": 0 },  // count only valid when day === today()
  "stylePassUntil": 0,           // epoch millis; access to ALL skins/worlds while Date.now() < this
  "paidProducts": [],            // string[] of Play Billing product ids "birdy_(skin|world)_<id>" actually owned
  "processedPurchases": [],      // string[] of already-applied purchase tokens (idempotency for coin-pack IAPs)
  "tutorialDone": false,         // bool
  "trails": ["none"],            // LEGACY owned trail ids
  "trail": "none",               // LEGACY equipped trail id
  "stats": {                     // lifetime aggregate stats, used by ACHIEVEMENTS' `stat` field
    "bestScore": 0, "bestZone": 0, "nearTotal": 0, "bestChain": 0,
    "bestPowerups": 0, "plantsTotal": 0, "coinsTotal": 0, "bestStreak": 0
  },
  "achieved": [],                 // string[] of unlocked ACHIEVEMENTS ids
  "items": {                       // CURRENT shop model: owned ids per KIND (see §2)
    "skin": ["sunny"], "pattern": ["plain"], "hat": ["none"], "eyes": ["normal"],
    "beak": ["round"], "trail": ["none"], "world": ["park"], "pipe": ["green"]
  },
  "equip": {                       // CURRENT shop model: equipped id per KIND
    "skin": "sunny", "pattern": "plain", "hat": "none", "eyes": "normal",
    "beak": "round", "trail": "none", "world": "park", "pipe": "green"
  },
  "upgrades": {}                   // { [upgradeId]: level(0..UPGRADE_MAX) }, absent key == level 0
}
```

A Kotlin port's persisted model should be the **post-migration** shape
(`items`/`equip`/`stats`/`upgrades` fully populated); the `owned`/`skin`/
`trails`/`trail` legacy fields and the standalone `birdy-best` key only need
to exist as *one-time WebView-migration inputs* (see the harness's migration
step), not as fields the native app itself ever writes again.

### 1.3 `load()` (lines 96-146) — defaulting and migration, step by step

1. Parse `localStorage.getItem(KEY)` as JSON; on any error (missing key,
   corrupt JSON) treat as `null` (`96-100`).
2. Merge onto a hard-coded defaults object with `{ ...defaults, ...(data||{}) }`
   (`101-119`) — i.e. **shallow** merge: any top-level key present in the
   saved data fully overrides the default, missing keys get the default.
3. `items`/`equip` are defaulted to `{}` then shallow-copied (`122-123`) —
   *not* deep-merged with per-kind defaults yet; that happens in step 5.
4. `paidProducts`/`processedPurchases` are coerced to `[]` if not arrays
   (`124-125`) — defends against a corrupt save.
5. **Legacy → current migration** (`126-129`):
   `items.skin = unique(items.skin ∪ owned)`, `items.trail = unique(items.trail ∪ trails)`,
   `equip.skin ??= skin`, `equip.trail ??= trail`. (`??=` = assign only if
   currently `null`/`undefined`.) This is idempotent and safe to run even on
   saves that already use the current model (their `owned`/`trails` default
   to `['sunny']`/`['none']`, already subsets).
6. **Per-`KIND` normalization loop** (`130-138`), `KIND` iterating
   `['skin','pattern','hat','eyes','beak','trail','world','pipe']` (catalog.js
   `KINDS`, declaration order):
   - `free = CATALOG[kind][0].id` (every kind's first entry, always price 0).
   - If `items[kind]` doesn't already contain `free`, **prepend** it
     (`items[kind] = [free, ...(items[kind]||[])]`) — guarantees the free
     item is always owned and always sorts first.
   - `trialAccess = (kind is 'skin' or 'world') && stylePassUntil > Date.now() && !item.rare` (rare skins excluded, main #8)`.
   - `paidAccess = paidProducts.includes('birdy_' + kind + '_' + equip[kind])`.
   - If `equip[kind]` doesn't reference an existing catalog item for that
     kind, **or** (`items[kind]` doesn't contain it AND neither `paidAccess`
     nor `trialAccess` apply), reset `equip[kind] = free`. In words: an
     equipped id survives normalization if it's a real catalog entry for that
     kind AND (owned OR currently covered by a paid product OR currently
     covered by an active style-pass-eligible kind).
7. `upgrades` shallow-copied with default `{}` (`139`).
8. `stats` defaulted per-field (not wholesale) onto whatever was saved,
   `bestScore` seeded from the (already-migrated) `best` (`140`).
9. Old-key migration `best = max(best, Number(localStorage['birdy-best'])||0)`
   (`142-144`), swallowing any storage error.
10. `load()` runs exactly once, into the module-level singleton `const data =
    load()` (`148`) — i.e. real usage loads it once per app/game process
    lifetime, mutating this in-memory object and periodically persisting via
    `save()`. **A Kotlin port must not reload from storage per-call**; it
    should load once into an in-memory model, mutate it, and persist on the
    same events `save()` is called at (every mutating method below calls
    `save()` at its end, so persistence is essentially "save after every
    state-changing action").
11. `save()` (`171-176`) simply does
    `localStorage.setItem(KEY, JSON.stringify(data))`, swallowing any error
    and returning a `boolean` success flag that most callers ignore.

See `meta-progress-load.json` scenarios `fresh-install`,
`legacy-pre-shop-save-migration`, `birdy-best-legacy-key-migration`,
`equip-points-to-unowned-item-falls-back-to-free`, `style-pass-trial-access`,
and `paid-product-ownership` for concrete before/after values of every rule
above, produced by actually running this code.

**Edge case, verified in the fixture**: a *brand-new* install writes
**nothing** to storage until the first mutating action (`fresh-install`
scenario: `getItem('birdy-progress')` is still `null` right after `load()`).
A Kotlin port that always eagerly persists a freshly-defaulted model on first
load would diverge from this (harmlessly, but note it if bit-exact
storage-file diffing matters for tests).

#### 1.5.1 `statValue(stat)` (lines 150-156)

- `stat === 'runs'` → `data.runs`.
- `stat === 'unlocks'` → `Σ over KINDS of (items[kind].length - 1)` (owned
  items minus the always-present free one) `+ Σ over upgrades of level`.
- otherwise → `data.stats[stat] || 0`.

#### 1.5.2 Unlock evaluation

- `unlockAchievements()` (158-169): iterates `ACHIEVEMENTS` in declaration
  order; for each not-yet-`achieved` whose `statValue(stat) >= goal`: push id
  to `achieved`, `coins += reward`, if it has a `skin` and that skin isn't
  already owned, push it into `items.skin` (does **not** auto-equip it).
  Returns the list of achievement objects unlocked *this call*. Called from
  `finishRun()` (after run-stat aggregation) and from the public
  `checkAchievements()` (158, for gift-streak/shop-unlock triggers outside a
  run).
- `wouldUnlock(run)` (371-381): a **non-mutating** preview used mid-run to
  fire a celebratory toast the instant a threshold is crossed, before the run
  actually ends. For each not-yet-achieved achievement: `v = statValue(stat)`;
  if `stat` is one of the four `RUN_MAX_STATS` keys, `v = max(v,
  run[correspondingRunKey] || 0)`; if it's one of the three `RUN_SUM_STATS`
  keys, `v += run[correspondingRunKey] || 0`; achievement "would hit" if
  `v >= goal`. (In practice every achievement's `stat` is in exactly one of
  the two maps, or neither — `unlocks`/`runs` are session totals not
  affected by the in-progress run, so `wouldUnlock` for those simply checks
  the already-committed lifetime value.)
- `achievements()` (362-368): full list with `value = min(goal,
  statValue(stat))` and `done` flag, for a status/overview screen — always
  returns all 21, never filtered.

### 1.7 Daily missions

#### 1.7.1 Mission pool (`MISSION_POOL`, lines 41-51)

8 templates, each `{ id, text(n) => {de,en}, stat, per: 'run'|'day', goals:
[tier0,tier1,tier2], minBest? }`. `stat` names the per-run counter field this
mission reads (`run[stat]`); `per: 'run'` means "best single-run value ever
seen while the mission is active" (`Math.max`), `per: 'day'` means "running
total across every run today" (`+=`). `minBest` (only 3 of 8 have it) gates
eligibility: the mission is excluded from the day's draw entirely unless the
player's lifetime `best` score is `>= minBest` (keeps obstacle-specific
missions from appearing before the player has ever seen that obstacle).

| id | stat | per | goals | minBest | text template (en) |
|---|---|---|---|---|---|
| coins | coins | day | 20,40,70 | – | "Collect {n} coins" |
| score | score | run | 10,20,35 | – | "Score {n} in one flight" |
| rows | score | day | 30,60,100 | – | "Fly through {n} pipes" (note: literally counts `run.score`, i.e. pipes passed, summed per day — same underlying counter as the `score` mission, different aggregation) |
| powers | powerups | day | 2,4,6 | 8 | "Grab {n} power-ups" |
| runs | runs | day | 3,5,8 | – | "Play {n} rounds" |
| plants | plants | day | 3,6,10 | 14 | "Pass {n} spiky cacti" |
| moving | moving | day | 4,8,14 | 10 | "Fly through {n} moving gaps" |
| star | starRows | day | 3,6,10 | 12 | "Pass {n} rows as a rainbow" |

`REWARDS = [40, 70, 120]` — flat per-tier coin reward, independent of mission
id.

#### 1.7.2 Seeded RNG (`seeded(str)`, lines 62-70)

A tiny deterministic string-seeded PRNG so every player sees the *same*
three missions on the same calendar day (no server, no shared seed beyond
the date string itself):

```
h = 2166136261                              // FNV-1a offset basis
for each char c in str: h = imul(h ^ c.charCodeAt(0), 16777619)   // FNV-1a, 32-bit
// h is now the seed. Each call to the returned function:
h = imul(h ^ (h >>> 15), 2246822507)
h = imul(h ^ (h >>> 13), 3266489909)
h ^= h >>> 16
return (h >>> 0) / 4294967296                // uint32 -> [0,1)
```
This is FNV-1a hashing to seed, then a MurmurHash3-finalizer-style mixer as
the generator (note: `h` is mutated as a captured closure variable across
calls — this is a *sequence*, not independent draws). Port this exactly with
32-bit wrapping integer arithmetic (`Int` in Kotlin naturally wraps; replicate
`Math.imul` with `Int * Int` — JVM `Int` multiplication already wraps
mod 2^32 the same way `Math.imul` does, so a straight `a * b` on `Int` is a
correct port of `Math.imul(a, b)`). Verify against
`meta-missions.json.seededRawDraws` (first 5 raw `[0,1)` draws for 5 sample
seed strings) before trusting anything downstream.

#### 1.7.3 `dailyMissions(date, best)` (lines 75-86)

```
rnd = seeded(date)
pool = MISSION_POOL.filter(m => best >= (m.minBest || 0))   // eligible templates only
list = []
for tier in 0..2:
  idx = floor(rnd() * pool.length)
  m = pool.splice(idx, 1)[0]        // REMOVE from pool: draws are WITHOUT replacement
  goal = m.goals[tier]
  if m.id == 'score': goal = max(5, round(max(8, best) * [0.6, 0.9, 1.1][tier]))
  list.push({ id: m.id, goal, progress: 0, reward: REWARDS[tier], done: false })
return { date, list }
```

Three important subtleties, all load-bearing for bit-exact parity:

1. **`pool.length` shrinks each iteration** (it's the same array being
   spliced), so `floor(rnd() * pool.length)` must be recomputed with the
   *current* (already-shrunk) length each of the 3 times — a common porting
   bug is to compute all three indices against the original length.
2. The **`score` mission's goal formula overrides `m.goals[tier]` entirely**
   using the live `best` score and per-tier multipliers `[0.6, 0.9, 1.1]`,
   clamped to a floor of `max(8, best)` before multiplying and `5` after
   rounding. This is the only pool entry whose goal isn't a flat table
   lookup.
3. `date` is produced by `dayKey(offsetDays=0)` (`54-58`):
   `` `${Y}-${M0+1}-${D}` `` — **not zero-padded**, month is `getMonth()+1`
   (1-based). E.g. Sept 28 2026 → `"2026-9-28"`, Jan 5 2026 → `"2026-1-5"`.
   This exact string is both the RNG seed and the `missions.date` stamp used
   to detect day-rollover (`missions()`, `178-184`: regenerate iff
   `data.missions.date !== today()`). A Kotlin port's date-key formatter must
   reproduce this non-padded format exactly, in the **device's local
   calendar**, not UTC (JS `Date` getters are local-time).

`missions()` (public, 304-309) maps the stored `{id,goal,progress,reward,done}`
tuples back onto their live localized `text(goal)` (re-resolved from
`MISSION_POOL` every call, so a language switch mid-day updates mission text
without regenerating the missions themselves).

See `meta-missions.json.dailyMissions` for the full output matrix across 7
dates × 8 best-scores (56 rows, each a fully resolved 3-mission list) to
verify a Kotlin re-implementation against.

#### 1.7.4 Mission progress & completion (`finishRun`, `wouldComplete`)

Inside `finishRun(run)` (336-359), after run-stat aggregation and before
achievement checks, for every **not-done** mission in the current day's list:

```
tpl = MISSION_POOL.find(t => t.id === m.id)
value = tpl.stat === 'runs' ? 1 : (run[tpl.stat] || 0)
m.progress = tpl.per === 'run' ? max(m.progress, value) : m.progress + value
if m.progress >= m.goal:
  m.progress = m.goal   // clamp, no "overflow" display
  m.done = true
  coins += m.reward
  completed.push({ ...m, text: tpl.text(m.goal) })
```

Note the **special-case for `stat === 'runs'`**: unlike every other stat
which reads a field off the `run` result object, "how many rounds were
played" isn't a field of a single run's result — it's simply `1` (this run
happened), always added regardless of the run's other data.

`wouldComplete(run)` (391-401) is the same formula as a **non-mutating**
preview (returns just the list of mission ids that *would* complete), used
to show a live "mission complete!" toast during the run before it actually
ends; note its `stat === 'runs'` branch differs subtly — it contributes `0`
here (line 396: `tpl.stat === 'runs' ? 0 : run[tpl.stat] || 0`), i.e. the
preview never shows the `runs` mission as completable mid-run (only
`finishRun` itself, called once at the true end, credits the `+1`).

### 1.8 Daily gift & streak (lines 88-91, 311-332)

- `GIFT_BASE = 20`, `GIFT_STEP = 10`, `GIFT_MAX_STREAK = 7`.
- `giftAvailable()`: `data.gift.last !== today()` — one claim per local
  calendar day.
- `streak` getter (316-319): if `gift.last` is today **or** yesterday
  (`dayKey(-1)`), returns the stored `gift.streak`; otherwise returns `0`
  (a broken streak is only *reported* as 0 by the getter — the stored value
  isn't reset until the next successful claim overwrites it).
- `giftAmount(streak)` (320-321):
  `GIFT_BASE + GIFT_STEP * (min(streak, GIFT_MAX_STREAK) - 1)`, streak
  counted from 1. Table (streak → coins): 1→20, 2→30, 3→40, 4→50, 5→60,
  6→70, 7→80, 8+→80 (caps at the 7-day value).
- `claimGift()` (323-332): if unavailable, returns `null`. Else:
  `newStreak = (gift.last === yesterday) ? gift.streak + 1 : 1` (a gap of 2+
  days resets to 1, matching the getter's "0" read but starting the *new*
  streak count at 1 on this claim, not 0). Sets `gift = {last: today(),
  streak: newStreak}`, adds `giftAmount(newStreak)` coins, updates
  `stats.bestStreak = max(bestStreak, newStreak)`, `save()`s, returns
  `{amount, streak: newStreak}`.

### 1.9 Rewarded ads & style pass (lines 92-94, 190-213)

- `REWARDED_ADS_PER_DAY = 3`, `REWARDED_COINS = 30`,
  `STYLE_PASS_MS = 60*60*1000` (1 hour).
- `rewardedAdsLeft` getter: `max(0, 3 - count)` where `count` is
  `rewardedAds.count` **only if** `rewardedAds.day === today()`, else `0` —
  i.e. the counter isn't explicitly reset at midnight, it's just ignored once
  stale (a `day` mismatch is treated as "0 used today").
- `useRewardedSlot()`: the shared gate behind **both** coin-grant and
  style-pass-grant (they draw from the *same* 3/day pool). Returns `false` if
  no slots left; else records `{day: today(), count: 3-left+1}` and returns
  `true`.
- `grantRewardedCoins()`: `useRewardedSlot()` then `+= 30` coins, `save()`,
  returns the amount granted (`0` if no slot).
- `stylePassMinutesLeft` getter: `max(0, ceil((stylePassUntil - Date.now()) /
  60000))`.
- `grantStylePass()`: no-op returning `false` if a pass is already active
  (`stylePassMinutesLeft > 0`) **or** no rewarded slot is left; otherwise sets
  `stylePassUntil = Date.now() + 3600000` (a **fresh** hour, it does not
  stack/extend an already-active pass — but the "already active" guard means
  this path is unreachable anyway; the guard exists to prevent wasting an ad
  slot on a no-op).
- While active, `owns('skin'|'world', anyId)` returns `true` for **every**
  id of those two kinds (§1.4) — this is the "try everything" trial, not a
  per-item grant.

### 1.10 Run-end aggregation (`finishRun`, lines 336-359) — full sequence

Called once per completed run with a `run` object holding that run's
counters (fields referenced across this file: `score`, `coins`, `zone`,
`bestChain`, `powerups`, `near`, `plants`, and whatever `moving`/`starRows`
the caller also includes for the mission stats in §1.7 — those two are only
ever read via `run[tpl.stat]`, never named explicitly in `progress.js`
itself, so treat them as pass-through counter names the caller (`main.js`)
must also populate).

1. `runs++`.
2. `coins += run.coins`.
3. `isBest = run.score > best`; if so, `best = run.score`.
4. For each of the 4 `RUN_MAX_STATS` pairs (`bestScore←score`,
   `bestZone←zone`, `bestChain←bestChain`, `bestPowerups←powerups`):
   `stats[stat] = max(stats[stat]||0, run[key]||0)`.
5. For each of the 3 `RUN_SUM_STATS` pairs (`nearTotal←near`,
   `plantsTotal←plants`, `coinsTotal←coins`): `stats[stat] += run[key]||0`.
6. Mission progress/completion (§1.7.4).
7. `unlockAchievements()` (§1.5.2).
8. `save()`.
9. Returns `{ isBest, completed: Mission[], achievements: Achievement[] }`.

Step order matters: stat aggregation happens **before** achievement checks
(so a run that both sets a new best AND crosses an achievement threshold
unlocks it the same call), and mission-progress happens **before**
achievements too, but **after** stat aggregation (so `unlocks`-stat
achievements, if any run's shop purchases changed `items` counts — they
don't, shop actions are their own calls — would also see the latest state;
in practice `unlocks`/`runs`-stat achievements never depend on the `run`
argument at all, only on already-committed lifetime counters).

## 3. `i18n.js` — DE/EN strings

### 3.1 Language detection & switching (lines 185-204)

```
detect():
  saved = localStorage.getItem('birdy-lang')
  if saved is 'de' or 'en': return saved
  nav = (navigator.language || 'en').toLowerCase()
  return nav.startsWith('de') ? 'de' : 'en'

lang = detect()   // evaluated ONCE at module load, into a closure variable

setLang(l):
  if l is not 'de' or 'en': no-op (silently ignored — verified in
    meta-i18n.json.setLangUnknownIsNoOp)
  else: lang = l; localStorage.setItem('birdy-lang', l)   // swallows storage errors
```

Port as: an in-memory current-language `enum{DE,EN}` state (not necessarily
a singleton var if the Kotlin architecture prefers DI, but semantically a
single "current app language" akin to a `StateFlow<Lang>`), defaulted once
at startup from `SharedPreferences["birdy-lang"]` if present and valid, else
from `java.util.Locale.getDefault().language.startsWith("de")`.

### 3.2 String lookup (`t`, `L`, lines 206-216)

```
t(key, values?):
  s = STRINGS[lang][key] ?? STRINGS.de[key] ?? key     // fallback: current lang -> German -> the raw key
  if values: s = s.replace(/\{(\w+)\}/g, (_, k) => values[k] ?? '')
  return s

L(v):  // localize a value that's either a plain string or {de,en}
  if v is an object: return v[lang] ?? v.de
  return v
```

- **Fallback chain is DE, not EN** — if a key is ever missing from the
  active-language table but present in German, German is shown (never
  silently falls to English). A totally unknown key returns the key string
  itself verbatim (useful during development, but a native port should
  probably assert/log on this rather than silently display raw keys in
  production — see `meta-i18n.json.fallbackRule`).
- Placeholder syntax is `{name}`, replaced via a single global regex pass;
  a value missing from the `values` map becomes an **empty string**, not the
  literal `{name}` — a Kotlin `String.format`-style or manual regex
  replacement must match this (Kotlin's default `%s`-style formatting would
  throw or misalign on a missing arg; keep a custom `{key}` substitution
  function with the same "default to empty string" behaviour).
- `L()` is used wherever catalog/achievement/mission data carries a
  `{de,en}` object directly (names, texts) rather than a `STRINGS` key.

### 3.3 String table

100 keys total (`meta-i18n.json` has the complete DE+EN table, extracted by
actually calling `t()` for every key — use it as the literal source of
truth for a Kotlin `strings.xml`/`Resources` file rather than retranscribing
by hand). Notable formatting conventions visible in the table:

- **Icon tags**: some strings embed `[iconName]` (e.g. `'[gift] Daily gift ·
  +{n}'`) which `rich()`/`setRich()` (icons.js, §4.3) expand into an inline
  SVG badge sized to the surrounding text. `meta-i18n.json.keysWithIconTags`
  lists every key that does this and which icon name(s) it references — a
  native (Compose) port needs an equivalent "inline icon in text" mechanism,
  e.g. `AnnotatedString` with an `InlineTextContent` per tagged run, keyed on
  the same `[name]` convention if the strings are kept as-is, or by splitting
  each such string into structured `(prefix, icon, suffix)` parts up front.
- Some strings carry raw **HTML** (`<b>`, `<br />`) for the two `howto`/
  `handSide`/`keys` tutorial strings, applied via `data-i18n-html` +
  `el.innerHTML = rich(...)` (icons.js `rich(s, escape=false)` — no
  escaping, since these are trusted first-party strings, not user input). A
  Compose port renders these as `AnnotatedString` with explicit bold spans /
  manual line breaks instead of parsing HTML.
- `lang`/`langLabel` are special: they describe the **other** language (DE's
  `lang: 'EN'` is the switch-to-English button's label shown while German is
  active, and vice versa) — i.e. always "what tapping this button switches
  you *to*", not the current language's own name.

### 3.4 DOM application (`applyI18n`, lines 219-223)

Web-only (`document.querySelectorAll('[data-i18n]')` /
`[data-i18n-html]`); **not portable as-is** — a Compose UI instead binds each
text `@Composable` directly to `t(key)`/`L(value)` calls (recomposed
automatically when the language `State` changes), so this function itself
has no native equivalent, only the underlying `t()`/`L()`/`rich()` primitives

## 4. `icons.js` — the game's own icon set

### 4.1 Data model (lines 1-63)

`ICONS: Record<name, Part[]>`, each icon a small list of **parts** on a
24×24 SVG grid (rendered with a 1px bleed via `viewBox="-1 -1 26 26"`,
`icons.js:126`). A part is one of:

- `[pathData: string, fillColor: string]` — a filled shape.
- `[pathData: string, null, strokeColor: string]` — an **open stroke** (used
  for wave/arc lines like eyebrows, wings-in-flight, snowflake spokes — no
  fill, drawn as a rounded-cap/join stroke).
- `['circle', cx: number, cy: number, r: number, fillColor: string]`.

33 icons total (`meta-icons.json.iconNames` / `.rawParts` has the complete,
literal data — port these as a Kotlin `sealed class IconPart` / data
structure with the exact same coordinates; do not approximate the paths,
they are bespoke vector art). Colours are a small fixed named palette (`C`,
lines 9-13) plus two standalone constants `INK = '#543847'` (outline/ink
colour used everywhere) and `LAND = '#6cbb35'` (only used by the `globe`
icon's "continents", specially remapped under the `badge` style — see §4.2).

A tiny helper `rr(x,y,w,h,r)` (line 15) builds a rounded-rect path string —
port as a straight rounded-rect draw primitive (e.g. Compose
`RoundedCornerShape`/`drawRoundRect`), not as a literal path string.

### 4.2 Render styles (`iconSvg`, lines 96-127)

Three styles, selectable per call:

- **`sticker`** (default): each part drawn as declared with a uniform
  `INK`-coloured 2px outline stroke on every path/circle (open strokes get a
  2.6px-wide stroke in their own declared colour, no separate outline layer
  since the "stroke" already reads as ink-adjacent artwork).
- **`glyph`**: white fills (parts whose colour equals `INK` stay `INK` — used
  for the few icons with intentionally-dark details even in glyph mode) with
  an ink outline, **plus a drop-shadow duplicate of the entire icon drawn
  first**, translated down `1.4` units, filled solid ink, `stroke-width=2`
  (i.e. a naive "draw twice, offset" shadow, not a blur/elevation shadow).
- **`badge`**: an ink-outlined filled circle (`r=11`, centre `12,12`, 1.6px
  ink stroke) in the icon's assigned `BADGE[name]` colour, with the icon
  itself drawn white (again `INK` parts stay `INK`, and **`LAND` maps to the
  badge colour** — so the globe's green continents become "cut out" in the
  badge's own colour, reading as a hole rather than a mismatched green splat
  on every badge tint) scaled to 0.7× and re-centred on the badge.

`BADGE: Record<name,color>` (lines 67-74) assigns one colour per icon for the
badge style — this is the "owner's chosen style" referenced in the source
comment (`docs/VISUAL.md`, not read for this spec but named as the design
reference). `icon(name, size=22)` (77-79) is shorthand for
`iconSvg(name, {style:'badge', size, badge: BADGE[name]})` — this is what
`rich()` (below) uses for inline icons in text.

A Kotlin/Compose port should represent each icon as a small immutable data
structure of parts (as above) and implement the three style renderers as
`DrawScope` extension functions producing the same visual result — see
Porting notes §6.4 for the general SVG→Compose-Canvas mapping. Exact
rendered SVG markup for all 33 icons × 4 render calls (`badge` at size 22 and
24, `glyph` at 24, `sticker` at 24) is frozen in
`meta-icons.json.renderedSvg` for pixel-level comparison against a native
renderer's snapshot tests.

### 4.3 Inline icons in text (`rich`, `setRich`, `esc`, lines 83-91)

```
rich(s, escape=false):
  str = escape ? escapeHtml(s) : s
  return str.replace(/\[(\w+)\]/g, (m, name) =>
    ICONS[name] ? `<span class="ic">${icon(name,'1.35em')}</span>` : m)   // unknown [name] left as literal text
```

`setRich(el, s)`: if `s` contains any `[\w+]` tag, sets `el.innerHTML =
rich(s, true)` (HTML-escaped first, so user-adjacent text can't inject
markup — though in practice all inputs are trusted static strings); else
plain `el.textContent = s` (avoids `innerHTML` entirely when there's nothing
to expand, a minor XSS-hardening / perf habit worth keeping conceptually
even though a Compose port has no DOM injection surface at all).

Port note: since Compose has no direct innerHTML equivalent, the cleanest
native approach is to keep the **string data** with its `[name]` tags intact
(so `strings.xml`/resource content matches 1:1 with the JS source and stays
diffable), and do the `[name]` → inline composable substitution at render
time by splitting on the same regex into a list of `{text}` / `{icon}` runs
and laying them out in a `Row`/`FlowRow` (or `AnnotatedString` +
`InlineTextContent` if within a single `Text`).

## 5. `bot.js` — playtest / QA autopilot

This is a **developer tool**, not shipped gameplay: `main.js`'s `?sim` query
parameter drives one of these bots headlessly to smoke-test level fairness
and balance (see `main-a.md`'s reachability section, which this bot's `pro`
skill level is specifically tuned to stress-test — "near-perfect play: used
to detect rows that are impossible (unfair)", `bot.js:15`). Per the
architecture brief, `commonMain` should still host this logic (not
Android-only) so the same headless-playtest harness can run against the
Kotlin engine in CI, exactly as `scripts/playtest.mjs` does against the JS
build today.

### 5.1 Constants & skill table (lines 4-17)

`GRAVITY = 36`, `FLAP = 11.5` (full flap impulse), `HOP = 6` (a lane-switch
tap without also needing a full flap — see main-b.md for how the real game
applies these same two impulse values to the bird), `BPM = 124` (must match
`audio.js`'s tempo — the cactus/plant obstacles pulse on the beat, see
`world-plant-timing.json`).

Three skill presets (`SKILLS`, lines 10-17) — full table in
`meta-bot.json.skills`:

| skill | plan2 | delay(s) | anticipate | interval(s) | noise | lookAhead | mistake | predict | lateSwitch | apexCheck |
|---|---|---|---|---|---|---|---|---|---|---|
| novice | false | 0.22 | 0.6 | 0.2 | 0.9 | 30 | 0.12 | false | false | 0.4 |
| good | false | 0.15 | 0.9 | 0.12 | 0.45 | 45 | 0.04 | false | true | 0.85 |
| pro | true | 0 | 1 | 1/60 | 0 | 80 | 0 | true | true | 1 |

Field meanings (inferred from use in `think()`/`band()`/`pickLane()`):
`delay` = input-to-action reaction latency (seconds, queued via `queue`,
lines 89, 99); `anticipate` = fraction of `delay` used when predicting
forward (`react = max(delay*anticipate, 0.05)`); `interval` = minimum
seconds between voluntary actions once one is taken (`cooldown`); `noise` =
half-width of a uniform random aim offset drawn once per newly-targeted
gate; `lookAhead` = world-Z distance ahead to start planning for a gate;
`mistake` = probability of ignoring the cost function and picking a
uniformly-random open lane instead; `predict` = whether `band()` reasons
about the *future* state of moving/breathing/plant gaps at arrival time
(`pro` only) vs. using instantaneous/static values; `lateSwitch` = whether
the bot is willing to defer a lane switch until forced (`good`/`pro`) vs.
switching immediately whenever it decides to (`novice`); `apexCheck` =
probability of actually performing the "would this flap/hop overshoot the
ceiling" safety check (a human/imperfect player sometimes just doesn't look).

### 5.2 `plantRise(beat)` (lines 19-25) — bot's OWN copy, note the divergence

```
p = ((beat % 4) + 4) % 4      // beat mod 4, always positive
if p < 2:    return 0
if p < 2.4:  return (p - 2) / 0.4      // LINEAR ramp 0->1
if p < 3.9:  return 1
return 0                                // INSTANT drop back to 0
```

**This is a simplified, linear-only copy** of the real cactus timing
function in `world.js` (see `world-plant-timing.json`, which documents the
actual `smoothstep`-eased rise **and** fall used for rendering/collision).
The bot only needs a cheap same-shape approximation for its own risk
estimate, not the exact render curve — a Kotlin port must keep **two**
separate `plantRise` implementations (one in the shared game-sim/render path
matching `world.js`, one private to the bot/QA module matching this simpler
linear version) rather than "helpfully" unifying them, since unifying would
change the bot's fairness-detection behaviour.

### 5.3 Lane selection (`pickLane`, lines 34-54)

```
options = gate.lanes.filter(l => !l.blocked)     // with their index i
if random() < mistake: return a uniformly random option's index
bestI = options[0].i; bestCost = +Infinity
for each (l, i) in options:
  cost = |i - state.lane| * 1.2
       + |((l.gapLow+l.gapHigh)/2) - state.y| * 0.25
       + (l.hasPlant ? 2.5 : 0)
       + (l.amp ? 1.5 : 0)
       - (l.gapHigh - l.gapLow) * 0.3
  if cost < bestCost: bestCost = cost; bestI = i
return bestI
```
Lower cost wins. Penalizes: switching further from the current lane, gaps
far from the bird's current height, cactus lanes (+2.5), moving/breathing
gaps (+1.5 — `l.amp` truthy = sinusoidal moving gap); rewards wider gaps
(`-0.3` per unit of gap height, i.e. a bigger safety margin lowers cost).
Ties keep the **first** (lowest-index) option encountered (strict `<`, not
`<=`). See `meta-bot.json.pickLaneCostExample` for a worked 3-lane example
with exact costs.

### 5.4 Target band & prediction (`band`, lines 57-86)

Computes the safe `[low, high]` range (already inset by the bird's radius,
`r = state.radius*0.8 + 0.15`) for the bird's centre-Y as it crosses the
currently-targeted gate's currently-picked lane:

- **Non-predictive** (`predict=false`, novice/good): start from the lane's
  static `gapLow/gapHigh`; if `hasPlant`, raise `low` to the lane's
  precomputed `hitLow` (the actual collision threshold already baked in by
  `world.js` at gate-configure time — see `main-a.md`/`world.md` for
  `hitLow`/`hitHigh`).
- **Predictive** (`predict=true`, pro only): estimate time-to-arrival
  `t = max(0, -gate.group.position.z / max(1,state.speed))`, then:
  - if `pulse` (breathing gap): shrink to the gap's **narrowest** point
    (`center ± size*0.35`, tighter than the nominal `size/2` half-width —
    i.e. plans for the worst moment of the breathing cycle, not the
    average).
  - if `amp` (moving gap): recompute the sinusoid's centre at arrival time
    `t` (`center + amp*sin((state.time+t)*speed+phase)`) and use ± `size/2`
    around *that* predicted centre, replacing the static band entirely.
  - if `hasPlant`: compute the beat phase at arrival
    (`beat = (state.time+t)*BPM/60 + plantOffset`), then take the **worst
    case rise** over a small window around that instant (`k` from -2 to 2
    steps of 0.12 beat — i.e. ±0.24 beats of arrival-time uncertainty) using
    this file's own `plantRise()` (§5.2), and raise `low` accordingly using
    the same `PLANT_REACH`/`PLANT_HEIGHT` world constants as the real
    collision code (`PLANT_HEIGHT=1.8`, `PLANT_REACH=0.9`, imported from
    `world.js`).

### 5.5 Decision loop (`decide`/`think`, lines 89-167)

- Input queue models reaction delay: every decided action is pushed with a
  countdown `t = delay` (only if `delay>0`); `decide(dt,ctx)` ticks the queue
  down and, if not empty/due, **skips calling `think()` entirely** that frame
  (the bot commits to whatever it already "pressed" before deciding again —
  a `pro` bot with `delay=0` never queues, `think()` runs and can act every
  call subject only to `cooldown`).
- Re-targeting: when the nearest active, unpassed, in-range (`z >
  -lookAhead`) gate changes, immediately re-run `pickLane()` for the new
  target and draw a fresh `aimOffset = (random()-0.5)*2*noise`.
- Aim clamp (lines 122-137): `want` = the target band's midpoint, unless
  `plan2` (pro only) and there's a *second* upcoming gate, in which case
  `want` is shifted to line up for that second gate's same lane's midpoint
  instead (pre-positioning for the row after next). Then clamp `want +
  aimOffset` so the ~±0.9-unit flap oscillation stays inside `[lo,hi]`: `a =
  min(lo+1, mid)`, `b = max(hi-1, mid)`, `aim = clamp(clamp(want,a,b) +
  aimOffset, lo, hi)`.
- Flap necessity (lines 139-149): predict `yPred = y + vy*react - 0.5*
  GRAVITY*react²` where `react = max(delay*anticipate, 0.05)`; `apex = y +
  FLAP²/(2*GRAVITY)` (note: uses the *current* `y` and the fixed `FLAP`
  impulse, **not** the bird's actual current `vy` — this is "if I flapped
  right now from here", not a true trajectory apex); `apexSafe = apex <
  ceiling+0.12 || random() > apexCheck` (an imperfect bot sometimes just
  doesn't check); `needFlap = yPred < aim-0.9 && apexSafe`.
- Lane-switch vs. flap gate (lines 150-166): if the target lane differs from
  the bird's current lane, a switch is a cheap `HOP` (not a full `FLAP`);
  `hopApex = y + (max(vy,HOP))²/(2*GRAVITY)` if `max(vy,HOP)>0` else `y`;
  `hopSafe` = same formula as `apexSafe` but against `hopApex`. The switch
  actually fires if `!lateSwitch || close || needFlap || hopSafe ||
  vy<0` (`close` = target gate within `z > -14`) — i.e. `lateSwitch` bots
  (good/pro) defer an early, not-yet-urgent switch unless one of the other
  conditions already forces action anyway; `novice` (`lateSwitch=false`)
  always switches the instant it decides to. If no switch is pending and
  `needFlap`, flap; otherwise do nothing this frame. Every actual action sets
  `cooldown = interval`.

See `meta-bot.json.flapDecisionFormulas`/`.flapDecisionSamples`/
`.aimClampFormula` for these as directly executable formulas with sample
inputs/outputs.

## 6. Porting notes

### 6.1 Randomness — what needs to be bit-exact vs. what doesn't

- **`progress.js`'s `seeded()`** (§1.7.2) is the **one** RNG in this batch of
  files that genuinely must be bit-exact cross-platform: it determines which
  3 missions every player sees on a given calendar day, seeded purely from
  the date string, with no server round-trip. If the Kotlin port's mission
  generator diverges even slightly from this algorithm, players moving
  between platforms (or a future iOS build) would see *different* daily
  missions than an Android/JS install on the same day — implement
  `Math.imul` as plain 32-bit `Int` multiplication (JVM `Int*Int` already
  wraps identically), and FNV-1a/the mixer exactly as written in §1.7.2.
  Verify against `meta-missions.json.seededRawDraws` and `.dailyMissions`.
- **`bot.js`'s `Math.random()` calls** (mistake-lane, `aimOffset`) do **not**
  need bit-exact parity — the bot is a fuzzing/QA tool; only its
  *distributions and decision formulas* need to match (already true of the
  JS itself, which never seeds `Math.random()`). A Kotlin port can use
  `kotlin.random.Random` freely here.
- Everything else in this batch (`catalog.js`, `i18n.js`, `icons.js`) is
  fully deterministic static data — no RNG involved at all.

### 6.2 Web APIs used here and their native equivalents

| Web API | Used in | Native (Android/KMP) equivalent |
|---|---|---|
| `localStorage.getItem/setItem` | `progress.js` (KEY, `birdy-best`), `i18n.js` (`birdy-lang`) | `SharedPreferences` (androidMain `actual`), behind a `expect`/injected `KeyValueStore` interface in `commonMain` so iOS can plug `UserDefaults` later |
| `JSON.parse`/`JSON.stringify` | `progress.js` load/save | `kotlinx.serialization.json.Json` with a `@Serializable` data class matching §1.2's shape |
| `navigator.language` | `i18n.js` `detect()` | `java.util.Locale.getDefault().language` (androidMain), or `Locale.current` if using Compose Multiplatform's locale APIs |
| `Date`/`Date.now()` | `progress.js` (`dayKey`, `gift`, `stylePassUntil`, `rewardedAds`), `bot.js` (none directly) | `kotlinx.datetime.Clock.System.now()` for epoch millis (`stylePassUntil` etc.); for the **local calendar day key** (§1.7.3's exact non-padded `Y-M-D` format), use `kotlinx.datetime.TimeZone.currentSystemDefault()` to get local Y/M/D and format with the same non-padded template — do not use `LocalDate.toString()` (ISO, zero-padded) directly, the *string* is an RNG seed and must match byte-for-byte |
| DOM (`document.querySelectorAll`, `innerHTML`, `el.dataset`) | `i18n.js` `applyI18n`, `icons.js` `setRich` | No equivalent needed — Compose recomposition replaces the "reapply i18n to the DOM" pattern entirely; see §3.4 |
| SVG string generation (`<svg>...</svg>` template literals) | `icons.js` `iconSvg` | Compose `Canvas`/`DrawScope.drawPath` (paths as `Path().apply{...}` built from the same coordinate data) or pre-generated `ImageVector`s; see §4.2 |
| Template-literal `{placeholder}` substitution | `i18n.js` `t()` | A small custom regex/`buildString` substitution function reproducing the exact "missing key → empty string" fallback (§3.2) — do not rely on `String.format` |

### 6.3 Three.js — not used directly in these 5 files

None of `progress.js`/`catalog.js`/`i18n.js`/`icons.js`/`bot.js` import or
call into `three` directly (verify: `catalog.js` only *stores* colour
numbers that `bird.js`/`world.js`/`main.js` later feed into
`THREE.Color`/materials — see those files' own specs for the
Color-space/lerp details, e.g. `world-biome-blend.json`'s sRGB↔linear
round-trip notes, which matter if a Kotlin renderer ever needs to blend two
of these catalog colours the same way three.js does). Treat every `0xRRGGBB`
value in `meta-catalog.json` as a **plain sRGB hex colour** for a Kotlin
`Color`/`Int` — no special decoding needed to *store* or *display* them
statically (only *blending* two of them, done elsewhere, needs the sRGB↔
linear treatment).

### 6.4 Icon/emoji rendering strategy

Two distinct icon systems exist in this codebase:

1. **`icons.js`'s own 33-icon vector set** (§4) — bespoke, small, and fully
   specified by `meta-icons.json`; port as native vector drawables or a
   `DrawScope`-based renderer matching §4.1/4.2 exactly.
2. **Raw Unicode emoji** used as `icon` fields on `PATTERNS`/`HATS`/`EYES`/
   `BEAKS` shop items (catalog.js, §2.1) — these render via the system emoji
   font on web. Android also has a system emoji font (Android's
   `NotoColorEmoji`), so `Text("🎩")` in Compose renders equivalently with no
   extra asset work; this is the simplest path and matches the JS behaviour
   (both "render whatever glyph the OS emoji font has"). Only worth revisiting
   if visual parity across Android OEM emoji fonts becomes an issue.

### 6.5 Storage/model architecture recommendation

Model `progress.js`'s module-level singleton (§1.3 step 10) as a single
injected repository object in `commonMain` (e.g. `ProgressRepository`,
backed by the `KeyValueStore` `expect`/`actual` from §6.2), loaded once at
app start, mutated in-memory, and persisted on every state-changing call —
mirroring exactly how the JS's `progress` object already behaves (every
mutating method ends in `save()`). Do **not** re-read from storage on every
getter call (the JS doesn't either — `data` is the one in-memory source of
truth for the process lifetime).

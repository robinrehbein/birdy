## 3. Game modes / screen state machine

`state.mode` (`main.js:703`) ∈ `{ ready, playing, dead, over }`; `state.menu` (`main.js:734`) ∈ `{ start, shop, achievements }` and is only meaningful while `mode==='ready'`. `state.paused` is an orthogonal boolean that only applies while `mode==='playing'`.

```
        resetGame()                    die(cause)             (0.45s later)
ready ────────────────► playing ──────────────────► dead ──────────────────► over
  ▲  menu=start/shop/ach   │  ▲                                                │
  │                 setPaused(true) [Android back / app-background]           │
  │                        ▼  │                                               │
  │                     paused=true ── setPaused(false) [tap / Weiter] ───────┘
  │                                                                           │
  └──────────────────────── goToMenu() [tap "Menü", or Android back] ────────┘
                                                                (tap game-over screen / retry)
```

Concretely:
- **ready → playing**: `flap()` (`main.js:1056-1081`) when `state.mode==='ready'` calls `resetGame()`.
- **playing → dead**: `die(cause)` (`main.js:1390-1422`), only fires `if (state.mode==='playing')`.
- **dead → over**: `updateDead()` (`main.js:1796-1806`) calls `showGameOver()` after `state.deadTimer > 0.45` seconds of simulated fall.
- **over → playing**: `tryRestart()` (`main.js:1184-1186`) — only if `performance.now() - state.overAt > 350` ms (debounce so the death-tap doesn't insta-restart) — calls `resetGame()`. Triggered by: tapping the game-over panel outside `#menu-btn`/`#next-unlock.ready`, pressing `Enter`, or Space/↑/W (`tryRestart()` inside the keydown handler, `main.js:1196`).
- **playing → paused**: `handleBack()` (Android back) or `visibilitychange`→hidden (`main.js:1372-1380`) while `mode==='playing'`.
- **paused → playing**: tapping anywhere on `#pause` except `#pause-menu-btn` (`main.js:1268-1271`), or the "Weiter" button.
- **paused/over/dead → ready(start)**: `goToMenu()` (`main.js:1328-1358`) — Android back button, or "Menü" button on pause/game-over.
- **ready(start) ↔ ready(shop)**: `openShop(true/false)` (`main.js:547-561`).
- **ready(start) ↔ ready(achievements)**: `openAchievements(true/false)` (`main.js:651-657`).

### Android back-button semantics (`handleBack`, `main.js:1359-1370`)
```
if playing && !paused        → pause the run
else if paused || over || dead → go to menu
else if menu === 'shop'        → close shop (back to start)
else if menu === 'achievements'→ close achievements (back to start)
else                            → exit the app
```
Registered only `if (window.Capacitor?.isNativePlatform?.())`, via `@capacitor/app`'s `backButton` event (`main.js:1366-1370`). **Porting note:** native Android maps this 1:1 to `OnBackPressedCallback`; the final `else` branch (`exitApp`) is `finish()`/`moveTaskToBack` — verify which one Capacitor's `App.exitApp()` did (it finishes the activity).

### Background/foreground (`main.js:1373-1380`)
`document.addEventListener('visibilitychange', …)`: on going hidden, pause the run if `playing`, else just suspend audio (`audio.setSuspended(true)`); on becoming visible again, resume audio unless still paused. **Porting note:** `Activity.onPause()`/`onResume()` (or `ProcessLifecycleOwner`) → same two calls (pause run / suspend-resume audio engine).

### `goToMenu()` full reset checklist (`main.js:1328-1358`) — every one of these must happen, in this order, when leaving a run to the menu:
1. `setPaused(false)`; `state.mode='ready'`; `state.hold=false`.
2. Zero every entry of `state.power` (no lingering rainbow/magnet/mini in the menu) and `state.grace=0`.
3. `bird.setGlow(null)`; `music.setHype(false)`; `music.setMode('menu')`.
4. Hide `#hud`, `#gameover`, `#shop`, `#achievements`; show `#start`, `#wallet` (remove `hidden` and `over` classes), `#lang-btn`.
5. Remove `hold`/`show` classes from the zone-hint overlay (`#zones`); `marker.visible=false`; `showHand(null)`.
6. Reset bird rotation to `(0,0,0)`, force `bird.group.visible=true`, `state.y=5`.
7. `state.menu='start'`; `applyBird()` (re-apply equipped skin/look, in case something changed while in a run… normally nothing does).
8. Deactivate every gate/coin/pickup pool entry and hide their meshes (clears the track so the menu view shows only bird + scenery).
9. `renderStart()`.

## 4. Pause screen (`#pause`)

DOM: `index.html:79-90`. Shows run stats formatted at the moment of pausing (`setPaused(true)`, `main.js:1045-1054`): `#pause-score`=`state.score`, `#pause-coins`=`state.coins`, `#pause-zone`=`state.zone+1` (1-based for display). Buttons: `#resume-btn` (`t('continue')`) and `#pause-menu-btn` (secondary style, `t('menu')`).
Interaction (`main.js:1268-1272`): a `pointerdown` **anywhere on `#pause`** except inside `#pause-menu-btn` calls `setPaused(false)` — the whole panel (not just the button) is a tap target to resume, matching the German string `resume: 'Tippen zum Weiterspielen'` ("tap to continue") shown as a subtitle... actually check: the string `resume` exists in i18n but the pause markup only shows `data-i18n="pause"` (title) — `resume` string appears unused in the DOM in this version; verify against i18n.js keys, port the string but note it may be vestigial/reserved for a future subtitle.
`setPaused()` also calls `audio.setSuspended(paused)` — pausing the run also suspends the WebAudio graph (native: pause the audio engine / mixer).
Visual: `#pause` gets a scrim `rgba(43,30,46,0.3)` + `backdrop-filter: blur(3px) saturate(1.15)` (`style.css:771-773`) with a `scrim-in` 0.25s fade-in (`style.css:746-747`), and the panel itself animates in with `slide-in` (`style.css:157-163`: `translateY(40px) scale(0.9) opacity:0` → identity, `cubic-bezier(.2,1.4,.5,1)` — an overshoot "pop" ease, 0.35s). **Porting note:** the backdrop blur of the live 3D game behind the panel needs either a render-to-texture blur pass (cheap on GLES: downsample + 2-pass Gaussian) or can be simplified to a plain darker scrim without blur if perf-constrained — note this as an acceptable visual simplification if needed, but prefer replicating it since it's part of the "style guide" (comment at `style.css:771` explicitly calls out "soft blur of the game instead of a heavy grey veil").

## 5. Game-over screen (`#gameover`)

Triggered by `showGameOver()` (`main.js:1424-1459`), called once from `updateDead()` 0.45s after death.

Sequence of side effects, in order:
1. `state.mode='over'`; `music.setMode('menu')`; `state.overAt = performance.now()` (used for the 350ms restart debounce, see §3).
2. `state.run.coins=state.coins; state.run.score=state.score;` then `const {isBest, completed, achievements} = progress.finishRun(state.run)` — this is where the run is persisted/scored against missions & achievements (see progress.js spec, not this file, for `finishRun`'s internals — but this file must call it at exactly this point with exactly `state.run` mutated as above).
3. Fill `#final-score`, `#final-coins`, `#final-best` text.
4. `#new-best` visible iff `isBest && state.score>0`; if so also: `setTimeout(()=>sfx.powerup(), 250)` and `buzz(30)` (30ms vibration) as a "record fanfare".
5. `#to-best`: a "so close!" nudge. `missing = progress.best - state.score`. Hidden if `isBest || missing>15 || progress.best<5` (don't nag on a first attempt or a huge miss). Text: `missing===0` → `t('tieRecord')` ("You tied your best!"); else → `t('toRecord', {n: missing+1})` ("Only {n} more to beat your best!") — **note the off-by-one**: it's `missing+1`, not `missing`, i.e. if you were 3 short you need "4 more" text-wise (one more than the raw point gap) because you need to *exceed*, not tie.
6. `#missions-done`: achievements-just-unlocked cards render first (class `mission done new achievement`, icon `[trophy]`-rich-text via `t('achUnlocked',{name})`, reward `+{a.reward}`), followed by **every** daily mission (not just today's newly completed ones) via `missionHTML(m, doneNow.has(m.id))` — `doneNow` is the just-completed set so those get the `.new` pop-in animation; missions already done earlier today show `.done` without the pop.
7. `#zone-reached`: hidden if `state.zone===0` (never left zone 1); else text `t('zoneReached', {n: zone+1, name: localized biome name})`.
8. `renderNextUnlock()` — see below.
9. Hide `#hud`; show `#gameover`, `#wallet` (with `.over` class added — see the `@media (max-height:720px)` rule at `style.css:693-698` that hides `.wallet.over` entirely on short screens, since the game-over panel needs that vertical space instead); show `#lang-btn`.
10. `renderWallet(bump)` where `bump = completed.length>0 || achievements.length>0 || state.coins>0` — the coin-wallet chip only does its "pop" animation if the run actually earned something.

### Native decluttered layout (Android port, supersedes the web layout above)
The Kotlin port shows a calmer panel (`GameOverScreen`, `GameOverUi`, `MenuTexts.gameOver`); the data/side-effect sequence above is unchanged.
- Top to bottom: small "Game Over" heading, the **score as the big number**, a small secondary line `best · coins`, then `#new-best` or the `#to-best` nudge (never both), the zone line, then **exactly one progress goal**: the next-unlock bar if present, else the unfinished daily mission with the highest `progress/goal` (`GameOverUi.goalMission`). Achievements unlocked this run stay as compact gold lines. The remaining missions collapse into one line `missionsSummary` ("Missionen 1/3" / "Missions 1/3").
- Buttons: optional gold **coins x2** button (below), then "Nochmal" as the large primary button at the bottom (min. 72dp), "Menü" as a small underlined text link. Tap-anywhere-to-retry and the 350ms debounce are unchanged.
- **Coins x2** (`GameOverUi.doubleCoins`, `MenuTexts.doubleCoins`): shown only if the run earned >= 5 coins, `RewardKind.DoubleCoins` is ready in `AdsStatus`, `progress.doubleCoinsAdsLeft > 0`, the player does not own `birdy_remove_ads` (then it is simply hidden), and it was not used for this game over yet. Label `"+{n} Münzen (Werbung)"` / `"+{n} coins (ad)"`. Tapping posts `RequestRewardedAd(DoubleCoins)`; `GameSession` emits `ShowRewardedAd(DoubleCoins)`. On `earned`, `progress.grantDoubleCoins(runCoins)` credits the run's coins once more (wallet bump + toast `doubleCoinsGranted`). Own limit of 5/day (`ProgressData.doubleCoinsAds`, separate from the shop's 3/day `rewardedAds`), persisted like that counter. The Android ads adapter maps `DoubleCoins` onto the coin rewarded unit.
- **Record marker**: when `best >= 5`, the row spawned with index `best` (`isRecordRow`, `GateRow.record`; passing it scores `best + 1`) gets a golden finish gate rendered by `view/world/RecordMarker.kt`: candy-striped posts outside the lanes with spinning stars and swinging pennants, a beam and a plum banner with the label `recordGate` ("REKORD {n}" / "BEST {n}", blocky 5×7 letters, one bar per pixel run) and a checkered finish line on the ground. The banner hangs entirely above `CEILING + BIRD_RADIUS` so the bird never flies through it, the row's cloud bank is hidden behind it, and the overhead parts hide once the gate is behind the bird so the chase camera never passes through them. The marker is purely visual (no collider). Beating the record pays `Tuning.RECORD_BONUS` (10) coins and toasts `recordBonus` ("Neuer Rekord! +10"), with a screen-space celebration (`UiState.recordFx`, 1.1 s): a golden glow along the screen edges and confetti popping up from the two bottom corners, kept to the outer 28 % of the width so the bird and the rows ahead stay in clear view (no 3D particles in the corridor). From `RECORD_HINT_ROWS` (5) rows out the HUD shows `recordIn` ("🏆 noch 3") under the score (`UiState.recordHint`).

### 5.1 Revive ("Weiterfliegen?", native only, not in main.js)
At most **once per run**, a crash can open a revive offer instead of the game over. When `updateDead()` reaches the 0.45 s mark, the offer opens instead of `showGameOver()` iff: not the tutorial, no offer yet this run, `best >= 10` and `score >= 0.8 * best` (`best` = the record **before** this run, so a new record qualifies), and the revive is payable:
- automatic ads removed (`birdy_remove_ads` in `paidProducts`): pay **100 coins**; the offer is shown even if the wallet is short, with the button disabled;
- otherwise only when a `RewardKind.Revive` rewarded ad is loaded (`AdsStatus.ready`); no ad → no offer. The revive ad reuses the coin reward's ad unit and never counts toward the shop's 3/day.

The overlay (`ReviveScreen`, mode stays `Dead`, the bird keeps falling behind it): heading `reviveTitle`, a 3 s countdown bar, the primary button (`reviveAd`, or gold `reviveCoins` with the price) and the secondary `reviveNo`. "No thanks", a tap outside the buttons, the back button or the countdown running out decline: the normal game over (§5) follows. Accepting freezes the countdown until the payment ends; an ad without the reward also ends in the game over.
Revived: same score, coins and run stats; the colliding row counts as passed (no point) and disappears; the bird returns to its lane and hovers at the middle of the next open gap in that lane (else at 5) with the pulsing lane hint, like the run's start, until the first tap; from then it has 2 s of the star's grace invulnerability (blink). A second crash in that run goes straight to game over. The game over of a run revived with an ad shows no interstitial.

### `renderNextUnlock()` (`main.js:1462-1479`)
Finds the **cheapest not-yet-owned cosmetic across every catalog kind** (`KINDS` from `catalog.js`), sorted by price ascending, first = `next`. If none (everything owned): `#next-unlock` hidden, `nextUnlock=null`.
Else: `pct = min(100, round(progress.coins/next.price*100))`.
- If `progress.coins >= next.price`: adds class `.ready` (glowing/pulsing per `style.css:616,749-750: unlock-glow` keyframes — a box-shadow pulse `0 0 0 3px #fff6d5, 0 0 16px 4px rgba(255,214,64,.9)` alternating 0.9s), text = `t('unlockReady',{kind, name})` (rich, "ready to unlock! ›"), bar filled 100%.
- Else: text = `t('unlockNext',{n: next.price-progress.coins, kind, name})`, bar width `{pct}%`.

Tapping `#next-unlock.ready` on the game-over screen (`main.js:1279-1289`) is a shortcut: `goToMenu()`, then if `nextUnlock` exists, jump straight into the shop pre-selecting that item's tab and id (`shopTab=nextUnlock.shopKind; openShop(true); shopSel=nextUnlock.id; renderShop();`). This bypasses the normal "tap anywhere = retry" behavior — check `e.target.closest('#next-unlock.ready')` **before** the generic retry check.

### Game-over tap handling (`main.js:1276-1291`)
```
pointerdown on #gameover:
  startAudio()
  if target inside #menu-btn: return (handled by its own click listener → goToMenu())
  if target inside #next-unlock.ready: [shortcut above]; return
  if mode==='over' and now - overAt > 350ms: resetGame()
```

## 6. Start menu (`#start`)

Label built via `setRich(giftBtn, t('gift',{n: progress.giftAmount(progress.streak+1)}))` — note it previews **tomorrow's/next** amount (`streak+1`), i.e. the reward you'd get *if you claim now* which advances the streak. Wiggle animation `gift-wiggle` 1.6s infinite (`style.css:476-490`): mostly still (0-70%), a quick double-wiggle-and-scale burst 76-92%, then settles — a "look at me" idle nudge repeated forever.

- Buttons: `#play-btn` → `flap()` (starts a run); `#shop-btn` → `openShop(true)`; `#ach-btn` → `openAchievements(true)`; privacy link (external URL, always visible) and `#ad-privacy-btn` (visible only if `ads.privacyOptionsRequired`, i.e. UMP says consent options must be re-offerable).

## 7. Shop (`#shop`)

DOM `index.html:63-77`. State: `shopTab` (one of `SHOP_TABS` kinds, default `'skin'`), `shopSel` (selected item id within the tab). `SHOP_TABS` (`main.js:292-302`, in order): skin(palette icon) · pattern(paw) · hat(tophat) · eyes(glasses) · beak(beak) · trail(sparkle) · world(globe) · pipe(pipe) · upgrade(bolt) — plus a 10th non-catalog "dice" tab (randomizer) appended after (`main.js:318-319`).

### Opening/closing (`openShop`, `main.js:547-561`)
Opening sets `state.menu='shop'`, `shopSel = defaultSel()` (= `UPGRADES[0].id` if tab is `'upgrade'`, else `progress.equipped(shopTab).id`), unhides `#shop`/hides `#start`, calls `renderShop()`. Closing resets `previewTrail=null`, re-applies the real equipped bird (`applyBird()`), restores the real world preview and pipe style, hides the pipe-preview mesh, calls `renderStart()`.

### `renderShop()` (`main.js:414-489`) — full behavior for a non-upgrade tab

## 9. Tutorial ghost hand (`tut`, `main.js:832-860`, `1144-1163`, `1616-1652`)

First-ever launch (`!progress.tutorialDone`) skips the menu and starts a scripted first run directly (`main.js:2092-2095`: `tut.active=true; resetGame(); tick();`).

State machine `tut.step` ∈ `'' | 'flap' | 'fly' | 'switch' | 'go'`:
1. `resetGame()` sets `tut.step='flap'`, `showHand('flap')` — ghost hand hovers over the bird's own screen position, animating a tap (`hand-tap` keyframes, `style.css:567-571`: bob down 8px→up 6px→settle, 0.9s loop), label `t('handFlap')` ("Tap = flap").
2. Player taps anywhere → **any** tap while `tut.step` is `'flap'` or `'fly'` forces `flap()` regardless of which lane was tapped (`main.js:1148`) — "the first rows only have a middle gap, a stray side tap must not kill a first-time player". First flap transitions `state.hold=false → tut.step='fly'`, `showHand(null)` (hand disappears while flying).
3. Gate spec for the first 3 rows (`tutorialSpec()`, `main.js:855-860`): rows 0,1,2 → `[null, {center:5.2,size:6.2}, null]` (only the middle lane open, fixed gap). Row 3 (`TUT_SWITCH_ROW`) → `[{center:5.2,size:6.2}, null, {center:5.2,size:6.2}]` (middle now **blocked**, left+right open) — the dodge lesson.
4. In `updatePlaying()` (`main.js:1624-1651`): once the tutorial gate (row 3) is within `z > -13` (close enough to react): if its current lane is blocked → `tut.step='switch'`, freeze `state.y` at current height (`tut.freezeY`), `showHand('side')` (hand now anchored over lane 0's screen x — see `updateHand`, always the *left* lane regardless of which lane the player is actually in, since the tutorial always blocks the middle and opens both sides — label `t('handSide')`, "Tap another lane = dodge"), and reveal the lane-boundary overlay (`zonesEl.classList.add('show')`, forcing a `zonesKey` cache-bust first). Else (player already dodged on their own before reaching the freeze distance) → `tut.step='go'` directly, skipping the freeze.
5. While `tut.step==='switch'`: the bird is **frozen** — `state.y` just bobs with `sin(time*3)*0.15` around `freezeY`, `state.vy=0`, gravity/physics fully suspended, **the world keeps scrolling** (gate/scenery movement is unaffected, only the bird's own y is pinned) — this is the "the game freezes in front of it until the player taps beside the bird" behavior. Any tap on a **different** lane than the bird's current one (`tapLane`, `main.js:1149-1153`) sets `tut.step='go'` and hides the hand; a tap on the *same* lane is ignored entirely while frozen (no flap happens either, since the code returns before falling through).
6. `tut.step==='go'`: normal physics resume; once the tutorial gate is `.passed`, `tut.active=false; tut.step=''`, `progress.finishTutorial()` persists the flag so this never runs again, toast `t('tutDone')` ("Great! Now on your own [star]"), `sfx.powerup()`, and the lane-boundary overlay is (re-)shown for the remainder of normal play.
7. The height marker (§ below) pulses larger/faster during the whole tutorial (`pulse = 1.6 + 0.25*sin(time*8)` vs `1` normally, `main.js:135`).

**Porting note:** this is a deterministic finite-state overlay coupled tightly to the gate-spawning of the first 4 rows; port it as an explicit `TutorialController` sealed-state enum mirroring the 4 steps above, driven from the same per-frame `updatePlaying` tick, not as ad-hoc flags.

## 10. Zone-boundary lane hint overlay (`#zones`, `updateZonesOverlay`, `main.js:1105-1122`)

Three columns matching the current lane screen-space boundaries (`laneBounds()`, projects the 3 lane x-positions through the camera and takes midpoints — this is why the overlay's `grid-template-columns` is set dynamically in JS, not fixed 33/33/33, and re-computed only when the memoized key `${b1}|${b2}|${lane}` changes to avoid layout thrash every frame). The bird's own column shows `▲` + `t('zoneFlap')`("flatter"/"flap"); the other two show `◀`/`▶` (pointing toward the bird's lane, i.e. based on `i < state.lane`) + `t('zoneMove')` ("hierhin"/"move here"). Column marked `.own` gets a subtle highlight tint (`rgba(255,241,118,.18)`, `style.css:699`).

Two display modes via CSS classes:
- `.hold` (during the pre-flap hover, `resetGame()` → `zonesEl.classList.add('hold')` unless in tutorial): fully opaque, each column **pulsing** forever (`zone-pulse` 1.2s ease-in-out alternate, background opacity 0.12↔0.08) — an idle "here are your 3 lanes" hint before the first tap.
- `.show` (after the first flap, `flap()` → remove `.hold`, force-reflow, add `.show`): plays a **one-shot 2.6s fade** (`zone-border`/`zone-fade` keyframes, `style.css:270-277`) — full opacity/border held through 60% of the duration then fades to a faint residual (`border-right rgba(255,255,255,.2)`, dividers only, background gone) that **persists for the rest of the run** as permanent lane-boundary dividers (since `.show` itself never gets removed again mid-run, only the CSS keyframe's `forwards` fill freezes it in the faded end-state).
Additionally there's a mask (`style.css:755`) so the dividers only render in the lower ~50-72% of the screen (`linear-gradient(transparent 28%, #000 52%)`), never crossing the sky/HUD area.
**Porting note:** the two visual states (opaque pulsing "hold" vs one-shot-fade-to-faint "show") are two different Compose animations (`InfiniteTransition` alternate vs a single `Animatable` fire-once tween with a held end value), not one — do not conflate them.

## 14. Toasts (`toast()`/`updateToast()`, `main.js:683-699`)

A simple FIFO queue (`toastQueue`, plain array, `push`/`shift`), one visible at a time. `updateToast(dt)` each frame: if a toast is showing, count down `toastTimer` from 2.2s, then hide (`.show` class removed, CSS transition `transform .3s, opacity .3s`); once hidden (`toastTimer<=0`) and the queue is non-empty, pop the next message, `setRich()` it in, show it, reset timer to 2.2s. **Note:** the queue is *not* cleared on mode transitions except explicitly in `resetGame()` (`toastQueue.length=0`, "no leftovers from the menu or the last run") — toasts queued mid-run (mission/achievement pop-ins) are allowed to keep draining into the game-over screen etc. unless a new run starts.

## 15. Quality auto-scaling (`adaptQuality`, `main.js:1991-2016`) and dev FPS overlay (`main.js:2018-2043`)

- `QUALITY_DPR = [min(devicePixelRatio,2), 1.5, 1.25, 1]` (`main.js:67`) — 4 steps, index 0 is "best" (native-ish DPR capped at 2×), each subsequent step a lower fixed device-pixel-ratio.
- Persisted level `quality` read from `localStorage.getItem('birdy-quality')` at boot (default 0), clamped `min(4, savedOr0)`.
- Every ~1.5s of accumulated real time (`perf.time`), compute `fps = frames/time`. Only evaluate while `mode==='playing' && !paused`, and only after a 3s cooldown since the last downgrade (`perf.cooldown`, decremented each window) has elapsed — so a downgrade can happen at most every ~3+1.5s and never mid-menu.
- A window counts as "slow" if `fps < 48`. Needs **two consecutive slow windows** (`perf.slow>=2`) before downgrading (avoids reacting to a single hiccup) — a single slow window increments `perf.slow`, any non-slow window resets it to 0.
- On downgrade: `quality++`; if still `< QUALITY_DPR.length` (i.e. steps 1,2,3 exist): lower `renderer.setPixelRatio` to the new step and call `resize()`; once `quality >= QUALITY_DPR.length` (i.e. all 4 DPR steps exhausted): **also disable shadow mapping** (`setShadows(false)`) as a final, one-time additional drop — this only happens once since there's no further `quality` value to reach beyond the array length re-triggering it (the `perf.slow<2 || quality>=QUALITY_DPR.length` guard at the top stops further evaluation once maxed... actually re-reading: once `quality===QUALITY_DPR.length` the guard `quality>=QUALITY_DPR.length` returns early, so shadow-disable fires exactly once then quality auto-scaling stops entirely for that session). Persist the new `quality` int to `localStorage['birdy-quality']`.
- **There is no upgrade path** — quality only ever ratchets down within a session/across sessions, never back up automatically. **Porting note:** replicate this one-directional ratchet exactly (do not "improve" it with hysteresis-based upgrades) — store the level in the native key-value storage under an equivalent key and apply it at renderer-init time on every launch (a fresh device isn't guaranteed the same headroom every run, but the spec explicitly never re-raises quality within the JS implementation, so match that for behavioral parity even though it seems like an omission).
- Dev overlay (`#fps`, bottom-left, monospace): tap the `<h1>` title 5× within 400ms of each other to toggle; text `"{fps} fps · {drawcalls} dc · Q{quality}"`; state persisted (`localStorage['birdy-fps']`) and also force-enabled by a `?fps` URL query param — **porting note: the URL-param trigger has no native equivalent and can be dropped; keep only the persisted toggle + an equivalent secret-tap gesture** (or a debug-build-only always-on flag).

## 16. Resize / orientation (`resize()`, `main.js:1941-1952`, `landscapeTouch`, `main.js:178`)

- `resize()`: sets renderer size to `app.clientWidth × clientHeight` (CSS pixels, `false` = don't also set CSS style, since it's already sized by CSS), updates `camera.aspect`, and **switches base FOV**: `baseFov = camera.aspect < 0.5 ? 74 : 68` — very narrow/tall phones (taller than 2:1) get a wider vertical FOV (74° vs 68°) so all 3 lanes stay visible at the edges. Called on `window.resize` and once at boot.
- `landscapeTouch = matchMedia('(orientation: landscape) and (pointer: coarse)')` — while true, the render loop (`tick()`, `main.js:2045-2052`) **skips calling `update()` entirely** (rendering still happens, but the game is frozen) and CSS shows the `#rotate` overlay (`style.css:88-90`) full-screen with an animated rotating-phone icon (`turn` keyframes: 1.6s, holds at -90°, snaps through to 0°, repeats) and localized text `t('rotate')`. **This only applies to touch/coarse-pointer devices** — a landscape desktop browser (`pointer: fine`) is unaffected, i.e. the rotate-lock is specifically a "phone sideways" guard, not a general aspect-ratio lock. **Porting note:** native Android should instead just lock the Activity to `portrait` in the manifest (`android:screenOrientation="portrait"`), making this entire overlay/pause-on-landscape mechanism unnecessary — simpler and stricter than the web version, which could not force orientation and had to fake it with this pause+prompt. Do not port the `#rotate` UI; there is no orientation-toggle scenario to handle for a portrait-locked native activity.
- FOV pace/rainbow "speed kick" widening during play (`updateCamera`, `main.js:1892-1899`): `pace = clamp((speed-18)/18, 0, 1)`; `fov = baseFov + pace*4 + (star-power-active ? 8 : 0)`, lerped toward target at `dt*4`. See golden fixture `main-b-camera-fov.json` for exact sampled values at both `baseFov` values (68 normal, 74 narrow-screen) crossed with representative speeds and star on/off.

## 17. Camera framing for menus (`measureMenuFrame`, `frameBird`, `main.js:1902-1938`)

Menus want the 3D bird visible in the empty band between the title and the panel, on every screen size. `measureMenuFrame()` measures (via `getBoundingClientRect`) the pixel gap between the bottom of `.menu-title` and the top of `.panel` for whichever menu (`start`/`shop`/`achievements`) is open, converts it to a fraction of `#app`'s height (`free`), and returns:
- `center`: the fraction-of-height at the vertical midpoint of that gap (where the bird should appear).
- `far`: `clamp(0.4/free, 1, 2.4)` — how far to pull the camera back; a smaller free-space fraction (short/cramped screens) pulls the camera back up to 2.4× to keep the whole bird visible in less room.
`frameBird(frame)`: projects the bird's world position through the camera, computes how far off-target (in pixels) it currently sits from `frame.center`, and applies that offset via `camera.setViewOffset(...)` (an asymmetric-frustum shift, not a camera move — keeps perspective consistent while nudging the visible crop), lerped in smoothly (`0.25` factor per call) so the frame doesn't snap. When leaving a menu (`frame` is `null`), it eases `viewShift` back to 0 and calls `camera.clearViewOffset()` once negligible.
Camera targets/looks per menu state (`updateCamera`, `main.js:1862-1899`):
- Shop: `camTarget=(5.6*far, y+0.9, -2.1*far)` (× a 1.15 multiplier if `baseFov<70`), `camLook=(0, y-0.3, 0)` — side-on view of the bird.
- Start/achievements ("ready" but not shop): `camTarget=(0, y+1.2*far, 6.5*far)`, `camLook=(0, y-0.6, -9.5)` — behind-the-bird view, pulled back by `far`.
- Playing/dead: fixed gameplay chase cam, `camTarget=(0, 7.5+y*0.6, 14)`, `camLook=(0, 1.8+y*0.6, -22)` — no menu framing logic applies.
Camera position/look lerp rate: `k = min(1, dt*(menu ? 3.5 : 6))` — menus ease slower (3.5) than gameplay (6) camera moves.
Camera shake on hit (`state.shake`, decremented each frame, magnitude `shake*0.8`, applied as `±random*0.5*magnitude` jitter to `camera.position.x/y`) — set to `0.5` in `die()`.

**Porting note:** `setViewOffset`'s asymmetric-frustum crop is a standard technique reproducible with a manually-adjusted projection matrix (`glFrustum`/custom perspective matrix with an x/y offset term) in the small GL engine — document this as a required primitive of the camera/projection module, not something to drop.

## 18. Death & impact feedback (`die(cause)`, `main.js:1390-1422`)

Only fires once (`if state.mode!=='playing') return`). Cause ∈ `{'pipe-top','pipe-bottom','plant','ground','blocked'}` (see main-a for where these are raised). Effects, all simultaneous:
1. `state.mode='dead'`; hide marker/hand/zone-overlay.
2. `state.hitStop = HIT_STOP (0.14s)` — a true freeze-frame: `update()` (`main.js:2055-2078`) short-circuits to *only* advance camera + impact-particle timers while `hitStop>0`, everything else (physics, scoring, animation) is frozen for that duration.
3. `buzz(70)` (70ms vibration).
4. `lastRun` snapshot recorded (score/coins/runTime/cause/zone) — consumed by `showGameOver()` later and by the headless `simulate()` bot harness.
5. `state.shake=0.5`; `state.vy = max(vy,6)` (guarantees at least a small upward "bonk" pop even if falling fast).
6. `sfx.hit()`; `music.duck()`; `music.setHype(false)`; `bird.setGlow(null)`.
7. Feather particle burst at the bird: 36 particles in the bird's own skin colors (`body, body, belly, wing, white`), speed 9, size 0.15, life 1.3s, gravity -8 (a satisfying "poof" of feathers falling).
8. A "bonk" impact star effect positioned at `bird position + HIT_OFFSET[cause]` — offset table (`main.js:1388`):

| cause | offset (x,y,z) |
|---|---|
| pipe-top | (0.25, 0.8, 0) |
| pipe-bottom | (0.25, -0.75, 0) |
| plant | (0.25, -0.75, 0) |
| ground | (0.25, -0.7, 0) |
| blocked | (0.8, 0.45, -0.6) |
(default/unlisted cause falls back to `blocked`'s offset) — chosen so the bonk star appears on the side that was hit while the squashed bird sprite remains visible next to it, not hidden behind the star.
9. Bird mesh **squashed flat**: `scale.set(sc*1.3, sc*0.72, sc*1.25)` (wider+shallower+deeper) as an instant (non-animated) snap, layered on top of whatever normal squash/stretch scale it already had.
10. White screen flash: `flash.style.opacity` snapped to `0.55` with `transition:none`, then on the next animation frame the transition is re-enabled (`opacity .35s`) and opacity set to `0` — this two-step dance is required to get an instant flash-on followed by an animated fade-out rather than an animated fade-in-then-out.

After death, `updateDead()` (`main.js:1796-1806`) lets the bird continue falling under gravity (spinning: `rotation.z += dt*6`) until it reaches `state.radius` above ground, purely cosmetic (no more collision checks), while gates already on-screen keep animating; after `deadTimer>0.45s`, `showGameOver()` fires (§5).

## 20. Edge cases and ordering subtleties worth getting exactly right

1. **Restart debounce (350ms)** applies to *both* the tap-to-retry and the keyboard Enter/Space paths (`tryRestart()` is the single gate, called from 3 places) — do not special-case keyboard input to skip the debounce.
2. **Game-over "to-best" text uses `missing+1`**, not `missing` (§5.5) — an easy off-by-one to get wrong when porting.
3. **`renderNextUnlock()` computes across ALL catalog kinds**, not just the currently-viewed shop tab — the game-over nudge can point at any cosmetic type.
4. **The daily-gift preview amount is `giftAmount(streak+1)`**, i.e. it always previews the reward *for claiming now*, not the current streak's historical reward.
5. **Toast queue is not cleared on death/game-over**, only on `resetGame()` — a mission-complete toast queued right before death will still show over the game-over screen.
6. **Quality only ever decreases** (§15) — confirmed intentional by the code structure (no upgrade branch exists), preserve this even though it might look like a missing feature.
7. **`updateZonesOverlay` memoizes on `${b1}|${b2}|${lane}`** specifically to avoid resetting the CSS animation every frame (which would restart the fade/pulse) — a naive per-frame `innerHTML`/style rewrite would break the `.show` one-shot-fade entirely (it would never reach the faded resting state). Port this as "only touch the overlay's visual properties when the lane geometry actually changes."
8. **`#gameover`'s next-unlock tap-shortcut is checked before the generic "tap anywhere to retry"** handler in the same `pointerdown` listener (§5) — order of the `if` chain matters.
9. **Tutorial: a tap on the bird's own (already-current) lane while frozen in `switch` step is silently swallowed** (no flap, no lane change) — only a tap on a genuinely different lane advances the tutorial.
10. **`goToMenu()` zeroes `state.power` but does NOT reset `state.score`/`state.coins`/etc.** — those are irrelevant once `mode` leaves `playing`/`dead`/`over`, but note that `resetGame()` (not `goToMenu()`) is what actually re-zeroes the run counters; going to the menu and starting a fresh run always goes through `resetGame()` again regardless of path taken to reach the menu.
11. **Short-screen (`max-height:720px`) CSS overrides** shrink several menu elements and, notably, **hide the wallet chip entirely on the game-over screen** (`.wallet.over{display:none}`) — on very short devices the coin count is simply not shown on that screen; do not treat this as a bug to "fix" when porting to a phone with a small screen.

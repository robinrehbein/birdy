# audio: procedural WebAudio music + SFX synth (no audio assets)

Source of truth: `src/audio.js` (388 lines), current file, all line numbers 1-indexed and
cited as `audio.js:N`. Consumers referenced for context only (not specced here — see their
own spec files/future specs): `src/main.js` (imports `sfx, music, audio, renderMusic` at
`main.js:4`, calls `music.beat()` every frame to drive cactus timing, calls `audio.unlock()` +
`music.start()` on the first tap), `src/world.js:960` (cactus pop-up timing consumes the
`beat` value that `music.beat()` produces — see `world.md` §"plant timing" / the
`world-plant-timing.json` golden fixture for the consumer-side math; this doc only specs
where the `beat` number *comes from*), `src/i18n.js:89-90,178-179` (mute button label
strings `muteOn`/`muteOff`, not part of this file).

There are **no visual assets** in this module (no meshes, colors, or materials — it is a
pure audio synthesis engine). "Visuals" is N/A here.

Golden fixtures for every pure/formulaic piece: `docs/native/golden/audio-*.json`,
generated by `scripts/native-golden/audio-*.mjs` (kept in the repo; re-run with
`node scripts/native-golden/<file>.mjs`). Truly random pieces (flap pitch jitter, noise
buffer start offset, the reverb impulse response, the white-noise buffer content) are
**not** fixtured bit-exact — they are unseeded `Math.random()` in the JS itself, so the JS
reference never reproduces them either. These are specified as formulas/ranges instead
(see §8, §10.7 "Randomness" below).

## 2. Mute persistence (`audio.js:12-15`, `audio.js:321-325`)

- Storage key: **`birdy-muted`** (exact string), value `'1'` (muted) or `'0'` (unmuted),
  read/written via `localStorage`. This is the only `localStorage` key this module owns.
- `loadMuted()`: returns `true` iff `localStorage.getItem('birdy-muted') === '1'`; any
  thrown exception (storage unavailable) or missing key → `false` (default unmuted).
- `audio.setMuted(v)` (`audio.js:321-325`): sets the in-memory flag, best-effort writes the
  key (swallows write errors silently), and if `master` already exists sets
  `master.gain.value = v ? 0 : 1` **immediately** (a hard, unramped mute/unmute — no
  envelope, no click-avoidance beyond what an instant gain-value assignment gives you in
  WebAudio, which just snaps at the next audio-render quantum).
- If `master` does not exist yet (audio graph never built because no gesture happened),
  the mute flag is still recorded and takes effect via `buildGraph(ctx, muted ? 0 : 1)`
  (`audio.js:78`) the first time the graph *is* built — i.e. a muted player who has never
  interacted starts with `master` gain already at `0`, not `1`-then-`0`.

## 3. First-user-gesture gating (`audio.js:68-82`)

Browsers block audio before a user gesture. The JS models this as:

- `unlocked` starts `false`.
- `audio.unlock()` (`audio.js:314-317`) sets `unlocked = true` and calls `ensure()`. It is
  called once, from `main.js:1041`, on the very first tap.
- `ensure()` (`audio.js:72-82`):
  1. If `!ctx && !offline && !unlocked` → return `null` (refuse to build/use the graph —
     "sounds requested before the first tap are simply skipped", `audio.js:68-69`).
  2. Else, if `ctx` doesn't exist yet, construct it: pick `window.AudioContext ||
     window.webkitAudioContext`; if neither exists, return `null` (no Web Audio support).
     Then call `buildGraph(ctx, muted ? 0 : 1)` (§4) and destructure `master, musicBus,
     sfxBus, noise` from its result.
  3. If `ctx.state === 'suspended' && !suspended && !offline`, call `ctx.resume()`
     (auto-resume on first real use, but never fights an explicit app-level pause).
  4. Return `ctx`.
- Every sound-producing call (`tone()`, `sfx.*`, `music.start()`) routes through `ensure()`
  first and silently no-ops if it returns `null`. **Porting note**: on Android there is no
  browser-gesture restriction, so the native `AudioEngine` can build its output pipeline
  eagerly at app start; `unlocked`/the gesture gate can be ported as an always-true no-op,
  or dropped, as long as nothing plays before the migrated equivalent of "first tap" if the
  product wants to preserve that behavior for consistency (not required for correctness).

## 4. Mixing graph — `buildGraph(ac, masterGain)` (`audio.js:21-66`)

Shared verbatim by the live context and `renderMusic`'s offline context. Signal flow:

```
music bus (gain 0.3) ──> lowpass (6500 Hz, Q 0.5) ──┬──> compressor ──> master gain ──> destination
                                                     └──> musicSend (gain 0.22) ──> reverb ──┐
sfx bus (gain 1, default) ───────────────────────────┬──> compressor (same node as above)    │
                                                      └──> sfxSend (gain 0.12) ──> reverb ────┤
                                                                                                ↓
                                                                          reverb (convolver) ──> wet gain (0.35) ──> compressor
```

Exact node parameters:

| Node | Params | Line |
|---|---|---|
| `comp` (DynamicsCompressorNode) | `threshold = -14` dB, `knee = 12` dB, `ratio = 3`, `attack = 0.005` s, `release = 0.2` s | `audio.js:22-27` |
| `out` (master GainNode) | `gain = masterGain` (the `1` or `0` passed in, i.e. `muted?0:1` for the live graph, always `1` for offline render) | `audio.js:28-29` |
| Reverb impulse response | Mono `AudioBuffer`, length `= floor(sampleRate * 1.2)` samples (1.2 s), content `d[i] = (Math.random()*2-1) * (1 - i/len)^3` per sample — **exponentially-decaying white noise**, cubic decay curve. **Not reproducible bit-exact** (unseeded `Math.random()`); port as: generate white noise, multiply by `(1 - i/len)^3` envelope, same length formula. Perceptually a short, dense "room" — exact noise realization does not matter. | `audio.js:33-39` |
| `reverb` (ConvolverNode) | `buffer = ir` above | `audio.js:38-39` |
| `wet` (reverb output gain) | `gain = 0.35` | `audio.js:40-41` |
| `music` bus (GainNode) | `gain = MUSIC_VOLUME = 0.3` | `audio.js:44-45` |
| `tone` (BiquadFilter on music bus) | `type = 'lowpass'`, `frequency = 6500` Hz, `Q = 0.5` | `audio.js:46-49` |
| `musicSend` (music → reverb send) | `gain = 0.22` | `audio.js:52-53` |
| `sfx` bus (GainNode) | `gain` left at WebAudio default (`1`) — never explicitly set | `audio.js:56-57` |
| `sfxSend` (sfx → reverb send) | `gain = 0.12` | `audio.js:58-59` |
| White-noise buffer (`nz`) | Mono, length `= sampleRate` samples (1 s), `nd[i] = Math.random()*2-1` per sample — uniform white noise. Not reproducible bit-exact; shared by every `noiseHit()` call (each picks a random 0–0.5 s start offset into it, see §8.2). | `audio.js:62-64` |

Routing order exactly as coded: `music → tone(lowpass) → comp`; `tone → musicSend → reverb → wet → comp`; `sfx → comp` directly; `sfx → sfxSend → reverb → wet → comp` (same reverb/wet chain, shared with music); `comp → out → destination`.

Return value `{ master: out, musicBus: music, sfxBus: sfx, noise: nz }` is what `ensure()`/`renderMusic()` destructure into the module state.

**Porting note (DSP)**: this whole graph must be reproduced with native primitives — see §11 "Porting notes: Web Audio → native DSP" for the concrete Android/iOS mapping of each node type (dynamics compressor, convolution reverb, biquad lowpass, gain).

## 6. `tone(...)` helper (`audio.js:86-101`)

Signature (all named/optional params): `{ freq, to = freq, dur = 0.12, type = 'square', vol = 0.12, delay = 0, at, dest }`.

1. `ac = ensure()`; if `null`, no-op (see §3).
2. Start time `t = at ?? (ac.currentTime + delay)` — either an absolute schedule time
   (used by the music sequencer, which always passes `at`) or "now + delay" (used by SFX,
   which never passes `at` but does often pass `delay`).
3. Create `OscillatorNode` (`type`) + `GainNode`.
4. `osc.frequency.setValueAtTime(freq, t)`; if `to !== freq`,
   `osc.frequency.exponentialRampToValueAtTime(to, t + dur)` — an exponential (i.e.
   log-linear / constant-ratio-per-second) glide from `freq` to `to` over the full note
   duration `dur`. If `to === freq` the oscillator holds a constant pitch.
5. Gain envelope (exponential, since `GainNode.gain.exponentialRampToValueAtTime` cannot
   ramp to/from exactly `0`, so `0.0001` is used as the effective floor):
   - `gain.gain.setValueAtTime(0.0001, t)`
   - `gain.gain.exponentialRampToValueAtTime(vol, t + 0.006)` — 6 ms attack, exponential
     curve from `0.0001` to `vol`.
   - `gain.gain.exponentialRampToValueAtTime(0.0001, t + dur)` — exponential decay from
     `vol` back to the `0.0001` floor, finishing exactly at `t + dur` (so if `dur` is short,
     e.g. `<0.006`, the decay ramp start time `t+0.006` can be *after* its nominal end time
     `t+dur`; WebAudio silently clamps/handles this — no note in the JS guards against it,
     so the port should just let the same numeric ramp happen, potentially producing a
     near-instant blip for `dur < 0.006`; no such call sites exist today, though, see §10.7
     "shortest dur used").
6. `osc.connect(gain).connect(dest || sfxBus)` — `dest` lets music route to `musicBus`
   instead of the default `sfxBus`.
7. `osc.start(t)`; `osc.stop(t + dur + 0.02)` (20 ms tail past the nominal duration, to let
   the exponential decay's asymptote settle before the node is torn down — the decay never
   truly reaches 0, so this is just a safe cutoff).

Oscillator waveform types used anywhere in this file: `'square'`, `'triangle'`, `'sine'`,
`'sawtooth'` — i.e. all four standard WebAudio periodic waves, no custom `PeriodicWave`.
**Porting note**: a native synth needs the same 4 bandlimited (or at minimum
click-free/anti-aliased-enough) waveform generators; see §11.

## 7. `noiseHit(...)` helper (`audio.js:103-115`)

Signature: `{ at, dur, vol, cutoff, dest }` (no defaults — always called with all of these
except `dest`).

1. `AudioBufferSourceNode` playing the shared 1-second `noise` buffer (§4).
2. `BiquadFilterNode`, `type = 'highpass'`, `frequency = cutoff`.
3. `GainNode`: `setValueAtTime(vol, at)` then `exponentialRampToValueAtTime(0.0001, at + dur)`
   — instantaneous attack (no 6 ms ramp-in, unlike `tone()`), exponential decay to the floor
   over `dur` seconds.
4. Routing: `src → filter → gain → (dest || sfxBus)`.
5. `src.start(at, Math.random() * 0.5)` — **starts playback at a random offset between 0
   and 0.5 s into the 1-second noise buffer** (so repeated hits don't all sound identical);
   not reproducible bit-exact, see §10.7.
6. `src.stop(at + dur + 0.02)` — same 20 ms tail convention as `tone()`.

Note this helper reads `ctx`/`noise` directly (not via `ensure()`) — it is only ever called
from places that already called `ensure()` first (either explicitly, or implicitly because
they run inside `playStep`, which is only invoked once the music transport is running).
**Porting risk**: if a native caller ever invokes the `noiseHit` equivalent without the
engine having been initialized, it will NPE/crash where the JS would (this is the one
place in the file that skips the `ensure()` guard) — a Kotlin port should either guard here
too, or guarantee-by-construction (e.g. non-nullable initialized-at-construction fields)
that this can't happen, matching the *practical* behavior rather than the letter of the bug.

## 8. Music sequencer

### 8.1 Transport constants (`audio.js:117-120`)

| Constant | Value | Meaning |
|---|---|---|
| `BPM` | `124` | Fixed tempo in **every** theme — "tempo stays at 124 BPM in every theme so the cacti stay on beat" (`audio.js:118`) |
| `STEP` | `60 / 124 / 4 = 0.12096774193548387` s | Duration of one 16th note (the sequencer's atomic step) |

Derived (not named constants in the JS, but used as literals / structural facts):
- 1 beat (quarter note) = `STEP * 4 = 0.4838709677419355` s → **beat is quarter notes**, matches `music.beat()` (§8.6).
- 1 bar = 16 steps = `STEP * 16` s.
- The song form is 16 bars = 256 steps long, then loops (`step = (step + 1) % 256`, `audio.js:250`).
- Scheduler wall-clock cadence: a `setInterval` fires every **25 ms** (`audio.js:261`) and
  each tick schedules every step whose time falls within the next **0.12 s** lookahead
  window (`while (nextTime < ctx.currentTime + 0.12)`, `audio.js:247`) — a standard
  look-ahead scheduler to stay robust against `setInterval` jitter. Since `STEP ≈ 0.121 s`
  is just over the 0.12 s lookahead, in steady state **exactly one step is scheduled per
  tick** (occasionally the timing could schedule 0 or 2 in a row depending on jitter — a
  Kotlin port on a dedicated audio/timer thread can use a tighter or sample-accurate
  scheduler instead and does not need to reproduce the 25 ms/0.12 s specifics, only the
  *musical* timeline in `docs/native/golden/audio-timing.json`).
- `startOffsetSec = 0.05` — `music.start()` sets `nextTime = startTime = ac.currentTime + 0.05` (`audio.js:260`), i.e. the very first step is scheduled 50 ms in the future, not at time 0.

Golden fixture: `docs/native/golden/audio-timing.json` (BPM, STEP, scheduler constants, the
`beat()` formula sampled over `elapsedSec ∈ [0,4]`, and the `tone()`/`noiseHit()` envelope
shapes as formulas).

| Chord | Notes (MIDI) |
|---|---|
| `C` | `[60, 64, 67]` |
| `Am` | `[57, 60, 64]` |
| `F` | `[53, 57, 60]` |
| `G` | `[55, 59, 62]` |
| `Em` | `[52, 55, 59]` |

**Melody A** (`MELODY_A`, `audio.js:126-131`) and **Melody B** (`MELODY_B`, `audio.js:132-137`):

Copy these two arrays verbatim (26 entries in A, 23 in B) — see the JS for the literal

`toMap` (`audio.js:138`) converts each melody array into a step→`[note,length]` lookup
(a `Map` in JS; a `Map<Int, Pair<Int,Int>>` or similar in Kotlin) for O(1) lookup by
`step % 64` during playback.

**Sections** (`SECTIONS`, `audio.js:139-142`):

| Section | Chord progression (4 bars) | Melody |
|---|---|---|
| `A` | `C, Am, F, G` | `MELODY_A` |
| `B` | `F, G, Em, Am` | `MELODY_B` |

**Song form** (`FORM`, `audio.js:144-149`) — 4 parts × 4 bars = 16 bars total:

| Part index | Section | Flags |
|---|---|---|
| 0 | `A` | — |
| 1 | `A` | `harmony: true` (adds a second, quieter melody voice a major third below — actually see §8.4, it's `n - 4` semitones = a major third down) |
| 2 | `B` | — |
| 3 | `A` | `breakdown: true` (first 2 of its 4 bars: drums silenced except a sparse hi-hat tick, bass silenced in bar 0 of the breakdown, melody silenced) |

`part = FORM[floor(bar/4)]` where `bar = floor(step/16)`, `bar ∈ [0,15]`; `barInSec = bar % 4` indexes into the 4-bar `chords` array of whichever section is active.

### 8.3 Zone themes (`THEMES`, `audio.js:152-157`)

One theme per zone (indices correspond to `main.js`'s zone/biome index, `music.setTheme(zone)` at `main.js:1541`):

| Index | Zone (comment) | `key` (semitone transpose) | `lead` waveform | `leadVol` | `octave` extra | `arp` pattern | `arpType` | `drums` kind | `minor` |
|---|---|---|---|---|---|---|---|---|---|
| 0 | Stadtpark (City Park) | `0` | `square` | `0.07` | — (0) | `[0,1,2,1]` | `square` | `pop` | false |
| 1 | Herbstwald (Autumn Forest) | `-3` | `triangle` | `0.16` | — (0) | `[0,2,1,2]` | `square` | `shuffle` | false |
| 2 | Canyon | `-5` | `sawtooth` | `0.04` | — (0) | `[0,1,0,2]` | `triangle` | `desert` | **true** |
| 3 | Blütenhain (Blossom Grove) | `2` | `sine` | `0.12` | `12` | `[0,1,2,3]` | `sine` | `light` | false |

`music.setTheme(i)` (`audio.js:271-275`) normalizes `i` into `[0, THEMES.length)` with
`((i % THEMES.length) + THEMES.length) % THEMES.length` (correct modulo for negative `i`
too), looks up `THEMES[...]`, and if it differs from the current `theme` object, stores it
in `pendingTheme` (applied on the next bar line, see §8.5 "Deferred switches").

`theme.minor` only affects section `A`'s chord progression: when true, `A`'s 4-bar
progression becomes `['Am', 'F', 'C', 'G']` instead of the default `['C','Am','F','G']`
(`audio.js:208`) — section `B`'s progression is never affected by `minor`.

`theme.octave` (only set, to `12`, for theme 3) is added to the melody note's MIDI number
before converting to Hz (§8.4) — i.e. theme 3's lead plays a full octave higher than its
raw melody data would otherwise imply, on top of its own `key` transpose.

### 8.4 Bass pattern (`BASS`, `audio.js:158`)

`BASS = { 0: 0, 3: 0, 6: 12, 8: 0, 11: 0, 14: 7 }` — maps `inBar` (0..15, the 16th-note
position within a bar) to a **semitone offset** added to the bass note. A bass note is
played only at these 6 positions per bar (steps 0,3,6,8,11,14 of each 16-step bar); all
other `inBar` values play no bass note.

Bass note formula (`audio.js:219`): `freq = midi(chord[0] - 12 + BASS[inBar])` where
`chord[0]` is the current bar's chord root (already transposed by `theme.key`). I.e. the
bass sits one octave below the chord root by default (`-12`), and at `inBar===6` jumps back
up an octave (`+12` cancels the `-12` → root pitch), and at `inBar===14` plays the fifth
above the low root (`+7` semitones from the `-12` root = a perfect fifth up from the low
root, still below the chord root itself). Duration `STEP * 1.6` (slightly longer than one
16th note, so bass notes overlap/legato into the next). Volume `0.55` normally, `0.3` in
calm/menu mode (`calm ? 0.3 : 0.55`). Waveform always `triangle`. Suppressed entirely when
`breakdown && barInSec === 0` (first bar of a breakdown plays no bass at all, regardless of
`inBar`) — `audio.js:218`.

### 8.5 `playStep(s, t)` — full per-step logic (`audio.js:196-243`)

Called once per 16th-note step, `s` the absolute step counter (`0..255`, wraps every 256
via `schedule()`), `t` the absolute AudioContext time this step should sound at.

1. `bar = floor(s / 16)` (`0..15`), `inBar = s % 16` (`0..15`).
2. **Deferred switches** (`audio.js:199-203`): only when `inBar === 0` (start of a new bar):
   if `pendingTheme` is set, `theme = pendingTheme; pendingTheme = null`; same for
   `pendingMode`/`mode`. This is why `music.setTheme`/`setMode` calls take effect "on the
   next bar line" rather than instantly — up to one full bar (`16 * STEP ≈ 1.94` s at
   124 BPM) of latency in the worst case (call happens the instant after `inBar` passed 0).
3. `part = FORM[floor(bar/4)]`, `sec = SECTIONS[part.sec]`, `barInSec = bar % 4`.
4. `chordName = sec.chords[barInSec]`, overridden to `['Am','F','C','G'][barInSec]` if
   `theme.minor && part.sec === 'A'` (§8.3).
5. `chord = TRIADS[chordName].map(n => n + theme.key)` — the active triad, transposed.
6. `calm = mode === 'menu'`; `breakdown = part.breakdown && barInSec < 2` (true only in the
   first half — 2 of 4 bars — of a `breakdown`-flagged form part).
7. **Drums**: if `!calm && !breakdown`, call `drums(theme.drums, inBar, t)` (§8.6). Else if
   `!calm && breakdown && inBar % 4 === 2`, play a single quiet hi-hat-style `noiseHit`
   (`dur 0.03, vol 0.06, cutoff 7000`) as the only percussion during a breakdown — a sparse
   tick every 4 steps. In calm/menu mode, **no drums at all**, ever, including no breakdown
   tick (the tick itself is gated on `!calm`).
8. **Bass**: as in §8.4.
9. **Arpeggio** (`audio.js:222-228`): `arpEvery = (theme.arp.length === 4 && theme.drums === 'light') ? 1 : 2` — i.e. **only theme 3 (Blütenhain, drums `'light'`, 4-element arp) plays the arpeggio on every 16th note**; every other theme plays it on every *other* 16th note (8th-note arpeggio). If `s % arpEvery === 0`: `i = theme.arp[(s/arpEvery) % theme.arp.length]`; note `n = (i === 3) ? chord[0] + 12 : chord[i]` (index `3` is a special sentinel meaning "root, one octave up" rather than a real chord-tone index — chords only have indices 0/1/2); final frequency `midi(n + 12)` (the whole arpeggio sits one octave above the chord/bass register). Duration `STEP * 0.9`. Type `theme.arpType`. Volume `0.05` if `arpType === 'square'` else `0.09`.
10. **Hype sparkle** (`audio.js:229-233`): if the external `hype` flag is set (see §8.7) and `!calm`: `idx = [0,1,2,1][s % 4]`, note `chord[idx] + 24` (two octaves above the chord tone), `midi(...)`, duration `STEP * 0.7`, always `square` waveform, volume `0.035`. This is an always-on-every-4th-of-the-arpeggio-pattern sparkle layer overlaid whenever a rainbow/hype power-up is active; independent of `theme.arp`/`arpType`.
11. **Melody** (`audio.js:236-242`): look up `sec.melody.get(s % 64)` (the section's own 64-step-long melody loop, independent of the 256-step song-level loop — i.e. within one 4-bar section repeat both `MELODY_A` and `MELODY_B` patterns tile every 4 bars, and since each `FORM` part is exactly 4 bars = 64 steps, each part plays its section's full melody exactly once). Suppressed entirely if `part.breakdown && barInSec < 2` (breakdown's silent half — matches drums/bass suppression, but note the *condition test uses `part.breakdown`+`barInSec` directly again*, not the already-computed `breakdown` local, though they are equivalent). If a note exists: `n = note[0] + theme.key + (theme.octave || 0)`; `vol = theme.leadVol * (calm ? 0.6 : 1)`; duration `STEP * note[1] * 0.95` (95% of its nominal length, for a slight staccato gap between notes); waveform `theme.lead`. If `part.harmony` (only form part 1), also play a second voice: `midi(n - 4)` (major third below), duration `STEP * note[1] * 0.9` (90% length, slightly shorter/more detached than the lead), same waveform, volume `vol * 0.5`.

Golden fixture: `docs/native/golden/audio-song-trace.json` — the fully expanded, per-step,
per-theme (`mode: 'game'`) event trace for all 256 steps × 4 themes (drums/bass/arp/melody
choices, exact MIDI numbers and Hz, exact durations/volumes/delays), plus a `calmTransform`
section documenting the closed-form relationship between `game` and `menu` mode (calm mode
is a pure function of the game-mode values: mute drums, bass `vol *= 0.3/0.55`, melody
`vol *= 0.6`, hype sparkle forced off — nothing about *which* notes play changes). This
fixture is the primary thing to diff a Kotlin port's output against.

### 8.6 `drums(kind, inBar, t)` (`audio.js:171-194`)

Four drum-kit "kinds", selected per-theme via `theme.drums`. Three shared voice helpers:
`kick(v=0.9)` = `tone({freq:150, to:45, dur:0.14, type:'sine', vol:v, at:t, dest:musicBus})`;
`snare(v=0.35)` = `noiseHit({at:t, dur:0.12, vol:v, cutoff:1500, dest:musicBus})`;
`hat(v)` = `noiseHit({at:t, dur:0.03, vol:v, cutoff:7000, dest:musicBus})` (no default — always called with an explicit `v`).

| Kind | Pattern (`inBar` = step within the 16-step bar, `0..15`) |
|---|---|
| `pop` | kick at `inBar % 8 === 0` (i.e. steps 0, 8); snare at `inBar ∈ {4, 12}`; hat at every even `inBar`, velocity `0.14` when `inBar % 4 === 2` else `0.07` |
| `shuffle` | kick at `inBar ∈ {0, 10}`; snare (`0.35`) at `inBar ∈ {4, 12}`; extra quiet snare (`0.12`) at `inBar === 14`; hat at `inBar ∈ {2,3,6,7,10,11,14,15}`, velocity `0.05` when `inBar` is odd else `0.12` |
| `desert` | kick (`0.85`) at `inBar ∈ {0, 6, 12}`; snare (`0.3`) at `inBar === 8`; hat (`0.1`) at `inBar % 4 === 2`; plus a distinct low "blip" tone (not a drum voice — a direct `tone()` call) at `inBar ∈ {3, 11}`: `{freq:220, to:110, dur:0.12, type:'sine', vol:0.3}` |
| (else, i.e. `light`) | kick (`0.7`) at `inBar ∈ {0, 8}`; snare (`0.22`) at `inBar === 12`; hat (`0.05`) at every odd `inBar` |

All drum-voice `tone`/`noiseHit` calls route to `musicBus` (`dest: musicBus`), not `sfxBus`.

### 8.7 `music` public API (`audio.js:254-291`)

State not yet covered: `playing` (bool), `step` (0..255 current position), `nextTime`
(seconds, next unscheduled step's AudioContext time), `startTime` (seconds, when step 0 was
scheduled), `timer` (interval handle), `hype` (bool, §8.5 step 10).

- **`start()`** (`audio.js:255-262`): `ac = ensure()`; no-op if `!ac` or already `playing`.
  Sets `playing = true`, resets `step = 0`, `nextTime = startTime = ac.currentTime + 0.05`,
  and starts the 25 ms `setInterval(schedule, 25)` (§8.1, §8.8).
- **`beat()`** (`audio.js:264-267`): returns `null` if not `playing` or no `ctx`; else
  `(ctx.currentTime - startTime) / (STEP * 4)` — **elapsed time since transport start,
  expressed in quarter notes** (beats). This is the exact value `world.js` consumes for
  cactus pop-timing (see `world.md`). Note it is **not clamped to the 16-bar loop** — it
  keeps counting up forever (monotonic), even though the note *pattern* loops every 256
  steps = 64 beats; consumers that need a "position within the loop" must take `% 64`
  themselves (`world.js`'s plant timing takes `beat % 4`, i.e. only cares about a 1-bar
  cycle, so this has never needed to be addressed at the `music` module level).
- **`setHype(v)`** (`audio.js:268-270`): sets `hype = v` directly — **not** deferred to a
  bar line (unlike theme/mode), takes effect on the very next step evaluated.
- **`setTheme(i)`** (`audio.js:271-275`): see §8.3. Deferred to next bar line.
- **`setMode(m)`** (`audio.js:276-279`): if `m !== mode`, `pendingMode = m`. Deferred to
  next bar line. Values used elsewhere in the codebase: `'game'` and `'menu'`.
- **`duck()`** (`audio.js:280-286`): no-op if `!ctx`. Otherwise, at `t = ctx.currentTime`:
  `musicBus.gain.cancelScheduledValues(t)`, then `musicBus.gain.setTargetAtTime(0.06, t,
  0.05)` (exponentially approach `0.06` with **time constant** `0.05` s — WebAudio
  `setTargetAtTime` formula: `v(τ) = target + (v0 - target) * e^(-τ/timeConstant)` for
  `τ = time - t`), then `musicBus.gain.setTargetAtTime(MUSIC_VOLUME /* 0.3 */, t + 1.4,
  0.4)` (starting 1.4 s later, exponentially approach `0.3` with time constant `0.4` s).
  Net effect: an audible "duck" of the music bed down to `0.06` gain almost immediately
  (5 %/95%-settling ≈ `3×0.05=0.15` s), held low for about 1.4 s, then recovered back up to
  full `0.3` gain over roughly `3×0.4=1.2` s. Called on a crash/hit (`main.js:1403`) to let
  the hit SFX read clearly over the music.
- **`stop()`** (`audio.js:287-290`): `playing = false`, `clearInterval(timer)`. Does **not**
  reset `step`/`nextTime`/`startTime` — a subsequent `start()` always resets them anyway
  (see above), so this has no observable effect on next playback, but note it for parity
  (a native port's `stop()` need not reset position either, since `start()` always will).

### 8.8 `schedule()` (`audio.js:245-252`)

```
if (!ctx || suspended) return
while (nextTime < ctx.currentTime + 0.12):
    playStep(step, nextTime)
    nextTime += STEP
    step = (step + 1) % 256
```
Run every 25 ms by the `setInterval` started in `music.start()`. This is the classic
"look-ahead" audio scheduler pattern (schedule slightly into the future each tick, so
`setInterval`'s imprecision never causes an audible gap) — see §8.1 for the specific
numbers. **Porting note**: a Kotlin implementation should use whatever precise/steady
timer/audio-clock primitive the platform offers (e.g. driving scheduling off the actual
audio callback / a dedicated high-priority timer) rather than literally porting
`setInterval`; only the *musical* result (which step sounds at which time, relative to
`startTime`) needs to match, not this specific wall-clock polling mechanism.

### 8.9 `renderMusic(options)` (`audio.js:293-311`, exported, offline utility)

Used for "checking levels and listening to the themes without playing" (`audio.js:293-294`)
— i.e. an internal/dev tool, not part of the live gameplay audio path. Options:
`{ seconds = 31, themeIndex = 0, calm = false }`.

1. Saves the entire current module-level audio state (`ctx, master, musicBus, sfxBus,
   noise, theme, mode, hype, offline, pendingTheme, pendingMode`) to restore afterward.
2. Creates an `OfflineAudioContext(1 /*mono*/, ceil(44100*seconds), 44100)` and assigns it
   as the module's `ctx`; sets `offline = true` (bypasses the gesture gate).
3. Rebuilds the graph via `buildGraph(off, 1)` (master gain always `1` regardless of mute —
   offline render is never muted).
4. Sets `theme = THEMES[themeIndex]`, `mode = calm ? 'menu' : 'game'`, `hype = false`,
   clears both pending-switch slots.
5. Manually drives the sequencer without any real-time scheduler: `for (t=0.05, s=0; t <
   seconds-0.2; t += STEP, s = (s+1) % 256) playStep(s, t)` — i.e. render starts at `t=0.05`
   (matching the live transport's start offset) and stops scheduling new steps once
   `t >= seconds - 0.2` (leaves 0.2 s of tail room in the buffer for the last note's decay
   to finish before the buffer ends).
6. `await off.startRendering()`, restores all saved state, returns
   `out.getChannelData(0)` — a `Float32Array` of mono PCM samples at 44.1 kHz.

**Porting note**: this is a nice-to-have dev/QA tool, not gameplay-critical. If ported at
all (e.g. for automated audio regression tests, akin to how `docs/native/golden/*.json`
verify note *selection*, an offline PCM render could additionally verify *sound*), the
native equivalent renders the same step/time loop through the same synth voices into an
offline PCM buffer — no interactive audio device needed, useful for headless/CI testing.

## 10. `sfx` public API (`audio.js:335-388`)

Shared state: `coinCombo` (int, starts `0`), `lastCoin` (ms timestamp, starts `0`) — used
only by `sfx.coin()`.

### 10.1 `flap()` (`audio.js:339-345`)
- Pitch jitter `k = 0.94 + Math.random() * 0.12` (uniform in `[0.94, 1.06)`) — "slight
  random pitch so rapid flapping doesn't sound like a machine gun" (`audio.js:340`).
- `tone({freq: 380*k, to: 620*k, dur: 0.09, type: 'triangle', vol: 0.18})` — upward chirp,
  frequency range scales with `k` (so both start and end move together, preserving the
  ratio `620/380 ≈ 1.632`).
- Plus, if `ensure()` succeeds, a `noiseHit({at: now, dur: 0.06, vol: 0.05, cutoff: 3000})`
  — a short breathy/wing-flap noise layered under the tone.
- Routes to default `dest` (`sfxBus`) for both.

### 10.2 `swoosh()` (`audio.js:346-349`)
- Single `noiseHit({dur: 0.18, vol: 0.12, cutoff: 1200})` at `ensure()`'s current time. No
  tonal component. Used for menu navigation whooshes.

### 10.3 `point()` (`audio.js:350-353`)
- Two fixed square tones: `{freq: 988, dur: 0.08, vol: 0.06}` immediately, `{freq: 1319,
  dur: 0.16, vol: 0.06, delay: 0.07}` — a two-note "ding-ding" (988 Hz ≈ B5, 1319 Hz ≈ E6).

### 10.4 `coin()` (`audio.js:354-362`)
- Combo logic: `now = performance.now()`; if `now - lastCoin < 700` (ms), `coinCombo =
  min(coinCombo + 1, 7)`, else reset `coinCombo = 0`. Then `lastCoin = now`.
- `k = 2^(coinCombo/12)` — i.e. each successive rapid coin climbs by 1 semitone, up to 7
  semitones (just under a fifth) above the base pitch, then the ratio stops increasing
  (clamped) until the combo breaks (>700 ms gap) and resets.
- Two square tones: `{freq: 1568*k, dur: 0.06, vol: 0.05}` immediately, `{freq: 2093*k,
  dur: 0.12, vol: 0.05, delay: 0.05}` (1568 Hz ≈ G6, 2093 Hz ≈ C7 at `k=1`).
- **Porting note (timing source)**: `performance.now()` → native monotonic clock
  (`System.nanoTime()`/`SystemClock.elapsedRealtime()` on Android). Must be a monotonic,
  not wall-clock, timer to avoid combo glitches across clock adjustments.
- Golden fixture: `audio-sfx-sequences.json` → `coin.byCombo[0..7]` (exact `k`, both
  frequencies, for every combo value 0 through the 7 clamp).

### 10.5 `powerup()` (`audio.js:363-367`)
- Fixed 7-note ascending square arpeggio, MIDI `[60, 64, 67, 72, 76, 79, 84]` (C4 major
  triad, octave, then major triad again up to C6), each `dur 0.1, vol 0.06`, staggered
  `delay = i * 0.045` s (so total span ≈ `6*0.045 + 0.1 = 0.37` s).

### 10.6 `powerdown()` (`audio.js:368-370`)
- Fixed 4-note descending triangle arpeggio, MIDI `[79, 74, 67, 62]` (G5, D5, G4, D4 — a
  falling G-D-G-D shape), each `dur 0.1, vol 0.12`, staggered `delay = i * 0.06` s.

### 10.7 `near(chain = 0)` (`audio.js:371-375`)
- "Close call: bright upward chirp, pitched up for chains of close calls" (`audio.js:371`).
- `base = 76 + min(chain, 6) * 2` — chain clamped to `[0,6]`, each step raises the base
  pitch by a whole tone (2 semitones); max base at `chain>=6` is `76+12=88`.
- 4 notes at chord-tone offsets `[0, 4, 7, 12]` from `base` (a major triad + octave, same
  shape as a `powerup`-style flourish but only 4 notes), each `{dur: 0.07, type: 'square',
  vol: 0.05}`, staggered `delay = i * 0.035` s.
- Golden fixture: `audio-sfx-sequences.json` → `near.byChain[0..8]` (includes a couple of
  values beyond the clamp point to demonstrate the clamping explicitly).

### 10.8 `zone()` (`audio.js:376-380`)
- "New zone: rising sweep plus a sparkly major arpeggio" (`audio.js:376`).
- Sweep: `tone({freq: 300, to: 900, dur: 0.35, type: 'triangle', vol: 0.12})` (3x frequency
  rise over 350 ms).
- Then a 5-note ascending square arpeggio, MIDI `[72, 76, 79, 84, 88]` (C5 major triad +
  octave + major third, i.e. up to E6), each `{dur: 0.14, vol: 0.05}`, starting at `delay =
  0.2` s and staggered further by `i * 0.07` s (so notes start at `0.2, 0.27, 0.34, 0.41,
  0.48` s) — timed to land after the sweep has mostly finished.

### 10.9 `bounce()` (`audio.js:381`)
- Single tone: `{freq: 200, to: 500, dur: 0.15, type: 'triangle', vol: 0.2}` — a short
  upward "boing".

### 10.10 `hit()` (`audio.js:382-387`)
- `tone({freq: 220, to: 60, dur: 0.35, type: 'sawtooth', vol: 0.18})` immediately — a
  falling buzzy tone.
- `tone({freq: 120, to: 40, dur: 0.5, type: 'square', vol: 0.1, delay: 0.05})` — a second,
  lower, longer falling tone starting 50 ms later, layering a thicker impact.
- Plus, if `ensure()` succeeds, `noiseHit({at: now, dur: 0.25, vol: 0.3, cutoff: 400})` — a
  low, loud noise thump. Together these three form the crash/game-over sound, called from
  `main.js:1402` alongside `music.duck()` (§8.7).

Golden fixture for all of §10.1–10.10's fixed numeric data: `audio-sfx-sequences.json`
(also includes the full `midiTable` reference and documents `flap`'s random range as a
formula rather than a fixed value, since it is unseeded).

## 11. Porting notes

### 11.1 Web Audio API → native DSP mapping

This module uses **no Three.js** at all (it's pure Web Audio), so the "how do I reproduce a
Three.js feature" question from other spec files doesn't apply here — instead, every Web
Audio node type used needs a native DSP equivalent:

| Web Audio feature | Used for | Android native equivalent |
|---|---|---|
| `AudioContext` / `OfflineAudioContext` | Live vs. offline graph (§4, §8.9) | A single `AudioTrack` (or `AAudio`/Oboe if lower latency is needed) fed by a custom mixer thread rendering all active voices into an interleaved PCM buffer per callback; "offline" rendering is just running that same mixer loop into an in-memory buffer instead of the device, no special API needed |
| `OscillatorNode` (`square`/`triangle`/`sine`/`sawtooth`) | All tonal voices (§6, §8, §10) | Generate each waveform's PCM samples directly per-voice each callback (a simple band-limited or even naive oscillator is fine at typical mobile sample rates for these frequency ranges — this is chiptune-style audio, some aliasing on `square`/`sawtooth` is stylistically appropriate and arguably matches the original's un-bandlimited WebAudio oscillators, which are *not* anti-aliased either) |
| `GainNode` + `exponentialRampToValueAtTime` / `setTargetAtTime` | Envelopes (§6, §7), bus mixing (§4), ducking (§8.7) | Per-sample gain multiplication; exponential ramps and `setTargetAtTime`'s specific exponential-approach formula (§8.7) are simple closed-form per-sample computations — implement both formulas directly rather than reaching for a generic "ramp" primitive that might use a different curve |
| `BiquadFilterNode` (`lowpass`, `highpass`) | Music-bus tone shaping (§4), noise-hit tonal coloring (§7) | Standard one-pole/two-pole biquad filter implementation (e.g. RBJ cookbook formulas) with the same `type`/`frequency`/`Q` semantics |
| `DynamicsCompressorNode` | Final bus glue (§4) | A standard feed-forward dynamics compressor (threshold/knee/ratio/attack/release) — the exact curve doesn't need to be bit-identical to Chrome's implementation, just perceptually equivalent gentle bus glue |
| `ConvolverNode` + generated impulse response | Room reverb send (§4) | A short (1.2 s) convolution reverb (direct convolution is fine at this IR length, or a partitioned-convolution/FFT approach if CPU-bound); generate the same decaying-noise impulse response formula |
| `AudioBufferSourceNode` (looping through a pre-generated white-noise buffer, random start offset) | All noise hits (§7), drum snare/hat (§8.6) | Pre-generate one white-noise PCM buffer once at startup (same 1 s length), and on each hit start playback at a random sample offset within the first half of the buffer, same as `Math.random()*0.5` seconds |
| `setInterval`-based look-ahead scheduler | Music transport (§8.8) | Any steady, low-jitter timer/thread on the audio pipeline (or drive scheduling from the audio callback itself for sample-accurate timing, which is strictly better than the JS original and does not break golden-fixture parity since the fixtures only encode *musical* time, not wall-clock scheduling behavior) |
| `performance.now()` | Coin-combo timing (§10.4) | A monotonic millisecond clock |
| `localStorage` | Mute persistence (§2) | `SharedPreferences` (per the architecture doc's storage interface), key `birdy-muted`; note the JS stores `'1'`/`'0'` strings rather than a boolean — a Kotlin port can just use a native boolean preference, no need to preserve the string encoding, since nothing else reads this key directly (verify against the migration spec/tool, §11.2) |
| Browser "requires a user gesture" autoplay restriction | §3 | Not applicable on Android; the audio engine can initialize eagerly. If exact behavioral parity with "nothing plays before first tap" is desired for feel/product reasons, gate it explicitly on the same first-tap event the game already has for other purposes, rather than reproducing a gesture *detection* mechanism (there is none needed) |

### 11.2 Migration note

`birdy-muted` is one of the five documented localStorage keys a Capacitor-era install may
have (`birdy-progress…`, `birdy-best`, `birdy-muted`, `birdy-lang`, `birdy-quality` — see
the top-level migration task description). This module is the sole owner/reader/writer of
`birdy-muted`; the one-time WebView-localStorage migration should read this key (string
`'1'`/`'0'`, or absent) and set the native mute preference accordingly (absent → unmuted,
matching `loadMuted()`'s catch-all default).

### 11.3 Randomness summary (nothing here needs seeding)

Every random number drawn anywhere in this file is used for a cosmetic/perceptual
variation the original game itself never reproduces bit-exactly (unseeded `Math.random()`
throughout, same posture as `world.js`'s scenery generators — see `world.md` §8.6). A
Kotlin port needs matching *distributions*, not matching *sequences*:

| Site | Distribution | Line |
|---|---|---|
| Reverb impulse response noise | Uniform `[-1, 1)` per sample, 1.2 s @ context sample rate | `audio.js:37` |
| Shared white-noise buffer content | Uniform `[-1, 1)` per sample, 1 s @ context sample rate | `audio.js:64` |
| `noiseHit` playback start offset | Uniform `[0, 0.5)` seconds into the 1 s noise buffer | `audio.js:113` |
| `sfx.flap` pitch jitter `k` | Uniform `[0.94, 1.06)` | `audio.js:341` |

No other function in this file consults randomness — the entire music sequencer (§8) and
every other `sfx.*` function are 100% deterministic given `(step/beat, theme, mode, hype,
chain/combo)`, which is exactly what `docs/native/golden/audio-song-trace.json` and
`audio-sfx-sequences.json` exhaustively capture.

### 11.4 Porting risks / things to verify against a running build

1. **`setTargetAtTime` exact curve** (`music.duck()`, §8.7): verify the native port's
   exponential-approach implementation against the WebAudio spec's formula (given above)
   with an actual recorded gain-automation trace from a real browser if bit-exact ducking
   feel matters; the formula is simple but easy to get subtly wrong (e.g. using the wrong
   time origin for `τ`).
2. **`OfflineAudioContext` rendering determinism vs. live playback**: `renderMusic` (§8.9)
   assumes `playStep` is 100% deterministic given `(step, t, theme, mode, hype)`, which is
   true by inspection, but it's worth a spot-check that a live `music.start()` session and
   an offline `renderMusic` call with the same `themeIndex`/`calm` actually produce
   identical note timing (should be exactly true, since both call the same `playStep`;
   flagged for a sanity check during the port QA pass rather than because the source
   suggests otherwise).
3. **`schedule()`'s 1-step-per-tick assumption** (§8.1): confirm on real hardware that the
   25 ms/120 ms constants never allow 2+ steps to be silently skipped or double-scheduled
   under load; irrelevant if the Kotlin port uses a fundamentally different (e.g.
   audio-callback-driven) scheduling strategy, as recommended in §11.1, but worth noting if
   anyone is tempted to port the `setInterval` mechanism literally.
4. **Compressor/reverb "feel"**: the exact compressor curve and reverb decay are
   unspecified beyond their parameters (browser DSP implementations of
   `DynamicsCompressorNode` are not standardized bit-exact across engines either) — treat
   §4's numbers as the target parameters for a *perceptually equivalent* native
   implementation, not as implying the original JS itself is bit-exact across browsers,
   and sanity-check by ear against the live JS game rather than chasing numerical parity
   with e.g. Chrome's specific DSP internals.

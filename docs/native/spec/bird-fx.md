# Bird model, animation, skins/trails, particles, and power-up FX

Source files (read in full for this spec):
- `/home/user/birdy-native/src/bird.js` (332 lines) — bird mesh construction, workshop cosmetics, wing animation, glow, skin recolouring.
- `/home/user/birdy-native/src/effects.js` (230 lines) — pooled particle system, speed-line streaks, crash "bonk" impact, power-up aura ring.
- `/home/user/birdy-native/src/skinfx.js` (173 lines) — procedural animated "rare" skins painted over the bird's materials via shader injection.
- `/home/user/birdy-native/src/powerups.js` (128 lines) — power-up catalogue, pickup meshes, pickup idle animation.

Supporting call sites cited from `/home/user/birdy-native/src/main.js` (2129 lines) wherever this spec depends on how the game loop drives these modules (wing phase/speed, squash & stretch, death sequence, power-up activation/expiry, trail emission, pickup collision). Those are the *only* parts of main.js this document draws on; main.js itself is specified elsewhere (`main-a.md`, `main-b.md`).

This is a behaviour spec for a Kotlin/KMP port. It is written to be sufficient **without** reading the JS: every constant, formula, colour, dimension and string used by these four files is listed below, with exact JS source line numbers. Every `Math.random()` call site is flagged — JS has no seedable RNG and the game never seeds one, so bit-exact random *sequences* are not a porting requirement; only the same *distributions, draw order and clamping* are (see "Porting notes" §8). Where logic is pure (no per-frame randomness), golden fixture JSON files under `docs/native/golden/bird-fx-*.json` give exact input→output tables generated by Node scripts in `scripts/native-golden/bird-fx-*.mjs` (kept in the repo; re-run with `node scripts/native-golden/<name>.mjs`).

## 1. `bird.js` — the bird mesh (`createBird()`, lines 5–153)

Returns `{ group, animateWings, setGlow, setSkin, setLook }`. `group` faces **−Z** (the direction of travel is +Z is *backward*; the bird flies toward −Z... actually the comment at line 4 says "Faces −Z", i.e. the bird's front/beak points down the −Z axis, which is the direction gates scroll toward the camera from). All meshes below are children of `group`, so `group.scale`/`.rotation`/`.position` (driven by main.js, §6) transform everything at once.

### 1.1 Materials

Helper `mat(color)` (line 8): `MeshStandardMaterial({ color, roughness: 0.55, flatShading: true })`. A second, non-flat helper `smooth(color)` (line 46) is `MeshStandardMaterial({ color, roughness: 0.45 })` (no `flatShading`) — used only for the tail feathers.

Base palette (all via `mat()` unless noted):

| Name | Hex | Used for |
|---|---|---|
| `yellow` | `0xf7d23e` | body |
| `cream` | `0xfff3c4` | belly |
| `white` | `0xffffff` | eye whites |
| `black` | `0x222222` | pupils |
| `beakMat` | `0xf57c21` | beak top (upper mandible) |
| `beakLowMat` | `0xe0521b` | beak bottom (lower mandible) |
| `wingMat` | `0xfff6d5` | wing (feather) |
| `coverMat` | `0xf6e3a1` | wing covert layer |

These are the *default* ("sunny") skin colours; `setSkin()` (§1.5) overwrites `.color` on the shared material instances at runtime — there is only ever one `MeshStandardMaterial` per slot (`body`, `belly`, `wing`, `cover`, `tail`, `beak`, `beakLow`), reused across all skins (not re-created).

Tail feather rotations: `rotation.set(0.45, rotY, 0)` with `rotY ∈ {0.35, 0, −0.35}` for `x ∈ {−0.12, 0, 0.12}` respectively (i.e. the two side feathers fan outward by ±0.35 rad about Y, all three tilted 0.45 rad about X).

All meshes in `group` get `castShadow = true` at creation (line 100–102), but main.js line 141 immediately sets `castShadow = false` on every child right after `createBird()` — **the bird casts no shadow in the shipped game** (the blob shadow, main.js lines 98–106, stands in for it; see main-b spec). A native port does not need real-time shadow casting for the bird.

### 1.3 Wings (`createWingGeometry()`, lines 44–66, 155–178)

One shared `ExtrudeGeometry` (`wingGeo`) is used for **both** the main wing and the smaller "covert feather" layer on top of it (different scale, not different geometry).

**Outline** (drawn in the local XY plane before extrusion; `x` = span outward from the body, `y` = chord, +y = forward):
```
moveTo(0, 0.26)
bezierCurveTo(0.3, 0.38, 0.7, 0.28, 0.9, 0.04)      // leading edge, root to tip
quadraticCurveTo(0.9, -0.16, 0.72, -0.13)           // scalloped trailing edge, feather 1
quadraticCurveTo(0.66, -0.33, 0.48, -0.24)          // feather 2
quadraticCurveTo(0.39, -0.4, 0.22, -0.28)           // feather 3
quadraticCurveTo(0.08, -0.32, 0, -0.16)             // back to root
lineTo(0, 0.26)                                     // close at the root edge
```
Extrude params: `depth: 0.04, bevelEnabled: true, bevelThickness: 0.035, bevelSize: 0.03, bevelSegments: 2, curveSegments: 5`. After extrusion: `geo.translate(0, 0, -0.02)` (centers the depth on 0), then `geo.rotateX(-PI/2)` (lays it flat: the local "chord" axis becomes world −Z/forward, thickness becomes world Y).

**Wing assembly per side** (`side ∈ {−1, 1}`, lines 51–66):
- `pivot` (a `Group`) at `position = (side·0.48, 0.08, 0.08)` — this is the shoulder joint; `animateWings` rotates `pivot`, not the mesh directly.
- `wing` mesh: `scale.x = side` (mirrors the left wing from the right-side geometry), `rotation.z = side · −0.15` (a slight resting droop), material = `wingMat`.
- `cover` mesh (same `wingGeo`): child of `wing`, `scale = (0.62, 1, 0.7)`, `position = (0, 0.045, −0.04)`, material = `coverMat`. This is the smaller "covert feather" layer that reads as a second, layered plate on top of the main wing.
- `pivot.userData.side = side`; both pivots pushed into the `wings` array returned via closure for `animateWings`.

### 1.4 Workshop parts (`buildParts()`, lines 180–331)

All hidden (`visible = false`) until selected by `setLook()`. Four categories, each a plain object keyed by id → `THREE.Object3D` (`Group` or `Mesh`):

**Shared geometry helpers:**
- `BODY = Vector3(0.6, 0.54, 0.69)` — the body's ellipsoid radii (sphere r=0.6 scaled `(1, 0.9, 1.15)` → `0.6, 0.54, 0.69`). Used to project decals onto the body's surface.
- `decal(geo, material, dir, lift=0.005)` (lines 186–194): given a direction vector `dir`, computes the point `p = normalize(dir) * BODY` (component-wise) on the ellipsoid surface, the surface normal `n = normalize(normalize(dir) / BODY)` there, positions the mesh at `p + n·lift`, and orients it with `quaternion.setFromUnitVectors(UP=(0,1,0), n)` — i.e. **a flat decal is created facing outward along the local surface normal at that point of the ellipsoid**, lifted `0.005` units off the surface to avoid z-fighting.
- `bodyRing(material, z, tube, arc=2π, y=0)` (lines 196–203): a ring around the body at depth `z` (and height offset `y`), sized so it hugs the ellipsoid's cross-section there: `f = sqrt(max(0, 1 − (z/BODY.z)² − (y/BODY.y)²))`; ring built from `TorusGeometry(radius=1, tube, radialSeg=4, tubularSeg=18, arc)`, then `scale.set(BODY.x·f + 0.01, BODY.y·f + 0.01, 1)`, `position.set(0, y, z)`.
- `heartShape(s)` (lines 205–211): a `Shape` heart built from two symmetric bezier lobes, parameterized by scale `s` (`bezierCurveTo` control points at `±1.3s, ±0.6s, 1s, 0.45s, −0.9s` etc. — see source for exact control points; used for the "heart" back-pattern and the "hearts" eyewear lens).
- `EYE` (line 213): fixed array of `{ side, pos, dir }` for both eyes: `pos = (side·0.38, 0.25, −0.38)` (matches §1.2's eye position), `dir = normalize(side·0.7, 0.1, −0.7)` (the outward-facing direction used to place eyewear in front of each eye).
- `overEyes(make, dist=0.2)` (lines 216–225): builds a `Group` with `make(side)` placed at `EYE[i].pos + EYE[i].dir·dist`, oriented via `quaternion.setFromUnitVectors((0,0,1), dir)` — i.e. a "lens" object's local +Z axis is rotated to face outward from the eye.

### 1.5 Skins (`setSkin(skin)`, lines 124–150)

`skinMats = { body: yellow, belly: cream, wing: wingMat, cover: coverMat, tail: tailMat, beak: beakMat, beakLow: beakLowMat }` — the 7 material *instances* created in §1.1/1.2/1.3, kept for the lifetime of the bird and recoloured in place (never replaced). `addSkinFx(material, index)` is called once at creation for `['body','belly','wing','cover','tail']` with `index = 0..4` (§3) — beak materials are **not** eligible for the animated premium-skin shader.

A `skin` object (see `catalog.js SKINS`, 20 entries) has shape:
```
{ id, name:{de,en}, price, body, belly, wing, cover, tail, beak, beakLow: hexInt, metal?: true, fx?: 'lava'|'diamond'|'water'|'galaxy'|'basketball'|'football'|'toadstool' }
```

`setSkin(skin)` does, in order:
1. `patDark.color.setHex(skin.tail)` — pattern "dark" decals always match the skin's tail colour.
2. `patLight.color.setHex(skin.belly === skin.body ? 0xffffff : skin.belly)` — pattern "light" decals match the belly colour, **unless** belly equals body (flat-coloured skins with no belly contrast — none of the current 20 skins hit this branch, but a modder/community skin could), in which case they fall back to pure white so the pattern still reads.
3. `setSkinFx(skin.fx)` — see §3; passing `undefined` for non-rare skins resolves to `FX.none = 0` inside `skinfx.js`.
4. `wc = wingColor(skin)` — see below.
5. For each of the 7 `skinMats` entries: `m.color.setHex(key==='wing'||key==='cover' ? wc[key] : skin[key])`; `m.metalness = (skin.metal && key!=='beak' && key!=='beakLow') ? 0.55 : 0`; `m.roughness = skin.metal ? 0.3 : (key==='tail' ? 0.45 : 0.55)`.
   - Only the `gold` skin (catalog.js) sets `metal: true`. Its body/belly/wing/cover/tail go metallic+shinier (`roughness 0.3`, `metalness 0.55`); its beak/beakLow stay matte (`metalness 0`, and roughness follows the same `0.3` — i.e. metal skins get roughness 0.3 on the beak too, just not metalness). Non-tail, non-metal parts get `roughness 0.55`; tail always gets `roughness 0.45` when not metal.

**`wingColor(skin)` rule** (lines 131–139, golden fixture `bird-fx-wing-color-rule.json`): computes `HSL-lightness` of `skin.wing` (via `THREE.Color.getHSL(hsl, THREE.SRGBColorSpace)`, equivalent to the standard sRGB-hex lightness — see fixture header for the exact formula a port should use). If lightness `< 0.8`, the skin's own `wing`/`cover` colours are used as-is. Otherwise (pale/near-white wings, which would read as invisible "stick" wings against the sky) the wing is repainted as `lerp(skin.body, skin.belly, 0.12)` (12% toward belly, in RGB) and the cover is repainted to `skin.tail`. Per the fixture, **17 of the 20 shipped skins** fall into the "repaint" branch (their `wing` hex has lightness ≥ 0.8); only `robin`, `night`, and skins with dark/saturated wings avoid the repaint — check the fixture's `perSkinResults` for the authoritative per-skin outcome and exact repainted hex values.

### 1.6 `animateWings(phase)` (lines 105–110)

```
a = sin(phase) * 0.8
for each wing pivot w: w.rotation.z = w.userData.side * a     // side = -1 (left) or +1 (right)
hat.cap parts.hat.cap.userData.propeller.rotation.y = phase * 2.2
hat.halo parts.hat.halo.userData.ring.position.y = 0.34 + sin(phase * 0.35) * 0.04
```
`phase` is a monotonically increasing float driven by main.js (§6.2); it is **not** wrapped (fine, since only `sin`/used-as-radians consume it). The propeller and halo lines run unconditionally every call regardless of whether that hat is equipped/visible — cheap, and avoids branching on the current look. Golden fixture: `bird-fx-wing-animate.json` (phase samples + a 60-frame post-flap simulation of the `wingSpeed` relaxation described in §6.2).

### 1.7 `setGlow(color, intensity=0.6)` (lines 112–122)

At bird-creation time, every mesh material in `group` whose `material.userData.ownGlow` is not truthy is added to a `glowMats` Set (this excludes exactly one material: the `halo` hat's emissive ring, §1.4, which manages its own constant emissive independently). `setGlow(null)` sets `emissive = (0,0,0)` on every material in the set (i.e. off); `setGlow(color, intensity)` sets `emissive = color * intensity` (component-wise) on every material in the set — used for the rainbow/invincibility glow (main.js line 1837, §6.5) and cleared on death/power-end (main.js lines 792, 1335, 1405, 1600).

## 2. Integration: how `bird.js` is driven each frame (from `main.js`)

This section exists so the spec is self-contained for porting the *behaviour*, even though the call sites live in main.js.

### 2.1 Scale constants (main.js lines 33–37)
```
BIRD_SCALE = 1.1     // normal visual scale
MINI_SCALE = 0.6     // scale while the "mini" power-up is active
BIRD_RADIUS = 0.5    // collision radius, normal
MINI_RADIUS = 0.3    // collision radius, mini
```
`bird.group.scale.setScalar(BIRD_SCALE)` at creation (line 142); `bird.group.traverse(o => o.castShadow = false)` right after (line 141, overriding §1.2's `castShadow=true`).

### 2.2 Wing phase/speed integration (main.js lines 1056–1080, 1824–1829; golden fixture `bird-fx-wing-animate.json`)
- On flap (`flap()`, called from tap input or auto-flap on `ready→playing` transition): `state.vy = FLAP_VELOCITY (11.5)`; `state.wingSpeed = 38`; `state.squash = 1`; `sfx.flap()` plays.
- Every frame **except** `state.mode === 'over'`:
  ```
  state.wingSpeed = lerp(state.wingSpeed, 12, min(1, dt*4))   // relax toward a 12 rad/s idle flap rate
  state.wingPhase += dt * state.wingSpeed
  bird.animateWings(state.wingPhase)
  tickSkinFx(state.time)                                       // skinfx.js, §3
  ```
  So a flap makes the wings beat at up to 38 rad/s and exponentially decays (63% of the way per `1/4`s, i.e. time-constant 0.25s) back down to a 12 rad/s idle flutter.

### 2.3 Squash & stretch (main.js lines 1832–1835; golden fixture `bird-fx-squash-stretch.json`)
```
state.squash = max(0, state.squash - dt*6)          // decays to 0 in ~1/6 s after being set to 1 on flap
q = sin(state.squash * PI) * 0.5 + state.squash * 0.2
g.scale.set(baseScale*(1-0.14*q), baseScale*(1+0.24*q), baseScale*(1-0.1*q))
```
`baseScale` is `state.baseScale`, itself smoothly interpolated toward `MINI_SCALE` or `BIRD_SCALE` (line 1831: `state.baseScale = lerp(state.baseScale ?? BIRD_SCALE, target, min(1, dt*8))`) — so the mini power-up's shrink/grow is a smooth ease, not a snap, and squash/stretch always multiplies whatever the current base scale is. Net effect: right after a flap the bird briefly stretches tall and thin (`y` up to `+24%`, `x`/`z` down to `−14%`/`−10%`) and springs back over ~0.17s (the `sin(squash·π)` term peaks near `squash≈0.5` then the `+squash·0.2` linear term adds a small extra stretch that is largest at `squash=1`, i.e. the very first frame after a flap — see the fixture's exact frame-by-frame `q` values).

### 2.4 Rotation/pitch/roll (main.js lines 1816–1823) — visual only, not part of bird.js itself, listed here for completeness:
```
pitch = clamp(state.vy * 0.06, -0.9, 0.5)
g.rotation.x = lerp(g.rotation.x, pitch, min(1, dt*10))
roll = (LANES[state.lane] - state.x) * -0.25
g.rotation.z = lerp(g.rotation.z, roll, min(1, dt*10))
```
While not `playing`/`ready` (e.g. dead/over), `g.rotation.x` instead lerps toward a fixed `−1.2` rad nose-dive (rate `dt*5`).

### 2.5 Invincibility glow (main.js line 1836–1837)
```
if mode === 'playing' && power.star > 0:
    bird.setGlow(Color.setHSL((time*1.5) % 1, s=1, l=0.5), intensity=0.7)
```
Cycles hue once every `2/3`s (`1/1.5`), full saturation, 50% lightness, at glow intensity 0.7 — this is the "rainbow star" invincibility look. Cleared (`setGlow(null)`) whenever the star power-up's timer reaches exactly 0 (main.js line 1600, inside `updatePowers`) and at every death/reset (lines 792, 1335, 1405).

### 2.6 Visibility blink during grace period (main.js line 1856)
```
g.visible = !(state.grace > 0 && floor(state.time*12) % 2 === 0)
```
`state.grace` counts down from `GRACE_TIME = 1.2`s after the star power-up ends (set in `updatePowers`, main.js line 1601). While grace is active, the bird blinks at 6 Hz (12 half-cycles/s → toggling every `1/12`s) — a standard "just got hit/invincible-ending" flicker, and the bird remains **immune to death** during this window (see `invincible()`, main.js line 741: `state.power.star>0 || state.grace>0 || state.god`).

### 2.7 Death pose (main.js `die(cause)`, lines 1390–1421)
On death: `bird.setGlow(null)`; the group's *current* scale `sc = bird.group.scale.x` is read and the bird is squashed into an ellipsoid: `bird.group.scale.set(sc*1.3, sc*0.72, sc*1.25)` (wider and flatter — a comic "splat", independent of the §2.3 squash formula, applied once and left in place through the freeze-frame). `HIT_STOP = 0.14`s freeze-frame follows (handled in main-b's update loop, not here). A particle burst and the impact "bonk" star also fire here — §4.3/§5.1.

## 3. `skinfx.js` — animated premium skins

### 3.1 Enum and uniforms (lines 4–20)
```
FX = { none:0, lava:1, diamond:2, water:3, galaxy:4, basketball:5, football:6, toadstool:7 }
```
Module-level shared state (one instance for the whole game, not per-bird — there is only ever one bird visible at a time anyway):
- `uniforms = { uFxTime: {value:0}, uFx: {value:0} }` — shared by every material that has the effect hooked in (`fxMats`, a `Set`).
- `setSkinFx(name)`: `uniforms.uFx.value = FX[name] || 0` (unknown/undefined name → 0/`none`). If this **toggles active vs. inactive** (i.e. crosses the 0 boundary), every material in `fxMats` gets `needsUpdate = true` (forces Three.js to recompile its shader program, since `customProgramCacheKey` — see §3.4 — changed).
- `tickSkinFx(time)`: `uniforms.uFxTime.value = time % 1000` (wraps every 1000s of *game-clock* time, i.e. `state.time`, to keep the float from growing unbounded over a very long session; called every frame in main.js's per-frame bird update, §2.2).

### 3.2 Shader injection mechanism (`addSkinFx(material, part)`, lines 156–172)
For each of the 5 eligible materials (`body=0, belly=1, wing=2, cover=3, tail=4` — the `part` index, only used inside the shader as `uFxPart` to lighten the belly, see `light` in §3.3), `material.onBeforeCompile` is set. **Crucially, the callback early-returns (`if (!active) return;`) while no premium skin is worn** — the normal 13 non-`fx` skins never pay the extra shader-compile cost, matching the source comment at line 7–8. Once active:
- Adds `shader.uniforms.uFxTime/uFx` (shared references to the module uniforms) and a **material-local** `uFxPart` uniform (`{ value: part }`, baked per-material at hook time, not shared).
- Vertex shader: after `#include <common>` adds `varying vec3 vFxPos;`; after `#include <begin_vertex>` adds `vFxPos = position;` — i.e. **the effect samples in the mesh's local object space** (so the pattern sticks to the body/wing shape and does not swim as the bird rotates/moves — this is the reason the source comment calls it "object space").
- Fragment shader: after `#include <common>` injects the whole `FRAG` GLSL block (noise/helper functions, §3.3); after `#include <color_fragment>` injects `vec3 fxGlow = vec3(0.0);` then the whole `APPLY` block (the big `if/else if` effect switch, §3.3), which may overwrite `diffuseColor.rgb` and always sets `fxGlow`; after `#include <emissivemap_fragment>` injects `totalEmissiveRadiance += fxGlow;` — so effects can both recolour the surface and add glow/bloom-feeding emissive light, on top of Three.js's standard PBR lighting pipeline (`MeshStandardMaterial`'s built-in shader chunks are otherwise untouched).
- `material.customProgramCacheKey = () => active ? 'skinfx' : 'plain'` — ensures Three.js does not try to reuse a "plain" compiled program for an "active" material or vice versa (both cache keys are shared by ALL 5 materials × all their instances, so effectively there are only ever 2 distinct compiled program variants live for this whole system, whichever is currently relevant).

### 3.3 Per-effect GLSL logic (`FRAG` helpers lines 22–67, `APPLY` lines 70–153)

Common: `p = vFxPos` (object-space position), `t = uFxTime`, `light = (uFxPart==1.0) ? 0.35 : 0.0` (belly gets a constant 0.35 lightening blend baked into most branches, so the belly reads as a lighter shade of whatever the effect is painting — e.g. lighter lava rock, lighter diamond ice, lighter basketball orange, lighter toadstool red).

Helper functions:
- `fxHash(vec3 p)`: `fract(sin(dot(p, (127.1,311.7,74.7))) * 43758.5453)` — the classic cheap GLSL pseudo-random hash, **deterministic given `p`** (this is why the effect needs no CPU-side RNG state: every frame recomputes from `(position, time)`, so it self-synchronizes across all pixels/instances with zero extra state — a port using a custom GL/Vulkan/Metal shader must reproduce this exact hash bit-for-bit-adjacent, or accept a visually-equivalent but numerically different noise field; exact bit parity is **not required**, matching sprite/skin appearance is what matters).
- `fxCells(p)`: 3×3×3-neighbourhood 3D Voronoi/Worley distance-to-two-nearest-feature-point (`d2 - d1`, i.e. cell-border proximity), feature points jittered per grid cell via `fxHash` with 3 different offsets (17.0, 31.0) to decorrelate the 3 axes — used for lava cracks and (indirectly, via the football/toadstool panel function) nothing else.
- `fxRainbow(h)`: `0.55 + 0.45*cos(2π*(h + (0, 0.33, 0.67)))` — a smooth RGB rainbow parameterized by hue `h∈[0,1]` via 3 phase-shifted cosines (a common cheap alternative to HSL→RGB in shaders).
- `fxRot(a)`: standard 2×2 rotation matrix `[[cos,-sin],[sin,cos]]`.
- `fxBall(q, out d1, out d2, out pent)`: given a unit direction `q`, finds the two closest of 32 candidate points on a **truncated icosahedron** (12 pentagon-face centers scaled by `golden ratio g=1.618` combinations, 20 hexagon/vertex-ish points at `(±1,±1,±1)` normalized, wait — 12 "pentagon" centers + 8 cube-corner points, total handled as 12+8+12=32 — see source lines 49–65 for the exact 3 generator families) and reports whether the closest belongs to the first (pentagon) family. This is a **spherical Voronoi over a fixed 32-point icosahedral/truncated-icosahedron-like point set**, used to fake a football/soccer-ball panel pattern and (reused) a toadstool cap's spot placement.

| `uFx` | Name | Visual summary | Key formulas |
|---|---|---|---|

**Porting takeaway:** a Kotlin/GLSL-ES port should treat §3.3's table as the full spec of 7 self-contained fragment-shader effects, each a pure function of `(objectSpacePosition, time, part)`; none of them read light direction, camera position, or any CPU-computed per-frame value besides `t`. This makes them straightforward to reimplement in GLSL ES 3.0 as a `switch(uFx)` (or 7 separate fragment shader variants selected at draw time) layered on top of whatever lighting model the custom low-poly renderer uses, exactly as done in JS (color/emissive injection after the base lit colour is computed).

## 4. `effects.js` — particles, speed lines, impact, aura

### 4.1 Pooled particle system (`createParticles(scene, max=300)`, lines 3–76)

One `InstancedMesh` of `max=300` unit icosahedra (`IcosahedronGeometry(radius=1, detail=0)` — a 20-triangle low-poly "gem" shape, not a sphere) shares **one** `MeshBasicMaterial({toneMapped:false})` (flat, unlit, full colour — particles do not receive scene lighting) and a **per-instance colour** buffer (`instanceColor`). `mesh.frustumCulled = false` (particles can be positioned anywhere via `emit`, so bounding-box culling based on the mesh's origin would be wrong). Every instance starts scaled to `0` (invisible) via a throwaway `dummy` matrix at init.

Each of the 300 pool slots is `{ life, maxLife, size, gravity, drag, pos: Vec3, vel: Vec3, spin }`; a single `cursor` ring-buffer index (`(cursor+1) % max`) is advanced on every `emit()`-loop iteration — **slots are recycled in strict round-robin order regardless of whether the slot's previous particle has finished its life**, i.e. this is not a "find a dead slot" pool; a burst larger than the remaining pool capacity silently overwrites still-alive particles.

`emit(pos, opts)` — `opts` defaults: `{ count:10, colors:[0xffffff], speed:4, size:0.12, life:0.6, gravity:-6, drag:1.5, spread:1, drift:0 }`. Per particle (golden fixture `bird-fx-particles.json` has the exact draw order and a seeded trace):
```
pos = copy(emit-origin)
dir = normalize(rand()-0.5, rand()-0.5, rand()-0.5)     // uniform in a CUBE, then normalized — NOT a uniform sphere distribution (corners of the cube are over-represented after normalization)
vel = dir * speed * (0.4 + rand()*0.6) * spread
vel.z += drift                                          // constant bias, e.g. "backward" trail drift
life = maxLife = life_param * (0.7 + rand()*0.6)
size = size_param * (0.6 + rand()*0.8)
gravity = gravity_param   (not randomized)
drag = drag_param         (not randomized)
spin = rand() * 6
color = colors[floor(rand() * colors.length)]           // uniform independent pick per particle
```
`emitColor(pos, hex, opts)` is a convenience wrapper: `emit(pos, {...opts, colors:[hex]})`.

`update(dt, dz)` — `dz` is how far the *world* moved this frame (so stationary-relative-to-world particles like the invincibility trail scroll correctly with the scenery):
```
for each live particle (life > 0):
  life -= dt
  vel.y += gravity * dt
  vel *= max(0, 1 - drag*dt)              // uniform scalar damping, all 3 axes
  pos += vel * dt
  pos.z += dz
  k = max(0, life/maxLife)
  renderRotation = (spin*k, spin*1.3*k, 0)
  renderScale = (life > 0) ? size * (0.3 + 0.7*k) : 0    // shrinks toward 30% of its base size as it dies, not to 0
```
`clear()`: sets every slot's `life = 0` then calls `update(0,0)` once (to zero every instance's render scale immediately).

#### 4.1.1 Flight trail cosmetic (main.js lines 1839–1850)
Active whenever `mode==='playing' && !state.hold && power.star<=0` (equipped trail, `progress.trail`) **or** in the shop preview (`mode==='ready' && menu==='shop'`, using `previewTrail`, the currently-hovered trail item). Emission is *accumulator-based*, not once-per-frame:
```
state.trailAcc += dt * 50                 // 50 "ticks" per second, independent of trail's own life/speed
drift = (mode==='playing') ? 0 : 6        // in the shop the world stands still, so a constant backward drift is added so the trail still reads as motion
trailPos = (state.x, state.y - 0.1, 0.45) // fixed offset behind/below the bird's own position
while (trailAcc >= 1):
  trailAcc -= 1
```

### 4.2 Speed lines (`createSpeedLines(scene, count=28)`, lines 80–111)

28 instances of `BoxGeometry(0.11, 0.11, 3.6)` (thin long streaks) in one `InstancedMesh`, sharing `MeshBasicMaterial({color:0xffffff, transparent:true, opacity:0, depthWrite:false, fog:false})`. Placement (`place(l,z)`, called once per line at init with `z = -rand()*60`, and again on recycle with `z = -50 - rand()*15`):
```
side = rand()<0.5 ? -1 : 1
x = side * (4.2 + rand()*5)     // either side of the 3-lane track (lanes span roughly x∈[-3,3])
y = 1 + rand()*11               // above the track, spanning up into where pipe gaps are
```
`update(dz, amount)` (`amount` = "rush", §4.2.1):
```
material.opacity = 0.7 * amount
mesh.visible = amount > 0.01
if not visible: return   // per-line simulation is skipped entirely (frozen) while invisible
for each line:
  pos.z += dz * 1.6              // 1.6x the world's own scroll speed, so streaks visibly outrun the track
  if pos.z > 12: place(line, -50 - rand()*15)   // recycle far ahead with a fresh random x/y

```

#### 4.2.1 "Rush" amount (main.js lines 2067–2069) — driver, listed for completeness:

```
rush = (mode==='playing' && !hold) ? clamp(0,1, (state.speed-22)/14 + (power.star>0 ? 0.6 : 0)) : 0
speedLines.update(mode==='playing' ? state.speed*dt : 0, rush)
```

### 4.3 Crash "bonk" impact (`createImpact(scene, camera)`, lines 113–176; golden fixture `bird-fx-impact.json`)

A single mesh, built once, merging 3 flat 8-pointed star outlines into **one** `BufferGeometry` with a per-vertex `color` attribute (so the whole 3-layer "bonk" is one draw call):

| Layer | Points | Outer r | Inner r | Colour | Z-offset |
|---|---|---|---|---|---|
| outline | 8 | 1.25 | 0.62 | `0x543847` (dark plum) | 0 |
| white | 8 | 1.08 | 0.52 | `0xffffff` | 0.01 |
| core | 8 | 0.62 | 0.34 | `0xffe14a` (yellow) | 0.02 |

`starGeometry(points, outer, inner)` (lines 115–124): a `ShapeGeometry` from a star `Shape` whose `2·points` vertices alternate `outer`/`inner` radius, first point at angle `π/2` (straight up), built via `moveTo`/`lineTo` around the shape (a simple flat star polygon, no bevel/extrusion — unlike the power-up star, §5.1). `mergeSimple(geos)` (lines 179–191) concatenates `position`+`color` attributes from all 3 (non-indexed) geometries into one. Material: `MeshBasicMaterial({vertexColors:true, transparent:true, depthTest:false, depthWrite:false, toneMapped:false, fog:false})`, `renderOrder = 11` (drawn after almost everything, always on top, ignoring depth). Starts `visible=false`.

`hit(pos)`: `t=0`; `bonk.position.copy(pos)`; `visible=true`; `opacity=1`; `scale.setScalar(0.5)`.
`update(dt)`: no-op if not visible; else:
```
t += dt
bonk.quaternion = camera.quaternion                    // billboard to face the camera...
bonk.rotateZ(t * 1.5)                                   // ...then keep spinning around the view axis at 1.5 rad/s
scale = 0.5 + 0.3 * min(1, t/0.12)                      // pops from 0.5x to 0.8x over the first 0.12s, then holds
opacity = 1 - smoothstep(t, 0.25, 0.5)                  // holds fully opaque until t=0.25s, eases out by t=0.5s
if t > 0.5: visible = false
```
`clear()`: `visible = false`.

**Where it fires** (main.js `die(cause)`, line 1413): `impact.hit(state.x + at[0], state.y + at[1], at[2])` where `at = HIT_OFFSET[cause] ?? HIT_OFFSET.blocked`:
```
HIT_OFFSET = {
  'pipe-top':    [0.25,  0.8,  0],
  'pipe-bottom': [0.25, -0.75, 0],
  'plant':       [0.25, -0.75, 0],
  'ground':      [0.25, -0.7,  0],
  'blocked':     [0.8,   0.45,-0.6],
}
```
i.e. the bonk always appears slightly to the bird's own +X side (so it doesn't sit on top of the squashed bird sprite, §2.7) and at a height matching what was hit; `blocked` (a fully-closed lane) additionally offsets in Z since the bird "hits a wall" rather than a specific pipe edge.

### 4.4 Power-up aura ring (`createAura(scene, camera)`, lines 193–229; golden fixture `bird-fx-aura.json`)

One `RingGeometry(innerRadius=0.82, outerRadius=1, thetaSegments=40)` mesh, `MeshBasicMaterial({color:0xffffff, transparent:true, depthWrite:false, toneMapped:false, fog:false, side:DoubleSide})`, `renderOrder=9`, starts `visible=false`.

`update(kind, pos, time, size)` — `kind ∈ {'star','magnet','mini', null}`, `size` = the bird's current `baseScale` (§2.3):
```
ring.visible = !!kind
if !kind: return
ring.position = pos
ring.quaternion = camera.quaternion     // full billboard every frame while any kind is active
switch kind:
  'star':   color = HSL((time*1.5)%1, s=1, l=0.6); opacity=0.75; scale = size*(1.25 + 0.08*sin(time*12))
  'magnet': k=(time*1.6)%1; color=0xff4a4a; opacity=0.7*(1-k); scale = size*(1 + 2.2*k)     // a sawtooth "pulse wave" traveling outward, repeating every 1/1.6≈0.625s (source comment says "every 0.6 s", slightly imprecise)
  else ('mini'): color=0xc58bff; opacity=0.85; scale = size*(1.5 + 0.15*sin(time*8))
```
Driven from main.js (line 1853, precedence `star > magnet > mini`): `auraKind = mode!=='playing' ? null : power.star>0 ? 'star' : power.magnet>0 ? 'magnet' : power.mini>0 ? 'mini' : null`. So if multiple power-ups are simultaneously active, only the highest-precedence aura is shown (star hides magnet/mini's aura, magnet hides mini's), even though all active timers keep counting down and their gameplay effects (speed boost, coin magnetism, small hitbox) all still apply.

### 5.2 Pickup meshes (`createPowerupPickup(scene, type)`, lines 12–116)

Every pickup = `Group(icon, bubble, rim)`, `visible=false` until placed. Two pooled instances exist per type (main.js line 154), so at most 2 of each power-up can be on-screen/pending simultaneously.

**`icon`** (uniform-scaled `×1.7` after building, line 103), one of 3 builders:
- `buildStar()` (lines 29–38): `ExtrudeGeometry` of a **10-point star outline** (`starShape(outer=0.5, inner=0.22)`, first vertex at angle `π/2`, closed path), extrude `{depth:0.14, bevelEnabled:true, bevelThickness:0.06, bevelSize:0.05, bevelSegments:1}`, then `geo.center()`. Material `mat(0xffd400, {emissive:0x664400})` (roughness 0.4, flatShading — via the shared `mat()` helper, line 12–13, distinct from bird.js's own `mat()`). `mesh.userData.rainbow = material` — this is what `animatePickup` cycles (below); only the star pickup has this hue-cycling behaviour.
- `buildMagnet()` (lines 40–56): a red torus arc (`TorusGeometry(0.3, 0.12, radialSeg=6, tubularSeg=12, arc=π)`, opening downward, at `y=0.05`) plus, per side (`±1`), a red cylinder "leg" (`r=0.12,0.12,h=0.22`, at `x=side·0.3, y=-0.06`) and a metal cylinder "tip" (`mat(0xd9d9d9,{metalness:0.6})`, same radii, `h=0.14`, at `y=-0.24`) — a classic horseshoe-magnet silhouette.
- `buildMushroom()` (lines 58–81): purple half-sphere cap (`SphereGeometry(0.42,10,6, 0,2π, 0,π/2)`, `scale.y=0.85`, at `y=0.02`) + 5 white spot spheres (`r=0.09`) placed via `setFromSphericalCoords(radius=0.4, phi, theta)` for the 5 `[theta,phi]` pairs `[0,0.3] [1.3,1.0] [2.8,0.9] [4.4,1.0] [5.6,0.95]`, each then `y = y*0.85 + 0.02` (flattening/repositioning onto the flattened cap) + a cream stem (`CylinderGeometry(top r=0.18, bottom r=0.22, h=0.34)`, `y=-0.15`) + 2 tiny dark "eye" spheres (`r=0.04`, at `x=±0.07, y=-0.12, z=0.2`) — a cute mushroom-with-a-face look.

**`bubble`**: shared `SphereGeometry(1.15, 16, 12)` (`bubbleGeo`, module-level, one instance reused across all pickup groups — fine since it's never mutated, only its material differs per instance), `MeshStandardMaterial({color: POWERUPS[type].color, transparent:true, opacity:0.3, roughness:0.1, depthWrite:false, emissive: POWERUPS[type].color, emissiveIntensity:0.35})`.

**`rim`**: shared geometry (`rimGeo`, module-level, built once, lines 86–97) merging two vertex-coloured `RingGeometry`s: outer white ring (`RingGeometry(1.14,1.32,32)`, vertex colour `0xffffff`) and an edge ring (`RingGeometry(1.32,1.4,32)`, vertex colour `0x543847`), combined via `mergeGeometries` from `three/examples/jsm/utils/BufferGeometryUtils.js`. Shared material `rimMat = MeshBasicMaterial({vertexColors:true, transparent:true, opacity:0.9, depthWrite:false, toneMapped:false})`.

### 5.3 `animatePickup(p, time, camera)` (lines 118–127; golden fixture `bird-fx-powerup-pickup.json`)

### 5.4 Pickup placement / collision / despawn (main.js, integration only)
- `placePickup(x,y,z)` (main.js lines 965–973): picks `type = POWERUP_TYPES[floor(rand()*3)]` uniformly, finds the first *inactive* pooled instance of that exact type (2 per type), and activates it at `(x,y,z)`; returns `false` (no visible effect) if both instances of that type happen to already be active.
- Per-frame (`main.js` lines 1760–1777): position advances by world scroll `dz`; `animatePickup` runs; a **forward shrink** identical in formula to coins (`k = clamp(0,1, 1 - (pos.z-1.5)/1.5); group.scale.setScalar(k); group.visible = k>0`) fades the pickup to nothing just before it would pass through the bird's Z-plane; despawns (`active=false`) once `pos.z > 15` (passed fully behind) if not already collected.
- **Collision radius is 1.4 world units** (main.js line 1772, `p.distanceTo(birdPos) < 1.4`), a value **independent of** the bubble's own visual radius (1.15 core / up to 1.4 including the rim's outer edge — the source comment at powerups.js line 83 explicitly notes this is intentional: "Looks only: the pickup radius (1.4, main.js) stays the same" even if the bubble's rendered size were ever changed). On collision: pickup deactivated/hidden, `activatePower(type)` called (sets `state.power[type] = powerDuration(type)`, fires a 24-particle burst in the powerup's colour, plays `sfx.powerup()`, and for `star` specifically also sets `music.setHype(true)` and resets `state.grace = 0`).

## 6. Cross-cutting state summary (for a Kotlin `BirdFx`/`PowerupFx` component)

A minimal state a port needs to track per running bird, distinct from `progress`/catalogue data:
```
wingPhase: Float          // monotonically increasing, radians
wingSpeed: Float          // rad/s, relaxes toward 12, jumps to 38 on flap
squash: Float             // 0..1, jumps to 1 on flap, decays at 6/s
baseScale: Float          // lerps toward BIRD_SCALE or MINI_SCALE at rate 8/s (critically-damped-ish exponential approach)
skin: SkinDef             // current equipped skin (drives 7 material colours + metal/roughness + fx enum)
look: { pattern, hat, eyes, beak }  // 4 independent single-choice selections
glowColor: Color?         // null or the current invincibility-glow colour
grace: Float              // seconds remaining of post-star blink/invuln window
power: { star, magnet, mini }: Float  // seconds remaining, 0 = inactive; drives aura precedence + trail suppression
trailAcc: Float           // particle-emission accumulator, +50/s while a trail is active
```
Transition triggers already covered above: flap (§2.2/2.3), death (§2.7), power activate (§5.4)/expire (§4.4 precedence + §2.5/2.6 glow/grace), skin/look change (§1.4/1.5, instant, no transition).

## 8. Porting notes

### 8.1 Three.js features used here, and how to reproduce them with a small custom GL engine

| Three.js feature | Used for | Native-engine equivalent |
|---|---|---|
| `SphereGeometry`, `CylinderGeometry`, `ConeGeometry`, `TorusGeometry`, `RingGeometry`, `BoxGeometry`, `IcosahedronGeometry` | almost every mesh in bird.js/powerups.js/effects.js | Precompute equivalent procedural mesh generators once in `commonMain` (a small "primitives" module — sphere/cylinder/cone/torus/ring/box/icosahedron vertex+index buffers, parameterized the same way: radius(es), segment counts, `thetaStart/Length`/`phiStart/Length` for partial spheres like the hats' `SphereGeometry(r,ws,hs,0,2π,0,π/2)` half-domes). These are static, buildable at app start, no runtime cost concern. |
| `ExtrudeGeometry` (wing outline, power-up star, crash-star, heart decal) | wing feather shape, star pickup, bonk star, heart pattern | Either (a) precompute the extruded triangle mesh **offline** (Node/JS at build time, exporting a static vertex/index buffer the Kotlin side loads as a resource — simplest, zero runtime geometry cost, recommended for wing/star/heart since they never change shape), or (b) port a minimal 2D-shape-to-extruded-3D-mesh triangulator (ear-clipping + bevel-ring generation) into `commonMain` if any of these shapes need to be data-driven later. Given these shapes are fixed constants in the JS, (a) is strongly preferred. |
| `ShapeGeometry` (flat, non-extruded star for the bonk) | crash impact "bonk" | Simple 2D polygon triangulate-and-fill (fan triangulation from center works for these star shapes since they're star-convex around the origin) — trivial to do at build time or even at runtime, no ear-clipping needed. |
| `mergeGeometries` (rim ring merge), and the hand-rolled `mergeSimple` (bonk star layers) | one-draw-call multi-part meshes | Simple buffer concatenation (positions/colors/indices with index offset) — reimplement as a small `commonMain` utility; no external dependency needed. |
| `InstancedMesh` + `setMatrixAt`/`setColorAt` | particle pool (300), speed lines (28) | GLES 3.0 instanced rendering (`glDrawElementsInstanced` + a per-instance matrix/colour buffer via `glVertexAttribDivisor`), or — simpler for these small counts and since particles need per-instance *arbitrary* transforms every frame anyway — just re-upload a dynamic VBO of per-instance mat4+color each frame (300 particles × 16 floats is trivial bandwidth). Either approach reproduces the visuals identically; instancing is a performance choice, not a behavioural one. |
| `MeshStandardMaterial` (roughness/metalness/flatShading/emissive) | almost all opaque meshes | The custom engine's GL facade needs one lit shader supporting: a `roughness`/`metalness`-ish simplified PBR-or-Blinn-Phong term (exact PBR fidelity is not load-bearing for this low-poly art style — a simple Lambert+specular with a metalness-driven specular tint/roughness-driven specular power is visually adequate and far cheaper), flat-shading (compute face normals in a geometry preprocessing step rather than interpolating vertex normals — i.e. duplicate vertices per face and assign the face normal, exactly reproducing three.js's `flatShading:true` at the geometry level, no shader trick needed) and a plain `emissive` add term (for `setGlow`, the halo ring, power-up bubbles). |
| `MeshBasicMaterial` (`toneMapped:false`, `vertexColors`, `depthTest`/`depthWrite` false) | particles, speed lines, bonk, aura ring, rim | A second, unlit shader variant: `outColor = vertexColor.rgb * uniformColor.rgb (if any); alpha = opacity`. Respect `depthWrite`/`depthTest` flags per-draw (GL state, trivial) and draw order via an explicit `renderOrder`-equivalent sort (render these overlay elements in a fixed late pass, matching the `renderOrder: 9/11` values noted in §4.3/4.4). |
| `Material.onBeforeCompile` + `customProgramCacheKey` (skinfx.js) | injecting the 7 animated-skin effects into the standard lit shader | Since the custom engine writes its own shaders from scratch anyway (no library shader chunks to patch), simply **always compile the lit shader with an optional `uFx`/`uFxTime`/`uFxPart` branch** (a `switch` over `uFx`, defaulting to a no-op pass-through when `uFx==0`) baked in from the start — the JS's "only compile when active" optimization exists purely to avoid needless shader-permutation cost in three.js's chunk system and has no bearing on the *visual* contract; a from-scratch engine can just always include the switch (7 GLSL branches is cheap) or, if compile-time/GPU cost is a real concern on very low-end devices, keep two shader program variants (`plain` / `withSkinFx`) exactly mirroring the JS's `customProgramCacheKey` split. |
| `Color.setHSL(h,s,l)` / `getHSL(target, colorSpace)` | rainbow glow, star aura, rainbow pickup icon, wingColor's lightness test | Implement standard HSL↔RGB conversion in `commonMain` (formulas given inline in §1.5 and the `bird-fx-wing-color-rule.json`/`bird-fx-aura.json` fixture headers) — these are colorspace-agnostic standard formulas, not three.js-specific. |
| `THREE.MathUtils.smoothstep(x,min,max)` | bonk fade-out opacity | `clamp((x-min)/(max-min),0,1)` then `u*u*(3-2u)` — trivial, given in §4.3/fixture. |
| `Quaternion.setFromUnitVectors(a,b)` | decal orientation, lens/eyewear orientation, billboarding (`copy(camera.quaternion)`) | Standard "shortest-arc rotation between two unit vectors" quaternion construction (well-known formula: cross product for axis, dot product for angle, with the antiparallel-vectors edge case handled via an arbitrary perpendicular axis) — implement once in `commonMain`'s math module; billboarding is just "copy the camera's orientation quaternion onto this node," trivial once quaternions exist. |
| `Vector3.setFromSphericalCoords(radius, phi, theta)` | mushroom pickup's 5 spot positions | `x = radius·sin(phi)·sin(theta); y = radius·cos(phi); z = radius·sin(phi)·cos(theta)` (three.js's convention — verify sign/axis convention matches when porting, since spherical-coordinate axis conventions vary between libraries; three.js's Y-up convention is what's captured here). |
| `object.traverse(fn)` | applying `castShadow=false`, collecting `glowMats` | A `commonMain` scene-graph needs an equivalent depth-first child-walk utility; trivial. |
| `Geometry.center()` (power-up star) | centers the extruded star mesh on its own bounding-box center after bevel | Since this is precomputed offline (see `ExtrudeGeometry` note above), just author the offline export step to translate the mesh so its bounding box is centered — a one-line adjustment in the export script, not a runtime concern. |

### 8.2 Web/JS APIs used here, and native equivalents

| Web/JS API | Used for | Native (Android/Kotlin, and iOS-ready) equivalent |
|---|---|---|
| `Math.random()` | particle emit jitter (velocity/life/size/spin/colour), speed-line placement, power-up type pick (`placePickup`, main.js — not in scope of these 4 files but a dependency) | A platform-injected seedable RNG behind a small `commonMain` interface (e.g. `expect fun interface RandomSource { fun next(): Float }`, `actual` on Android via `kotlin.random.Random` or a shared `mulberry32`-style PRNG kept in `commonMain` for cross-platform determinism if ever desired for replays/tests). Exact JS-`Math.random()` sequence parity is **not** required (browsers give no seed anyway); only matching draw order/count and the same distributions (§4.1's "uniform in a cube then normalized", not a true uniform sphere) matters for visual parity. The `lib-prng.mjs`/golden fixtures in this repo exist only to freeze the **algorithm**, not to be bit-matched by the Kotlin RNG. |
| `requestAnimationFrame` / implicit per-frame `dt` | driving `animateWings`, `tickSkinFx`, particle `update`, aura/impact `update` | Android: a `Choreographer` frame callback or the GL render loop's own frame timing feeding a `dt` (seconds, clamp large `dt` spikes e.g. after a stall, matching how the JS loop likely already clamps `dt` elsewhere in main.js — see main-b spec). |
| `navigator.vibrate(ms)` | (death `buzz(70)`, not in these 4 files but called from the death sequence this spec documents in §2.7) | Android `Vibrator`/`VibratorManager` (`vibrate(VibrationEffect.createOneShot(ms, DEFAULT_AMPLITUDE))`), behind the `Haptics` platform interface named in the task's architecture. iOS equivalent: `UIImpactFeedbackGenerator`. |
| `performance.now()` / `Date.now()` (implicit via `state.time`) | all the `time`-parameterized formulas throughout (§2.5, §3, §4.4, §5.3) | A monotonic clock behind the `Clock` platform interface; must be a `Float`/`Double` **seconds-since-run-start** (or since-app-start, consistently) value, matching how `state.time` accumulates in main.js (main-b spec) — these bird-fx formulas only care that `time` increases smoothly in seconds, not its epoch. |
| Three.js `WebGLRenderer` used for **offscreen shop-tile thumbnails** (main.js lines 322–354, `thumbUrl()`) | rendering a 112×112 PNG-ish canvas snapshot of the bird wearing a candidate pattern/hat/eyes/beak, for the shop grid | Not part of bird.js/effects.js/skinfx.js/powerups.js proper, but directly depends on `createBird()`/`setSkin()`/`setLook()`/`animateWings(1.2)` (a fixed "mid-flap" pose for thumbnails) and 4 fixed camera rigs (`THUMB_VIEW`, main.js lines 324–329: per-kind `cam:[x,y,z], look:[x,y,z], fov`). On Android, reproduce with a second, smaller offscreen `GLSurfaceView`/FBO render of the same bird rig at those 4 camera presets (or, cheaper, pre-bake the shop-tile thumbnails once as bitmaps at build/first-run time and cache them, since the inputs — skin × look-kind × item-id — are a small finite catalogue). This is a UI/shop concern, not gameplay-critical FX, but is called out here since it is the only other runtime consumer of `bird.js`'s API surface. |

### 8.3 Known-inert / low-priority-for-port details
- `POWERUPS[type].label` is dead data (§5.1) — safe to drop.
- The `magnet` aura's source comment ("a wave every 0.6 s") is slightly imprecise; the actual period is `1/1.6 = 0.625s` — port to the formula, not the comment.
- The halo hat's ring material (`ownGlow: true`) is the **only** bird material excluded from `setGlow()`'s group-wide emissive control — a port must replicate this exclusion (tag it, or otherwise route it outside whatever generic "apply emissive tint to every material" helper the Kotlin renderer uses), or the halo will incorrectly flash/tint during the rainbow invincibility glow.

# world: scene, lighting, fog, ground, scenery, clouds, pipes/gates, coins, biome blending

Source of truth: `src/world.js` (1086 lines) and `src/biomes.js` (124 lines), current files, all line numbers
1-indexed and cited as `world.js:N` / `biomes.js:N`. Consumers of these modules referenced for context (not
specced here — see their own spec files): `src/main.js` (`gateSpec()`/`spawnGate()`/`moveWorld()`/game loop),
`src/catalog.js` (`WORLDS`, `PIPES` catalogs), `src/bird.js`/`src/effects.js`/`src/skinfx.js` (bird + particles,
not covered here).

Golden fixtures for the pure/formulaic pieces: `docs/native/golden/world-*.json`, generated by
`scripts/native-golden/world-*.mjs` (kept in the repo; re-run with `node scripts/native-golden/<file>.mjs`).
Everything else in these two files is procedural-geometry construction driven by `Math.random()` (unseeded —
see §8.6) and is specified structurally (shapes, formulas, ranges) rather than as fixed golden numbers, because
the JS itself never produces the same mesh twice.

## 2. Scene setup — `createScene()` (`world.js:14-67`)

Creates a `THREE.Scene`, sets:
- `scene.background = Color(SKY_HORIZON)` — flat color, no gradient (the gradient is the sky dome mesh, drawn on top; the background color only matters where the dome doesn't cover, which in practice is never, but it is also the color the camera clears to before the dome renders and it is one of the biome-blended targets, see §9).
- `scene.fog = Fog(SKY_HORIZON, near=70, far=180)` — linear fog, color = horizon color, starts at 70 units, fully opaque at 180 units. This is a `THREE.Fog` (linear), not `FogExp2`.

### Sky dome
- `SphereGeometry(radius=300, widthSegments=24, heightSegments=12)`.
- `ShaderMaterial`, `side: BackSide` (rendered from inside), `depthWrite: false`, `fog: false` (not affected by scene fog), `renderOrder = -1` (drawn first).
- Uniforms: `top` (Color, zenith), `horizon` (Color).
- Vertex shader: passes `vDir = normalize(position)` (object-space direction from sphere center, since the dome is centered on the origin/camera-ish).
- Fragment shader:
  ```glsl
  float h = clamp(vDir.y * 1.8, 0.0, 1.0);
  gl_FragColor = vec4(mix(horizon, top, pow(h, 0.7)), 1.0);
  #include <colorspace_fragment>
  ```
  i.e. blend factor = `clamp(dirY * 1.8, 0, 1)` then raised to power `0.7` (an ease that pushes more of the view toward "horizon" before quickly transitioning near the zenith), lerp from `horizon` to `top`. `#include <colorspace_fragment>` is three.js's boilerplate that converts the linear working-space color to the renderer's output color space (sRGB) — a native GL port must gamma-encode the final fragment color exactly once, the same as every other lit material in the scene, so this dome matches.
- **This exact gradient function is reused twice more**: once by `addSkyHaze()` for the pipe-fade-to-sky effect (§7.3), and implicitly by nothing else — but any native reimplementation should factor it into one shared function of `(dirY) -> Color` fed by `top`/`horizon` uniforms, matching what `biomes.js` blends (§9).

### Lights
- `HemisphereLight(skyColor=0xdff6ff, groundColor=0x6a8f3a, intensity=1.4)`.
- `DirectionalLight(color=0xfff4d6, intensity=2.2)`:
  - `position = (12, 30, 10)`, `target.position = (0, 0, -15)` (light points down and slightly forward, i.e. toward -Z where the track scrolls to).
  - `castShadow = true`, `shadow.mapSize = 1024×1024`.
  - Shadow camera (orthographic): `left=-18, right=18, top=40, bottom=-30, near=1, far=90`.
  - `shadow.bias = -0.0005`.
  - Both `sun` and `sun.target` are added to the scene (required by three.js for the target to take effect).

`scene.userData.env = { sky: sky.material.uniforms, hemi, sun }` — the handle `biomes.js` uses to blend sky/hemi/sun colors and intensities, and that `addSkyHaze` (pipes) reads `sky.top`/`sky.horizon` from.

**Porting note (lighting model):** three.js's `MeshStandardMaterial` is a physically-based (metallic-roughness) BRDF; a small custom GL engine porting this exactly needs at minimum a Lambertian diffuse term from the hemisphere light (sky/ground lerp by the surface normal's up-dot) + a directional light with a shadow map, matching intensities and colors 1:1 — the game deliberately uses only two lights so this is tractable. Where materials use `MeshBasicMaterial` (see pipes/cactus/coin below) there is **no lighting at all** — those meshes are unlit flat-colored, so a native engine's "unlit" shader path must exist alongside the lit one; they are only later given vertex-colors and re-rendered as lit `MeshStandardMaterial` after baking (see `bakeGroup`, §3.1) or, for `pipeBodyGeo`/`capBelowGeo`/`capAboveGeo`/cactus/coin, the *bake* step itself is what makes them lit (the `MeshBasicMaterial` colors during construction only exist to be captured into vertex colors; the final displayed material is always `MeshStandardMaterial{ vertexColors: true, flatShading: true }`).

## 3. `bakeGroup(root, spikes = false)` (`world.js:185-218`)

The central optimization used by scenery, clouds, pipes, coins and the cactus: flattens a `THREE.Group` tree of meshes (each with its own solid-color `MeshBasicMaterial` or `MeshStandardMaterial`) into **one non-indexed `BufferGeometry`** with a per-vertex `color` attribute baked in, so the whole group renders in one draw call with one shared material (`vertexColors: true`).

Algorithm:
1. `root.updateMatrixWorld(true)`; `inv = root.matrixWorld.inverse()`.
2. For every descendant mesh `o`:
   - Get geometry as **non-indexed** (`toNonIndexed()` if indexed, else `clone()`).
   - If `spikes`: stash the un-transformed local positions in `g.userData.local` (needed later to find the tip vertices in local space, since after step 3 positions become root-relative).
   - Transform: `g.applyMatrix4(inv * o.matrixWorld)` — bakes each mesh's full world transform (relative to `root`) directly into its vertex positions, so the merged geometry needs no further transform hierarchy.
   - Read `o.material.color` (a single `THREE.Color`) and write it to every vertex of `g` as a new `color` `BufferAttribute` (3 floats/vertex, all vertices the same flat color — this is what makes `flatShading` + solid material colors survive baking as "vertex colors").
   - If `spikes`: build a `spike` attribute (3 floats/vertex). If the source mesh has `userData.spikeDir` set, every vertex whose **local** Y is `> 0.01` (i.e. the tip of a cone whose base sits at local Y=0, apex up) gets `spikeDir` written into its `spike` attribute; all other vertices get `(0,0,0)`. This lets a per-vertex shader later push only the tips outward (see cactus bristle, §8.5).
   - Delete every attribute except `position`, `normal`, `color`, `spike` (drops UVs etc. — irrelevant once vertex-colored and unlit-baked).
3. `mergeGeometries(geos)` (from `three/examples/jsm/utils/BufferGeometryUtils.js`) concatenates all the per-mesh buffers into one, then every source geometry is disposed.

**Porting notes:**
- This whole step is a **CPU-side, one-time mesh-merge/flattening pass**, not a three.js-specific feature — any engine can implement it as "for each source mesh, transform its verts into the target space, tag each vertex with a flat color (and optional custom attribute), concatenate the vertex/index buffers". A Kotlin/OpenGL port should do exactly this on the CPU at scene-build time (or app startup for the pipe/cactus/coin geometries, which are shared/module-level and built once) and end up with plain `FloatBuffer`s for position/normal/color(/spike), uploaded once to a VBO.
- Non-indexed geometry means 3 unique vertices per triangle (no shared-vertex smoothing) — this preserves flat shading (each triangle's face normal is genuinely per-triangle) without needing a `flatShading` material flag once baked; `flatShading: true` is still set on the resulting material because `computeVertexNormals`/import may leave smooth normals depending on source geometry — treat `flatShading` as authoritative for how normals should be computed (per-face, not interpolated) regardless of the attribute layout your engine ends up using.
- `spike` requires custom per-vertex attribute support in your vertex shader (a plain "extra float3 attribute" — trivial in raw GLES).

## 4. Ground — `createGround(scene)` (`world.js:69-178`)

Two flat planes, both textured via **2D canvas-drawn procedural textures**, both scrolling by offsetting the texture's V (T) coordinate as the world moves (no actual geometry moves).

### 4.1 Track texture (`drawGround`, `world.js:73-102`, canvas 512×128 px)
Drawn into a `512×128` 2D canvas (`makeGroundTexture`, `world.js:103-114`), re-drawn whenever the road palette changes (`setRoad`).
- `clearRect(0,0,512,128)` — grass-side area is left **transparent** (alpha 0); the grass plane underneath shows through via `alphaTest: 0.5` on the track material (so the track mesh's grass-colored area doesn't occlude/z-fight the real grass plane, it's simply invisible there and the grass plane, positioned 0.02 below, shows).
- Track ("sand") band: `x ∈ [150, 362]` (212 px wide, ~41% of the 512 px width), fill color = `road` (index 0 of the palette).
- Diagonal stripes: `strokeStyle = stripe (palette[1])`, `lineWidth = 14`; for `i` from `-128` to `256` step `32`, draw a line from `(x0, i)` to `(x1, i+128)` — i.e. parallel diagonals at 45° (Δx=212, Δy=128 → not exactly 45°, slope ≈ 0.604), spaced 32 px apart vertically, giving diagonal "candy-cane" road markings that appear to slide as the texture's V offset scrolls (`ground.update`, §4.3).
- Lane dividers: 2 dashed vertical strips at `x = 226.5` and `285.5` (each `5px` wide, `x-2.5 .. x+2.5`), `y ∈ [8, 56]` (`fillRect(x-2.5, 8, 5, 48)`), color `rgba(255,252,235,0.75)`. Comment states these correspond to the lane boundaries at world X = ±1.5 (halfway between lanes -3/0 and 0/3), positioned ~29.5 px either side of the track's horizontal center (256) given the texture spans 26 world units (see `createGround`'s `width=26`) mapped across the 512 px canvas width... **note the asymmetry**: the track band itself (150–362) is centered at 256, and 226.5/285.5 are ±29.5 from 256 — consistent with the comment. Only 2 dividers are drawn (not repeated along the strip's 48px height) — this one placement repeats vertically for free because the whole texture tiles via `tex.wrapT = RepeatWrapping`.
- Track borders: two solid `10px`-wide bars at the track edges in `edge` (palette[2]): `fillRect(x0-10, 0, 10, 128)` and `fillRect(x1, 0, 10, 128)`. Then a **fixed** (palette-independent) `4px` dark trim `#543847` just outside each border: `fillRect(x0-14, 0, 4, 128)` and `fillRect(x1+10, 0, 4, 128)`.
- `css(hex)` helper: `#${hex.toString(16).padStart(6,'0')}` — plain hex-to-CSS-color-string.

Texture setup (`makeGroundTexture`): `THREE.CanvasTexture`, `colorSpace = SRGBColorSpace`, `wrapS = ClampToEdgeWrapping` (no horizontal tiling — the 512px canvas *is* the full width), `wrapT = RepeatWrapping` (tiles vertically/along Z), `anisotropy = 8`.

### 4.2 Grass texture (`makeGrassTexture`, `world.js:118-133`, canvas 4×128 px)
A tiny `4×128` canvas: fill white, then 4 grey (`#e0e6d8`) horizontal bands of height 16 at `y = 0, 32, 64, 96` (i.e. a `32px`-period stripe pattern, half grey/half white). This is a **greyscale mask**: the actual displayed grass color comes from tinting via `MeshStandardMaterial.color = 0x73bf2e` multiplying the texture — so re-tinting the material color (done per-biome, §9) recolors the whole striped pattern, reproducing the comment's stated original stripe pair `#73bf2e` (white band × green tint ≈ unchanged) / `#65ad26`-ish (grey band `0xe0e6d8` × green tint, darker). `wrapS`/`wrapT` both `RepeatWrapping`, `anisotropy = 8`, `colorSpace = SRGBColorSpace`.

### 4.3 Meshes and scroll
- **Track**: `PlaneGeometry(width=26, length=400)`, rotated `-90°` about X (lying flat), `position.z = -length/2 + 30 = -170`, `receiveShadow = true`. Material: `MeshStandardMaterial{ map: trackTex, roughness: 1, alphaTest: 0.5 }` (no explicit base `color`, so it's pure white ×texture; `alphaTest` discards the transparent grass-side pixels rather than blending them). `tex.repeat.set(1, length/GROUND_TILE) = (1, 40)` — the 512×128 texture (which is one `GROUND_TILE=10`-unit tile tall) repeats 40× along the 400-unit-long plane.
- **Grass**: `PlaneGeometry(600, 600)`, rotated flat, `position.y = -0.02` (very slightly below the track, so it never z-fights and reads as "underneath"), `receiveShadow = true`. Material: `MeshStandardMaterial{ map: grassTex, color: 0x73bf2e, roughness: 1 }`. `grassTex.repeat.set(1, 600/10) = (1, 60)`.
- **Scroll**: `update(distance)`: `tex.offset.y = (distance / GROUND_TILE) % 1`; `grassTex.offset.y` is set to the same value — both textures scroll in lockstep by total distance traveled (`state.distance`, accumulated every frame in `main.js:moveWorld`), wrapping every `GROUND_TILE=10` world units. Neither plane's geometry ever moves; this is the entire "infinite ground" illusion.
- **`setRoad(palette)`**: compares `palette.join()` against the last-applied key; no-ops if unchanged (avoids redundant canvas redraws every blend tick). Otherwise redraws the 512×128 canvas in place with the new `[road, stripe, edge]` triple and sets `tex.needsUpdate = true`. Called every blend frame during a biome transition by `biomes.js` (`paintRoad`, §9.2) but only actually repaints ~9 times per transition because the caller pre-quantizes the palette to 1/8 steps.

**Porting notes:**
- The canvas-drawn textures are **static raster images per palette**; a Kotlin/Android port doesn't need a live 2D-canvas-drawing API at runtime — it can either (a) port `drawGround` line-for-line onto an Android `Canvas`/`Bitmap` (straightforward, `Canvas.drawRect`/`drawLine` map directly), which is the most faithful and keeps the exact same repaint-on-palette-change behavior, or (b) precompute/cache a small fixed set of textures if the palette set is closed (it isn't — worlds can add arbitrary custom `road` palettes via `catalog.js`, so (a) is the correct approach). The grass texture (4×128, purely a repeating band mask) is trivial to instead express as a tiny **procedural shader** (a `sin`/`step` on world-space Z scaled by `GROUND_TILE`) if that's simpler in the target renderer than raster textures — visually identical since it's just two flat colors.
- `alphaTest` (discard-based alpha cutout, no blending) is a common GLES feature (`discard` in the fragment shader when `alpha < 0.5`) — straightforward 1:1 port.
- Texture `offset.y` scrolling is a simple UV-offset uniform; trivial.
- `wrapT: RepeatWrapping` with a `ClampToEdgeWrapping` on the other axis is directly expressible with `GL_REPEAT`/`GL_CLAMP_TO_EDGE` per-axis in GLES (note: true per-axis wrap modes need `glTexParameteri` with `GL_TEXTURE_WRAP_S`/`_T` independently, which GLES supports).

## 5. Scenery — `createScenery(scene)` (`world.js:220-516`)

Low-poly themed decoration along both sides of the track, built from shared primitive geometries (`G`, `world.js:234-245`) and per-theme generator functions, baked per-chunk (§3) so each chunk of scenery costs one draw call regardless of how many individual bushes/trees/rocks it contains.

### 5.1 Shared primitive geometries `G` (`world.js:234-245`)
| Key | Geometry | Params |
|---|---|---|
| `trunk` | `CylinderGeometry` | radiusTop 0.3, radiusBottom 0.4, height 2, radialSegments 6 |
| `leaf` | `IcosahedronGeometry` | radius 1.8, detail 0 |
| `box` | `BoxGeometry` | 1×1×1 |
| `bush` | `IcosahedronGeometry` | radius 0.8, detail 0 |
| `rock` | `DodecahedronGeometry` | radius 0.9, detail 0 |
| `cactus` | `CylinderGeometry` | radiusTop 0.35, radiusBottom 0.4, height 1, radialSegments 7 |
| `cone` | `ConeGeometry` | radius 1, height 1, radialSegments 4 |
| `pine` | `ConeGeometry` | radius 1.5, height 3.2, radialSegments 7 |
| `hill` | `IcosahedronGeometry` | radius 1, detail 1 |
| `flower` | `IcosahedronGeometry` | radius 0.22, detail 0 |

`mesh(geo, color, x=0, y=0, z=0, sx=1, sy=sx, sz=sx)` (`world.js:247-252`): convenience constructor — position + **non-uniform scale** (defaults to uniform `sx` if `sy`/`sz` omitted) — using a cached `MeshStandardMaterial{ color, flatShading: true }` per unique color (`sceneryMat`, `world.js:227-230`, a `Map<hex,material>`, so identical colors across different scenery items share one material instance — irrelevant post-bake since colors become vertex data, but matters if any of these materials were ever used un-baked, which they are not).

`pick(arr)` = uniform-random array element; `rand(a,b) = a + Math.random()*(b-a)`.

### 5.2 Item generators (all return a `THREE.Group`; exact formulas — port 1:1 for visual parity)

- **`tree(leafColors, trunk=0x8b5a2b)`** (`254-259`): trunk mesh at `(0,1,0)` using `G.trunk` (default brown `0x8b5a2b`) + one leaf `G.leaf` at `(0, 3.2, 0)`, color = random pick from `leafColors`, uniform scale `rand(0.8, 1.4)`.
- **`bush(colors, flowers?)`** (`260-272`): `n = 2 + floor(random()*3)` (2..4) blob instances of `G.bush`; each at `x=(i-n/2)*0.8, y=rand(0.3,0.6), z=random()*0.6`, scale `rand(0.7,1.2)`, random color from `colors`. If `flowers` array given, each blob also gets one `G.flower` at `x+rand(-0.3,0.3), y+0.6*scale, z+rand(-0.2,0.3)`, random color from `flowers`.
- **`building(colors, windowColor, roof?)`** (`273-286`): box body `w=rand(4,8)`, `d=rand(4,8)`, `h = roof ? rand(4,8) : rand(6,20)` (shorter buildings if it has a roof), positioned `(0, h/2, 0)`, random `colors`. Windows: one `G.box` row every `2.5` units from `y=2` to `y<h-1`, each `w*0.8 × 0.8 × d+0.1` in `windowColor` (flush with/poking slightly past the walls in Z so they don't z-fight). If `roof`: a `G.cone` roof scaled `(w*0.78, 2.8, d*0.78)` at `y=h+1.4`, rotated 45° about Y (so a 4-sided cone reads as a pyramid roof aligned to the box), color = `roof`.
- **`cactus()`** (scenery decoration, distinct from the *obstacle* cactus in §8) (`287-300`): main trunk `G.cactus` scaled `(1, h, 1)` with `h=rand(2.2,3.6)`, centered `y=h/2`, green = pick of `[0x4f9d3a, 0x5cae45, 0x3f8a33]`. For each `side ∈ {-1,1}`: 30% chance to skip; else one horizontal "arm stub" (`G.cactus` rotated 90° about Z, scaled `(0.45,0.35,0.45)`) at `x=side*0.55, y=rand(h*0.4,h*0.7)` plus one vertical arm (`G.cactus` scaled `(0.5, ah, 0.5)`, `ah=rand(0.8,1.4)`) at `x=side*0.8, y=arm_y+ah/2`.
- **`mesa()`** (`301-314`): `layers = 2 + floor(random()*3)` (2..4) stacked boxes, each layer `h=rand(2.5,5)`, shrink factor `k = 1 - i*0.12` (each layer 12% narrower/shallower than the base `w=rand(6,11), d=rand(6,10)`), color per layer picked from `[0xd9774a, 0xe8915a, 0xc9653f, 0xf0b27a]`, stacked bottom-up (`y` accumulates by each layer's `h`).
- **`hill(colors)`** (`315-318`): single `G.hill` scaled `(s*1.4, s*0.8, s)` with `s=rand(4,7)`, `y=s*0.25`, color from `colors`.
- **`snowman()`** (`320-327`, winter `near` alt): 3 white `G.hill` "balls" at increasing height/decreasing scale `(y=0.7,s=0.8)/(1.75,0.55)/(2.5,0.38)`; orange `G.cone` nose `(0.1,0.4,0.1)` at `(0,2.5,0.45)` rotated 90° about X; 2 dark `G.flower` eyes at `x=±0.13, y=2.62, z=0.33`; a red `G.cactus` "scarf" flattened to `(1.25,0.22,1.25)` at `y=2.08`.
- **`snowyPine()`** (`328-335`): brown `G.trunk` short stub `(0.7,0.5,0.7)` at `y=0.5`; a `G.pine` (green, pick of `[0x2f6b4a,0x3a7a55]`) scaled by random `s=rand(0.9,1.4)` at `y=2.4s`; a smaller white `G.pine` "snow cap" `(s*0.62, s*0.5, s*0.62)` at `y=3.4s`.
- **`snowPeak()`** (`336-343`, winter `far`): a big grey-blue `G.cone` mountain (`w=rand(7,12), h=rand(9,16)`, color pick `[0x9fb4c8,0xa9bfd6,0x8fa6bd]`) plus a smaller white `G.cone` snowcap `(w*0.42, h*0.4, w*0.42)` at `y=h*0.8`.

### 5.4 Chunk placement — `buildChunkGroup(theme)` (`world.js:458-474`)

For each chunk (chunk-local Z runs `0 .. -SCENERY_CHUNK` i.e. `0..-25`), for **each side** `∈ {-1, +1}`:
- **Near ring**: `z` from `0` to `<25` step `5` (5 items/side): `place(theme.near(), x = side*rand(6.8,7.6), z = -z - random()*2, turn=true)`.
- **Mid ring**: `z` starts at `rand(0,3)`, steps `7` while `<25` (~4 items/side): `place(theme.mid(), x = side*rand(9,13), z = -z - random()*3, turn=true)`.
- **Far ring**: `z` starts at `rand(0,6)`, steps `12` while `<25` (~2-3 items/side): `place(theme.far(), x = side*rand(22,34), z = -z, turn=false)`.

`place(item, x, z, turn)`: sets `item.position.x/z`; if `turn` is true, `item.rotation.y = random()*2π` (plants/rocks face any direction); if false, rotation stays `0` (buildings/mesas stay axis-aligned).

### 5.5 Chunk pool & recycling — `createScenery` (`world.js:476-516`)

- `SCENERY_SPAN/SCENERY_CHUNK = 225/25 = 9` chunk meshes are created up front, each an empty `BufferGeometry` immediately filled by `rebuild(c)` (= `bakeGroup(buildChunkGroup(theme))`, then swap into `c.geometry`, disposing the old one; `c.userData.theme` records which theme it was last built in).
- Initial `theme = 'park'`.
- Chunks are placed at `z = 20 - k*25` for `k = 0..8`, i.e. `z = 20, -5, -30, -55, -80, -105, -130, -155, -180` (spanning the full 225-unit span, with the frontmost chunk starting 20 units *ahead* of the camera/origin).
- **`update(dz)`**: every chunk's `position.z += dz` (world scroll). If a chunk's *back edge* has scrolled fully behind the camera (`c.position.z - SCENERY_CHUNK > 25`, i.e. `position.z > 50`), it's recycled: `position.z -= SCENERY_SPAN (225)` (teleports it to the far end, maintaining the fixed 25-unit spacing of the ring), and if its baked theme no longer matches the current target theme it's rebuilt in the new theme. This is how a theme visually "streams in from the horizon" — only chunks that wrap around get regenerated, existing visible chunks keep their old theme's decoration until they cycle out.
- **`setTheme(name, instant=false)`**: sets the target theme; if `instant`, immediately rebuilds every chunk whose `userData.theme` doesn't match (used for hard cuts, e.g. equipping a different world skin from the shop — see `biomes.js` `set()`, §9.2, called with `blend===0`). Non-instant calls (the normal zone-to-zone transition) just change the target and rely on natural recycling — meaning a **zone transition does not repaint scenery already on screen**; only new chunks streaming in from the far end appear in the new theme. This matches the "the new place starts right where the banner appears" comment in `main.js:987`.

**Porting notes for scenery:**
- All of §5.2/5.3/5.4 is pure procedural mesh generation driven by `Math.random()` — there is **no seeding**, so exact vertex-for-vertex parity with any specific JS run is neither possible nor required; a Kotlin port must reproduce the **distributions and formulas** (uniform ranges, discrete pick weights, counts) so the *statistical* look matches, not literal per-instance output. Where a golden fixture would help (e.g. verifying `rand`/`pick` helper semantics) none is needed — they're one-liners (`a + Math.random()*(b-a)`, `arr[floor(Math.random()*arr.length)]`), directly portable to `Random.nextDouble(a,b)`/array indexing in Kotlin.
- `IcosahedronGeometry(r, 0)` = a regular icosahedron (20 tri faces) of circumradius `r`; `detail 1` = one level of subdivision (80 faces) — three.js's icosahedron subdivision algorithm (recursive midpoint-splitting of a base icosahedron, then re-normalizing to the sphere) must be reproduced exactly if using a custom mesh library, or simply precompute the two icosahedron LODs (detail 0 and 1) as static vertex/index arrays once (they never change) and ship them as fixed data — this is simpler than reimplementing three.js's subdivision and is recommended.
- `DodecahedronGeometry`, `ConeGeometry(radial=4)` (a square pyramid), `ConeGeometry(radial=7)`, `CylinderGeometry` with varying `radialSegments` (6 or 7) are all standard parametric solids — straightforward to generate directly (cylinder: N-gon cap fan + N side quads; cone: N-gon base fan + N side triangles meeting at an apex; dodecahedron: fixed 20-vertex/12-pentagon-face solid, precompute as static data since it's used with fixed radius 0.9 and detail 0 everywhere).
- The "bake to one draw call per chunk" strategy (§3) is even more valuable in a native low-level renderer than in three.js — implement it the same way (build once per chunk into a big vertex buffer, re-upload only on theme change).

## 6. Clouds

### 6.1 Sky clouds — `createClouds(scene)` (`world.js:524-556`)
18 free-floating cloud clusters, each built from 3-5 `IcosahedronGeometry(1,1)` "puffs" (a fresh `THREE.Group`, `n = 3 + floor(random()*3)`), puff `j` positioned `x = j*1.6 - n*0.8` (spreads puffs left-to-right, centered), `y = random()*0.6`, `z = random()*1.2`, scale uniform `1.3 + random()*0.9`. All puffs share one un-baked `MeshStandardMaterial{ color: 0xffffff, roughness: 1, flatShading: true, fog: true }` during construction, then the whole cluster group is baked (§3) into one geometry, rendered with the shared `cloudMat` (module-level, `world.js:522`: `MeshStandardMaterial{ vertexColors: true, roughness: 1, flatShading: true, fog: true, emissive: 0xffffff, emissiveIntensity: 0.22 }` — the emissive self-glow keeps cloud undersides from reading as heavy grey since there's no bounce light in this scene). `cloudMat` is exported implicitly by being the shared handle returned as `.material` and is also the material used for pipe-row cloud banks (§6.2) — **both use the exact same material instance**, so any biome tint applied to one applies to both.

Each cloud cluster mesh: `position = ((random()-0.5)*90, 18+random()*14, -random()*220)`; `userData.speed = 0.3 + random()*0.3` (a per-cloud parallax multiplier).

`update(dz)`: `position.z += dz * speed` (moves slower than the ground/pipes — the parallax); if a cloud drifts past `z > 30` (behind the camera), wrap: `z -= 250`, re-randomize `x = (random()-0.5)*90` (a fresh horizontal position each wrap, unlike ground scenery which keeps its chunk's contents).

### 6.2 Pipe-row cloud banks/collars (`world.js:679-730`)
Every gate row optionally gets a cloud decoration the pipes visually "pass through" at `y = BANK_Y (16)`:
- **Bank** (`makeBankGeometry(seed)`, `685-700`): a wide row of puffs spanning `x = -6.5` to `6.5`, step `1.6 + rnd()*0.5` (so a bank has a variable, seeded-random puff count, roughly 6-8 puffs), each puff `y = BANK_Y + rnd()*0.9`, `z = (rnd()-0.5)*1.6`, scale `(s*1.2, s*0.62, s)` with `s = 1.5 + rnd()*0.9` — flattened icosahedra. 30% of puffs use a shaded gray color (`0xe9eef5`) instead of white.
- **Collar** (`makeCollarGeometry(seed)`, `701-718`): per-lane (`LANES`) rings of exactly 5 puffs each (15 total), angle `a = (k/5)*2π + rnd()`, radius 1.25 around the lane's X, `y = BANK_Y + (rnd()-0.5)*0.5`, scale `(s*1.1, s*0.65, s)` with `s = 0.8+rnd()*0.4`. All white.
- Both use their **own tiny LCG** seeded from an integer `seed` (1, 2 or 3): `h = seed*K + C` then each call does `h = (h*9301 + 49297) % 233280; return h/233280` — bank uses `K=9301, C=49297`; collar uses `K=7919, C=104729`. **This is a different multiplier/increment pair per call-site but the same recurrence shape.** 3 variants of each are precomputed at module load: `cloudGeos = [bank(1), bank(2), bank(3), collar(1), collar(2), collar(3)]` (6 static baked geometries total, indices 0-5).
- **Row pick** — `pickRowCloud()` (`720-726`): a **separate module-level LCG** (`cloudPick`, seeded `12345`, same recurrence `h=(h*9301+49297)%233280`) advanced once per call: `r = cloudPick/233280`; if `r < 1/3` → **no cloud** (`null`); else index into `cloudGeos` via `floor(((r - 1/3) * 1.5) * 6) % 6` — this maps the remaining `[1/3, 1)` range evenly across all 6 variants (bank and collar equally likely, 3 seeds each). Because `cloudPick` is module state advanced on every `configure()` call for every gate (§7.4), **the sequence of cloud choices across a run is deterministic given a fixed number of prior calls since module load** — i.e. it always starts the same way at app start, and is exactly reproducible; see `docs/native/golden/world-cloud-rng.json` for a golden trace of `pickRowCloud()`'s first 60 outputs and each seeded generator's first 8 raw `rnd()` values.
- Bank material (`bankMat`, `world.js:729-730`): `MeshStandardMaterial{ vertexColors: true, roughness: 1, flatShading: true, fog: true, emissive: 0xffffff, emissiveIntensity: 0.32 }`, and its `.color` is explicitly aliased to `cloudMat.color` (`bankMat.color = cloudMat.color`) — **the same `THREE.Color` object is shared by reference**, so tinting one tints both instantly (this is how `biomes.js` only needs to touch `clouds.material.color` once and have it affect sky clouds, banks and collars uniformly).

**Golden fixture:** `docs/native/golden/world-cloud-rng.json` — `pickRowCloud()`'s first 60 index outputs (module seed 12345; `null` = no cloud, `0-2` = bank seed 1/2/3, `3-5` = collar seed 1/2/3) plus the first 8 raw outputs of each seeded per-geometry `rnd()` for seeds 1-3, generated by `scripts/native-golden/world-cloud-rng.mjs`. **Portable 1:1**: this is a linear congruential generator with fixed integer constants and modulo `233280` — implement the identical recurrence in Kotlin with 32/64-bit integer math (watch for overflow: `h*9301` for `h` up to `233279` is ~2.17M, safe in a 32-bit `Int` even after adding the constant, so plain `Int` arithmetic with the same `%` is sufficient) and the golden file lets you verify bit-exact agreement.

**Porting note:** if the native game reproduces gate-row cloud picks (recommended, for visual continuity with the JS reference and because a fixed LCG is trivial to port), the call **order** matters — `pickRowCloud()` must be invoked exactly once per gate `configure()` call, in the same order gates are configured in the JS (row-by-row as they spawn ahead of the player), for the sequence to line up.

## 7. Pipes

### 7.1 Shared geometries (module-level, built once, `world.js:561-566`)
- `pipeGeo`: `CylinderGeometry(PIPE_RADIUS, PIPE_RADIUS, 1, 16)` then `.translate(0, 0.5, 0)` — origin at the **bottom** of a unit-height cylinder, so scaling `scale.y = height` stretches it upward from a fixed base (used for both the lower pipe, which grows from Y=0, and the upper pipe, which grows from its gap edge upward to `PIPE_TOP`).
- `lipGeo`: `CylinderGeometry(PIPE_RADIUS+0.25, PIPE_RADIUS+0.25, 0.8, 16)` — the flared rim/lip disc at a gap edge, radius `1.35`, height `0.8`, origin at its own center (not translated).
- `bandGeo`: `CylinderGeometry(PIPE_RADIUS+0.28, PIPE_RADIUS+0.28, 0.14, 16)` — a thin dark ring just inside the lip.
- `stripeGeo`: `BoxGeometry(0.28, 1, 0.28)` then `.translate(0,0.5,0)` (also bottom-anchored) — a thin vertical highlight/shadow bar running the full height of a pipe segment.

### 7.2 Baked pipe part geometries (`world.js:596-613`)
`bakeParts(parts)`: builds a temp group of `[geo, hex, x?, y?, z?]` tuples (each a `MeshBasicMaterial(hex)`-colored mesh at the given local offset), then bakes it (§3) into one vertex-colored geometry.
- **`pipeBodyGeo`**: `pipeGeo` (color = `style.pipe`) + a light stripe (`stripeGeo`, color `style.light`, at `x=-RADIUS*0.57, z=RADIUS*0.8`) + a dark stripe (`stripeGeo`, color `style.dark`, at `x=RADIUS*0.64, z=RADIUS*0.75`) — two stripes on nearly-opposite sides (one slightly forward-left, one forward-right) suggesting a cylindrical highlight/shadow without real specular lighting variance.
- **`capBelowGeo`** (used on the **bottom** pipe's lip, band sits *below* the lip): `lipGeo` (`style.pipe`) + `bandGeo` (`style.dark`) at `y=-0.4`.
- **`capAboveGeo`** (used on the **top** pipe's lip, band sits *above*): `lipGeo` (`style.pipe`) + `bandGeo` (`style.dark`) at `y=+0.4`.

These 3 geometries are **shared by every pipe segment in the game** (all gates + the shop preview) — recoloring them (via `setPipeStyle`) simultaneously restyles every visible pipe.

### 7.3 Sky haze shader — `addSkyHaze(mat, sky)` (`world.js:574-592`)
Patches a `MeshStandardMaterial` via `onBeforeCompile` (three.js's shader-injection hook) so tall pipe geometry fades into the sky color above `HAZE_START (32)`, fully sky-colored by `HAZE_END (40)`:
- Vertex shader: adds a varying `vHazePos` = world-space position of the vertex (`(modelMatrix * vec4(transformed,1)).xyz`, injected right after `#include <begin_vertex>`).
- Fragment shader: injected right after `#include <tonemapping_fragment>` (i.e. this happens to the fully lit+tonemapped color, overriding it):
  ```glsl
  vec3 dir = normalize(vHazePos - cameraPosition);
  vec3 skyCol = mix(skyHorizon, skyTop, pow(clamp(dir.y * 1.8, 0.0, 1.0), 0.7));
  float haze = smoothstep(HAZE_START, HAZE_END, vHazePos.y);
  gl_FragColor.rgb = mix(gl_FragColor.rgb, skyCol, haze);
  ```
  Note this recomputes the **identical sky-gradient formula** as the sky dome shader (§2) but using the direction from the *camera* to the *fragment's world position* rather than a fixed sphere-relative direction — since the pipe is far closer than the 300-unit sky dome this is a reasonable approximation of "what color is the sky behind this point", not a true reflection/lookup. `skyTop`/`skyHorizon` uniforms are bound directly to the scene's live `sky.top`/`sky.horizon` `THREE.Color` objects (`env.sky`, from `createScene`), so this automatically tracks the current biome's sky colors with no extra update code — **the same object references are shared, not copied**.
- Only applied to the **gate row's** pipe material (`mats.pipe` in `createGate`, `world.js:881`) — **not** to the shop preview pipes (`createPipePreview`, uses a plain `MeshStandardMaterial` without haze, since the preview isn't tall enough to need it) nor to the classic `pipeBodyGeo`'s original bake material (haze is a shader patch on the *lit display material*, applied per-gate, all gates get their own `mats.pipe` instance so each has independently-injected haze but reads the same shared uniforms object).

**Porting note (shader injection):** three.js's `onBeforeCompile` string-patches its own generated GLSL by find/replacing named `#include` markers. A native from-scratch renderer has no such generated-shader-with-includes system — instead, write the haze logic directly into your one hand-authored pipe fragment shader (a single unconditional `if`/`mix` at the end of your lighting calculation, using the same formula above) — there is no need to reproduce the "patch an autogenerated shader" mechanism, just the resulting math. Do reuse a single small GLSL function for the sky-gradient formula (`skyGradient(dirY, top, horizon)`), called from both the sky dome shader and the pipe haze shader, to guarantee they never drift apart.

### 7.4 `createGate(scene)` — one row of pipes across all 3 lanes (`world.js:876-1019`)

**Structure per lane** (`lanes = LANES.map(...)`, `world.js:884-898`): each lane owns a `bottom` and `top` `makePipeSegment` (§7.5) plus a `plant` (cactus obstacle instance, §8.3), and per-lane runtime state: `x, bottom, top, plant, blocked, center, size, amp, speed, phase, hasPlant, plantOffset, pulse, gapLow, gapHigh, hitLow, hitHigh`.

One `bank` mesh (`cloudGeos[0]` initially, swapped per-configure) using `bankMat`, added to the row's group.

`makePipeSegment(mat, capGeo, castShadow=true)` (`world.js:667-677`): builds `{ g: Group, body: Mesh(pipeBodyGeo, mat), lip: Mesh(capGeo, mat) }`, both `receiveShadow=true`; `castShadow` defaults true but the **top pipe passes `false`** (`world.js:886`) — "upper pipes cast no sun shadow: it fell far beside the lanes, and skipping it saves up to two draw calls per pipe in the shadow pass" (a deliberate render-budget cut, not a visual requirement — a native port under render-budget pressure may reproduce this, but it is not required for visual parity since the shadow was landing off-screen anyway).

`setSegment(seg, from, to, lipAt)` (`world.js:903-909`): `seg.g.position.y = from`; `seg.body.scale.y = max(0.01, to-from)` (never zero-height, avoids degenerate scale); `seg.lip.visible = lipAt !== null`; if visible, `seg.lip.position.y = lipAt - from` (lip position is **local to the segment's group**, i.e. relative to `from`).

`setGap(lane, center, size=lane.size)` (`world.js:911-916`): computes `gapLow = center - size/2`, `gapHigh = center + size/2`, then:
- Bottom segment: `setSegment(bottom, from=0, to=gapLow, lipAt=gapLow-0.4)` — grows from the ground (`Y=0`) up to the gap's lower edge, lip positioned `0.4` below that edge (using `capBelowGeo`, band below lip).
- Top segment: `setSegment(top, from=gapHigh, to=PIPE_TOP(40), lipAt=gapHigh+0.4)` — grows from the gap's upper edge to the fixed sky height, lip `0.4` above the edge (`capAboveGeo`).

#### `configure(z, spec)` (`world.js:925-957`) — called once per row spawn
1. `group.position.z = z`.
2. `pickRowCloud()` advances the shared LCG (§6.2) and picks this row's bank/collar/none.
3. `group.visible = true`; `this.passed = false`; `this.setOpacity(1)` (reset any prior fade-out, e.g. from a reused pooled gate).
4. For each of the 3 lane specs (`spec[i]`, indexed to `LANES`), reset `lane.plant.group.visible = false`, then:
   - **`spec[i]` is falsy (blocked lane)**: `lane.blocked=true`, `hasPlant=false`, all 4 gap/hit bounds zeroed, bottom segment stretched **full height** `setSegment(bottom, 0, PIPE_TOP, lipAt=null)` (a solid pillar, no visible lip since `lipAt=null`), and the top segment hidden entirely (`top.g.visible=false`).
   - **`spec[i]` is a gap object `{ center, size, amp?, speed?, phase?, plant?, pulse?, plantOffset? }`**: `blocked=false`, `top.g.visible=true`, copies `center/size` directly, `amp=gap.amp||0`, `speed=gap.speed||0`, `phase=gap.phase||0`, `hasPlant=!!gap.plant`, `pulse=!!gap.pulse`, `plantOffset=gap.plantOffset||0`; calls `setGap(lane, gap.center)` (uses the just-set `lane.size`, i.e. the *base* size, ignoring any `pulse` animation at spawn time — pulsing starts applying next `update()`); sets `hitLow=gapLow, hitHigh=gapHigh` (the initial, un-animated hitbox — see `update()` for how these evolve every frame).

   *(The shape of the `spec[i]` gap object — who sets `center/size/amp/speed/phase/plant/pulse/plantOffset` and with what game-design ranges/probabilities — is determined by `main.js gateSpec()`/`makeReachable()`, out of scope for this document; this spec only documents what `createGate` does with whatever shape of object it is given.)*

#### `update(time, beat, dt)` (`world.js:961-1001`) — called every frame for every **active** gate
For each non-blocked lane:
1. **Moving-gap oscillation**: if `lane.amp` is truthy, `center = lane.center + sin(time*lane.speed + lane.phase) * lane.amp`; else `center = lane.center` (static).
2. **Breathing/pulse gaps** take priority: if `lane.pulse`, `setGap(lane, center, lane.size * pulseScale(beat + lane.plantOffset))` (re-applies the gap every frame at the oscillated center and a beat-driven size factor — see `pulseScale` below). Else if `lane.amp` (moving but not pulsing), `setGap(lane, center)` (re-applies gap at the base size, oscillated center only). If **neither** `amp` nor `pulse` is set, the gap is never re-applied after `configure()` — a fully static gate row costs zero per-frame work beyond the loop overhead.
3. `lane.hitLow/hitHigh = lane.gapLow/gapHigh` (re-synced every frame to whatever `setGap` most recently computed, static or animated) — **this is the collision hitbox** consumed by the game's physics (out of scope here), before any plant narrows it further in step 4-6.
4. If `!lane.hasPlant`, skip to next lane.
5. If `this.passed` (the bird has already flown through this row), force `plant.group.visible = false` and skip — plants stop animating/appearing once passed (avoids pop-in behind the camera and wasted animation work).
6. Otherwise, compute `rise = plantRise(beat + lane.plantOffset)` (0..1, see below) and `peek = plantPeek(...)`:
   - **Peek-only state** (`rise <= 0 && peek`): only the flower/head tip is visible above the pipe's lip (**no hitbox contribution** — comment: "no hitbox"). `plant.group.visible=true`; Y positioned so only a sliver (`0.12` units) of the head shows above `gapLow`: `y = gapLow + 0.12 - (CACTUS_Y + CACTUS_R.y)` (i.e. the group origin sits `CACTUS_Y+CACTUS_R.y` — the height of the body's top — below the intended visible peek height); a small wiggle: `rotation.z = sin(time*22)*0.1`; body scale forced to `(PLANT_WIDTH, 1, PLANT_WIDTH)` (no puff); `bristle.value = 0`.
   - **Otherwise**: `plant.group.rotation.z = 0` (no wiggle once past peek); `plant.group.visible = rise > 0`; if `rise <= 0`, nothing more to do this lane.
   - **Risen** (`rise > 0`): Y position: `y = gapLow + PLANT_REACH + 0.15 - PLANT_HEIGHT*(2 - rise)` — at `rise=0` this would place it at `gapLow + PLANT_REACH + 0.15 - 2*PLANT_HEIGHT` (deep inside/below the pipe, hidden by the solid pipe geometry in front of it), and at `rise=1`, `y = gapLow + PLANT_REACH + 0.15 - PLANT_HEIGHT` (its head sticks `PLANT_REACH` above `gapLow`, since the body's visual top is `PLANT_HEIGHT` above the group origin). **Hitbox update**: `lane.hitLow = max(lane.gapLow, plant.group.position.y + PLANT_HEIGHT - 0.15)` — the hitbox floor is raised to just under the plant's visual top once it pokes up far enough to exceed the gap's own floor (never lowers `hitLow` below `gapLow`). `hitHigh` is untouched by the plant (only the bottom pipe's cactus is modeled; it never affects the gap's ceiling).
   - **Puffing** (only once `rise > 0.9`, i.e. near-fully-risen): `puff = 0.5 + 0.5*sin(time*16)` (oscillates 0..1); else `puff = 0`. Body scale set to `(PLANT_WIDTH*(1+0.08*puff), 1-0.03*puff, PLANT_WIDTH*(1+0.08*puff))` (widens and slightly flattens on the "chomp" beat — cosmetic, "same hitbox" per comment, since the hitbox math above only depends on `position.y` and the constant `PLANT_HEIGHT`, not this scale). `plant.bristle.value = puff` (drives the spike-bristle vertex shader, §8.5, "looks only, same hitbox").

**Timing helper functions** (module-level, pure, `world.js:854-872` — golden-fixtured, see below):
- **`pulseScale(beat)`** = `0.85 + 0.15 * cos(beat * π)` — oscillates the gap-size multiplier between `0.7` (beat ≡ odd integer, `cos=-1`) and `1.0` (beat ≡ even integer, `cos=1`) with a full period of **2 beats**. Comment: "open (1) → narrow (0.7) → open, over two beats."
- **`plantPeek(beat)`**: `p = ((beat % 4) + 4) % 4` (JS-safe positive modulo into a 4-beat cycle); returns `true` iff `1.1 ≤ p < 2`.
- **`plantRise(beat)`**: same `p`, piecewise over the 4-beat cycle:
  - `p < 2` → `0` (hidden — this window includes the peek window `[1.1, 2)` which is handled by the *separate* `plantPeek` check in `update()`, not by `plantRise`)
  - `2 ≤ p < 2.4` → `smoothstep(p, 2, 2.4)` (rising edge, 0.4-beat ease)
  - `2.4 ≤ p < 3.5` → `1` (fully up, holds for 1.1 beats)
  - `3.5 ≤ p < 3.9` → `1 - smoothstep(p, 3.5, 3.9)` (falling edge, 0.4-beat ease)
  - `p ≥ 3.9` → `0` (hidden again until the cycle repeats)
  - `smoothstep(x, min, max)` is three.js's `THREE.MathUtils.smoothstep`: clamp `t=(x-min)/(max-min)` to `[0,1]`, return `t*t*(3-2t)` (the standard Hermite ease, identical formula used by `biomes.js`'s blend easing, §9.3).

  **Golden fixture**: `docs/native/golden/world-plant-timing.json` (from `scripts/native-golden/world-plant-timing.mjs`) — `plantPeek`, `plantRise` and `pulseScale` sampled every 0.1 beat from `beat=-4` to `beat=8` (negative beats exercise the wraparound modulo). All three are pure trig/arithmetic — port directly; verify against the fixture for the modulo-wrap edge cases (e.g. `beat=-0.05` should behave identically to `beat=3.95`).

#### Opacity / fade-out — `setOpacity(o)` (`world.js:1002-1017`)
Used to fade a passed gate out before recycling it back into the pool (driven by `main.js`, out of scope). Early-outs if the change is below `0.001` (avoids redundant material-flag churn every frame while fully opaque or fully faded). Toggles `transparent`/`depthWrite` on **only** `mats.pipe`(this gate's single shared pipe material) based on whether `o < 0.999`: `transparent=true, depthWrite=false` while fading, restored to `transparent=false, depthWrite=true` once fully opaque again (`o≈1`) — this is the standard three.js "only pay the alpha-blending/depth-sort cost while actually translucent" pattern. **Note**: the cloud bank (`bankMat`) and the cacti (their own per-lane materials) are **not** included in this opacity object (`mats` only ever contains `pipe`) — so a passed gate's bank cloud and any still-visible cactus do **not** fade with the pipes; verify whether this is intentional (likely: cacti are hidden by `this.passed` well before opacity fade matters, and the bank is small/high enough that its persistence is unnoticed) or a gap to fix when porting — flagged as a porting risk below.

### 7.5 `setPipeStyle(style)` (`world.js:618-634`)

## 8. Obstacles: the spiky cactus ("plant")

### 8.1 Purpose
A grumpy cactus that periodically pops up out of the **lower** pipe of a lane, timed to the music beat (`plantRise`/`plantPeek`, §7.4), acting as a mid-gap obstacle. One instance is built per lane per gate (3 per gate × up to 12 pooled gates = up to 36 live instances, though only lanes with `hasPlant=true` are ever shown).

### 8.2 Geometry — `buildCactusGeometry()` (`world.js:747-822`), built **once** (module-level `cactusGeo`, lazily on first `createPlant()` call) and shared/baked across all instances (materials differ per-instance only in the `bristle` uniform, §8.5, not per-instance geometry).

All parts are `MeshBasicMaterial` (unlit) during construction, baked with `bakeGroup(root, spikes=true)` (so a `spike` attribute is produced, §3) into one final geometry.

- **Body**: `SphereGeometry(1, 10, 7)` scaled by `CACTUS_R = (0.74, 0.8, 0.74)`, positioned `y = CACTUS_Y (0.85)`, color `CACTUS.green (0x2fa58f)`.
- **`onBody(d, lift=0)`** helper: given a direction vector `d` (not necessarily unit — it's divided component-wise by `CACTUS_R` to find the surface normal), returns `{ pos, n }` where `n = normalize(d / CACTUS_R)` (the ellipsoid's true outward surface normal at that parametric direction) and `pos = d*CACTUS_R + (0,CACTUS_Y,0) + n*lift` (a point exactly on the ellipsoid surface in the given direction, optionally lifted outward along the normal by `lift`).
- **`place(mesh, d, lift, up=(0,1,0))`**: positions `mesh` at `onBody(d,lift).pos` and orients it via `quaternion.setFromUnitVectors(up, n)` (rotates the mesh's local "up" axis to point along the surface normal — i.e. features are built pointing "up" in their own local space and this reorients them to point outward from the body at their placement direction).
- **Spikes** (`768-777`): 46 cones (`ConeGeometry(radius=0.05, height=0.32, radial=4)`, color `CACTUS.spike (0xfff3d6)`) distributed via a **Fibonacci-sphere** point distribution: for `i=0..45`, `phi = acos(1 - 2*(i+0.5)/46)` (polar angle), azimuth `= i * 2.399` radians (2.399 ≈ the golden angle, `2π/φ²`, the standard even-sphere-packing increment), `d = sphericalToCartesian(r=1, phi, azimuth)` (three.js `Vector3.setFromSphericalCoords`, using three.js's spherical convention — verify axis convention when porting: three.js spherical `phi` is polar from +Y, `theta` is azimuthal around Y). A spike is **skipped** if: `d.z > 0.3 && d.y > -0.6 && |d.x| < 0.8` (a roughly-frontal "face" region, kept clear for the face features) **or** `d.y > 0.8` (near the top pole, kept clear for the flower) **or** `d.y < -0.6` (near the bottom pole, presumably kept clear since it's hidden inside the pipe / near the attachment point). Each placed spike is tagged `userData.spikeDir = (0,1,0) rotated by the spike's own placement quaternion` — i.e. the world/local direction the spike should bristle outward along (used by `bakeGroup`'s `spikes` mode to tag its tip vertex, §3).
- **Face** (`779-796`), built per `side ∈ {-1, +1}` (mirrored left/right):
  - **Eye**: `SphereGeometry(0.15, 10, 8)` at direction `(side*0.34, 0.26, 0.9)` normalized, `lift=-0.05` (slightly recessed into the body), placed with `up=(0,0,1)` (i.e. the sphere's local +Z axis — irrelevant for a sphere but consistent with the `place()` contract), non-uniform `scale=(1, 1.1, 0.6)` (taller than wide, flattened in its own Z i.e. depth), color `CACTUS.eye (white)`.
  - **Pupil**: `SphereGeometry(0.065, 8, 6)` at direction `(side*0.3, 0.24, 0.92)` normalized, `lift=0.02` (sits proud on the eye), color `CACTUS.pupil (dark)`.
  - **Brow**: `BoxGeometry(0.28, 0.07, 0.05)` at direction `(side*0.32, 0.5, 0.8)` normalized, `lift=-0.01`, color `CACTUS.brow`, then `rotateZ(side * 0.4)` **applied after** placement (composes with the `place()` orientation) — inner ends angle down for a grumpy/angry brow.
  - **Mouth**: one shared (not per-side) `SphereGeometry(0.2, 10, 6, phiStart=0, phiLength=2π, thetaStart=0, thetaLength=π/2)` (a hemisphere cap, i.e. only the "polar cap" half of a sphere) at direction `(0,-0.12,1)` normalized, `lift=-0.06`, scale `(1, 0.45, 0.35)` (flattened into an arch shape read as a frown), color `CACTUS.mouth`.
  - **Fangs** (per side): `ConeGeometry(0.05, 0.14, 4)` at direction `(side*0.12, -0.15, 1)` normalized, `lift=0`, then **manually nudged** `position.y += 0.04` after placement (a small vertical correction on top of the surface placement), color `CACTUS.tooth (white)`.
- **Flower** (top, `798-810`): 6 petals, each `SphereGeometry(0.13, 6, 4)` scaled `(1.4, 0.45, 0.8)` (flattened, elongated), positioned in a flat ring of radius `0.17` around `top = CACTUS_Y + CACTUS_R.y (1.65)`, `y = top + 0.02`, `rotation.y = -angle` (each petal reoriented to point outward from center — **note**: petals are placed directly by explicit `position.set`/`rotation.y`, not via the `onBody`/`place` helpers used for the spikes/face, since they sit on the flat top rather than the curved body), color `CACTUS.petal (pink)`. Plus one center "pollen" ball, `SphereGeometry(0.08,6,4)` at `y = top+0.06`, color `CACTUS.pollen (yellow)`.
- **Outline hull** (`811-820`): a "cartoon outline" trick — a second, slightly larger copy of the body sphere (`SphereGeometry(1,10,7)`, same tessellation) with its **triangle winding reversed** (`for each triangle, swap index[1] and index[2]` — flips front/back faces without needing a separate winding-order render state), scaled `CACTUS_R + 0.07` (uniformly larger by `0.07` in each axis, i.e. `(0.81, 0.87, 0.81)`), same `y=CACTUS_Y`, color `CACTUS.outline (dark plum, 0x3a2433)`. Because the winding is reversed, standard backface culling shows only its **far/inside** surface from the camera's viewpoint... actually re-read: reversing winding makes what was the front face now the back face — so with standard CCW-front backface culling, the *originally front-facing* triangles (visible side, facing the camera) are now culled, and the *originally back-facing* triangles (facing away from camera, i.e. the silhouette edge as seen in profile) become front-facing and rendered — this is exactly the classic "inverted hull outline" technique (a slightly-scaled, inside-out, flat-dark-colored duplicate mesh), producing a dark rim visible only at grazing/silhouette angles, without any dedicated outline/edge-detection shader pass.
- Finally, `bakeGroup(root, spikes=true)` merges everything into `cactusGeo`.

### 8.3 Per-instance material/state — `createPlant()` (`world.js:841-850`)
`cactusGeo` built lazily once (`??=`). Each call creates its own `cactusMaterial()` (§8.5) — **not shared** — wrapping a fresh `Mesh(cactusGeo, mat)` (shared geometry, unique material) in a `Group`. `body.castShadow = false` explicitly (comment: "sits inside the pipe, whose shadow covers it — render budget"). `group.visible = false` initially. ### 8.4 Placement in `createGate` (`world.js:889-891`)

### 8.5 Bristle shader — `cactusMaterial()` (`world.js:827-839`)
A `MeshStandardMaterial{ vertexColors:true, roughness:0.55, flatShading:true }` with `customProgramCacheKey = () => 'cactus'` (tells three.js all cactus materials, despite being separate instances, can share one compiled shader program — only the `bristle` uniform value differs per-instance) and an `onBeforeCompile` patch:
```glsl
// vertex shader, after #include <common>:
attribute vec3 spike;
uniform float bristle;
// after #include <begin_vertex>:
transformed += spike * bristle * 0.22; // BRISTLE_LENGTH
```
i.e. every vertex is displaced along its baked `spike` direction (zero for all non-tip vertices, §3/§8.2) scaled by the per-material `bristle` uniform (0..1, driven by the `puff` oscillation in `update()`, §7.4) times the fixed `BRISTLE_LENGTH (0.22)` world units — this is how the spikes visibly "stand up" when the cactus puffs, without any bone/skinning system, just a masked vertex offset.

**Porting note:** identical to the pipe-haze shader situation (§7.3) — a native engine doesn't need three.js's `onBeforeCompile`/`#include` patching mechanism, just a hand-written vertex shader for the cactus that includes this one extra attribute + uniform + displacement line. The `spike` attribute itself must be baked exactly as described in §3/§8.2 at mesh-build time (a `vec3` per vertex, zero except at cone-tip vertices, where it holds the cone's own bristle direction).

#### `set(i, blend=3, b=BIOMES[i % BIOMES.length])` (`biomes.js:83-101`)
Called by `main.js` at: game start (`blend=0`, instant), returning to menu after equipping a different world in the shop (`blend=0.5`), and on every zone rush (`blend=3`, the ~3-second cross-fade during the "coin rush" pipe-free stretch, §main.js `spawnRush`).
1. `index = i`; `current = b` (the biome object passed in — may be a `BIOMES[]` entry or a `catalog.js WORLDS[]` entry, see §1).
2. `roadFrom = road` (current blended value); `roadTo = b.road || SAND_ROAD`.
3. For each target key: `from[k] = targets[k]` (snapshot current live color as the blend start), `to[k] = Color(b[ (k==='background'||k==='fog') ? 'horizon' : k ])` (the special-cased lookup above).
4. `fromI = {hemi: env.hemi.intensity, sun: env.sun.intensity}` (snapshot current); `toI = {hemi: b.hemiI, sun: b.sunI}`.
5. `duration = max(0.001, blend)` (guards against div-by-zero for `blend=0`); `t=0` (blend restarts from 0 progress).
6. `scenery.setTheme(b.scenery, instant = (blend===0))` — **if `blend===0`, scenery chunks are rebuilt immediately** (see §5.5); otherwise the new theme only streams in naturally as chunks recycle.
7. If `blend===0`: call `update(0)` immediately (snaps every color/intensity/road straight to the target in one step, since `t=0` combined with `update`'s `t += dt/duration` where `duration≈0.001` and `dt=0`... **actually** — with `dt=0`, `t` stays `0`, so `update(0)` at `e=ease(0)=0` would apply **no** actual blending (`lerp(from,to,0) = from`) — re ***verify***: since `from[k]` was just set equal to the pre-change target color and `to[k]` to the new color, calling `update(0)` with `t` advancing by `0/0.001 = 0` leaves `t=0`, so this call is a no-op and colors would NOT snap instantly through this path. Re-reading: `set()`'s own step 6 conditional is `if (blend === 0) update(0); else paintRoad(0);` — so for `blend===0` it calls `update(0)` (which, per the analysis above, **does not actually change any live color** because `t` doesn't advance with `dt=0`) ... **this looks like it may only rely on the *next* real `update(dt)` call (in the main render loop, called every frame with the real frame `dt`) to complete the instant snap almost immediately given `duration=0.001` is tiny** — i.e. "instant" `blend=0` transitions are technically a single very-fast (0.001s-duration) ease completing on the very next `update(dt)` tick with real `dt`, not a synchronous snap inside `set()` itself. **This is a porting risk** (see below) — a native port should verify by testing whether a `blend=0` call visibly snaps within one frame (it should, functionally, since `0.001s` is imperceptible) but should not assume `set(i, 0, ...)` synchronously mutates colors before returning.
   For `blend!==0`: `paintRoad(0)` is called instead (repaints the ground canvas to the start-of-blend road palette at `e=0`, i.e. `roadFrom` — a no-op if unchanged from the previous biome's end state, thanks to `ground.setRoad`'s key-comparison short-circuit).
8. Returns `b`.

#### `update(dt)` (`biomes.js:103-111`) — called every frame (`main.js:2074`, unconditionally, even outside a run)
- Early-returns if `t >= 1` (blend already finished — this is a persistent no-op state most of the time between transitions).
- `t = min(1, t + dt/duration)`.
- `e = t*t*(3-2*t)` (Hermite smoothstep ease of the linear progress `t` — **same formula as `THREE.MathUtils.smoothstep`**, but hand-inlined here rather than calling the utility).
- For every target key: `targets[k].lerp(from[k]→to[k], e)` — **three.js `Color.lerp(color, alpha)` operates in the color's internal working space**; with three.js's color management enabled (default since r152, and this project pins `three@^0.186.1` which has it enabled), colors are stored internally in **linear-sRGB** and `.lerp()` interpolates linearly in that linear space, not in raw sRGB byte space — this produces a visually different (generally "brighter-through-the-middle") blend than naively lerping sRGB hex values directly. **This is called out explicitly because it is easy to get wrong when porting**: a native GL engine that just lerps raw 0-255 sRGB channel values will produce a visibly different, slightly "muddier" transition than the JS reference. See `docs/native/golden/world-biome-blend.json` for worked example numbers (`scripts/native-golden/world-biome-blend.mjs`) showing the easing curve and a full SAND_ROAD→winter-road blend computed with the linear-sRGB round trip; if bit-exact parity with the JS reference matters, decode sRGB→linear before lerping and re-encode after, matching that script's `srgbToLinear`/`linearToSrgb` helpers (standard IEC 61966-2-1 transfer function, threshold `0.0031308`/`0.04045`, gamma `2.4`).
- `paintRoad(e)` (see below).
- `env.hemi.intensity = lerp(fromI.hemi, toI.hemi, e)`; `env.sun.intensity = lerp(fromI.sun, toI.sun, e)` — plain scalar lerps, no color-space concerns.

#### `paintRoad(e)` (`biomes.js:76-80`)
`step = round(e*8)/8` (quantizes the eased progress to the nearest 1/8, i.e. 9 discrete levels: 0, 0.125, 0.25, ..., 1.0) — **then** `road = roadFrom.map((c,k) => mix(c, roadTo[k], step))` where `mix(a,b,e) = new THREE.Color(a).lerp(new THREE.Color(b), e).getHex()` (same linear-sRGB round-trip as above, applied per-channel-color of the 3-entry road palette) — `ground.setRoad(road)` is then called, which itself short-circuits (`world.js:167-169`) if the resulting 3-hex array is unchanged from last time (comparing `.join()` strings) — **so across a full 3-second blend, the ground canvas is redrawn only up to 9 times total** (once per distinct 1/8 step reached, fewer if `e` jumps past a step in one frame at low framerate), not once per frame — a deliberate perf optimization since redrawing a 512×128 2D canvas every frame would be comparatively expensive. **Golden fixture** `world-biome-blend.json` includes the exact `step` value and resulting road palette at 9 evenly-spaced `t` samples for a `SAND_ROAD → winter-road` transition, letting a Kotlin port verify its own stepped-canvas-repaint logic reaches the identical intermediate palettes.

**Accessors**: `blender.index` (current biome index passed to the last `set()`), `blender.current` (the current biome/world object).

## 10. Coins — `world.js:1021-1085`

### 10.1 Geometry (`coinGeo`, module-level, built once, `1025-1046`)
Baked (§3) from `MeshBasicMaterial`-colored parts:
- **Face**: `CylinderGeometry(radiusTop=0.4, radiusBottom=0.4, height=0.1, radial=16)`, rotated 90° about X (so its flat faces point along ±Z, disc-shaped), color `0xffcf33` (gold).
- **Rim**: `TorusGeometry(radius=0.41, tube=0.055, radialSegments=4, tubularSegments=16)`, color `0xf2a100` (darker gold/orange) — a low-poly (4-sided tube cross-section) ring around the disc's edge.
- **Star** (embossed, both faces): a `THREE.Shape` 10-point star (alternating outer radius `0.21` / inner radius `0.09`, starting angle offset `+π/2` so a point faces up), extruded via `ExtrudeGeometry(shape, {depth: 0.03, bevelEnabled: false})` — a flat 5-pointed star prism. Two copies: `front` at `z=+0.04`, `back` at `z=-0.04` with `rotation.y = π` (flipped to face the opposite way, so both faces of the coin show an upright star, not a mirrored one), both color `0xfff0a0` (pale gold).

### 10.2 Material (`coinMat`, `1049-1057`)
`MeshStandardMaterial{ vertexColors:true, color:0xffffff, emissive:0xb07800, emissiveIntensity:0.55, metalness:0.15, roughness:0.35, flatShading:true }` — low metalness (comment: "there is no environment map to reflect, so a metallic coin would look brown") plus a warm self-emissive glow standing in for the missing specular environment reflection.

### 10.3 Instancing — `createCoinField(scene, count)` (`1062-1085`)
One `THREE.InstancedMesh(coinGeo, coinMat, count)`, `frustumCulled=false` (instances can be anywhere across the whole scrolling track; per-instance culling isn't attempted, the whole batch is always considered visible — simpler and cheap enough at this instance count). The game manipulates **plain `THREE.Object3D` proxies** (`coin.mesh`: position/rotation/scale/visible, never actually added to the scene graph) for each of `count` pooled coin slots; `sync()` is called once per frame (`main.js:2077`) to copy every **visible** proxy's world matrix into the instanced mesh's next free instance slot (`inst.setMatrixAt(n++, proxy.matrix)`), then sets `inst.count = n` (so invisible/inactive coins simply aren't submitted at all — not hidden via a zero-scale trick) and `inst.instanceMatrix.needsUpdate = true`. `inst.visible = n > 0` (skip the draw call entirely when no coins are active).

**Porting note:** this instanced-draw + "compact array of visible proxies, recompute active count every frame" pattern is a standard and directly portable GLES/GL ES 3.0 technique (`glDrawArraysInstanced`/`glDrawElementsInstanced` with a per-instance transform attribute or UBO/SSBO array, updated via `glBufferSubData` each frame with only the `n` active transforms). No three.js-specific behavior here beyond the API shape.

| Three.js / Web feature | Where used | Native (Kotlin/OpenGL ES 3.0) equivalent |
|---|---|---|
| `THREE.Scene`, `.background`, `.fog` (linear `Fog`) | §2 | Own scene graph; linear fog is a simple `mix(color, fogColor, clamp((dist-near)/(far-near),0,1))` in the fragment shader, or per-vertex if budget-constrained |

| `HemisphereLight`, `DirectionalLight` + shadow map (ortho camera, bias, map size) | §2 | Two uniforms (sky/ground colors + up-dot lerp) for hemi light; a standard single-cascade shadow map (ortho projection matching the given frustum bounds, same bias) for the directional light |
| `MeshStandardMaterial` (metallic-roughness PBR), `flatShading`, `vertexColors`, `emissive` | Nearly everything post-bake | A simplified PBR or even a Lambert+hemi+specular-highlight shader is likely close enough given the low light count (2 lights) and flat/cartoon art style — exact BRDF match is not required for gameplay/visual parity at this stylization level, but hue/brightness of the lit result should be checked against a reference screenshot |

| `CanvasTexture` + 2D Canvas drawing API (`fillRect`, `moveTo/lineTo/stroke`, `strokeStyle`, `lineWidth`) | Ground/grass textures (§4) | Android `Canvas`/`Bitmap` (`drawRect`, `drawLine`, `Paint.setStrokeWidth`) → upload as a GL texture (`GLUtils.texImage2D` or manual `glTexImage2D` from the bitmap's pixel buffer); re-run on palette change exactly like `setRoad` |

| `customProgramCacheKey` | Cactus material sharing (§8.5) | Native equivalent: reuse one compiled shader program object across all cactus-material instances, varying only the `bristle` uniform per draw call (a program-object cache keyed however the engine likes) |
| `Color.lerp` (color-managed, linear-sRGB space) | Biome blending (§9.3) | Explicit sRGB↔linear conversion around any color lerp if bit-exact parity matters (see `world-biome-blend.json`); otherwise a straight sRGB lerp is visually close but will differ slightly mid-transition — decide based on how strict "parity" needs to be |
| `THREE.MathUtils.smoothstep` | Plant timing (§7.4), blend easing (§9.3, hand-inlined) | `fun smoothstep(x,a,b) = clamp((x-a)/(b-a),0,1).let{it*it*(3-2*it)}` — trivial |

| Small hand-rolled LCGs (`h = (h*9301+49297) % 233280`) | Pipe-row cloud picking (§6.2) — **seeded/deterministic, unlike the rest** | Port the exact recurrence with `Int`/`Long` arithmetic (verify no overflow — see §6.2) to get bit-identical cloud-pick sequences; golden-fixtured, see `world-cloud-rng.json` |

### Additional porting risks / things to verify against a running build, not just the source

1. **`biomes.js set(i, 0, ...)` "instant" semantics** (§9.2 step 7): the code does not appear to synchronously snap colors when `blend===0`; it relies on the next `update(dt)` call completing an extremely short (`duration=0.001s`) ease. Verify with the actual JS app (or by adding console instrumentation) whether players ever perceive a 1-frame stale-color flash on a `blend=0` transition (e.g. app boot, `biomes.set(0,0,...)` at `main.js:91`) before porting this as "always fully synchronous" in Kotlin — if the JS reference *does* show a frame of the old color, the Kotlin port should match that rather than being polished it away.
2. **Gate opacity fade excludes the cloud bank and cacti** (§7.4, end of `setOpacity`): only `mats.pipe` fades; verify visually whether a passed, fading gate's cloud bank or straggling cactus is ever visible/jarring, and decide whether the native port should intentionally replicate this narrow scope or widen it (a genuine behavior question for the game designer/owner, not something inferable from the code alone).
3. **`Color.lerp` color-space behavior** depends on the exact three.js version's default `ColorManagement` setting and the renderer's `outputColorSpace`; the golden fixture (`world-biome-blend.json`) encodes the sRGB round-trip believed to match `three@^0.186.1` defaults, but this should be spot-checked against an actual rendered frame (e.g. a mid-blend screenshot compared pixel-by-pixel against the same `t` computed by the native port) since color-management edge cases are easy to get subtly wrong from reading source alone.
4. **Fibonacci-sphere spherical convention** (§8.2 cactus spikes): confirm three.js's `Vector3.setFromSphericalCoords(radius, phi, theta)` axis convention (phi = polar angle from +Y, theta = azimuthal around Y, per three.js docs) before porting the spike-placement loop, since swapping the convention would visibly rearrange all 46 spikes (though, since placement is randomized-looking already via the golden-angle sweep, a wrong convention might not be obviously "broken" — compare against a reference screenshot).
5. **`pickRowCloud()` / seeded-LCG call ordering** (§6.2): the native game must call its ported RNG in the exact same per-row order as gates are configured for the golden sequence to mean anything; if the native game's gate-spawn order or pooling strategy differs from `main.js`'s (out of scope here), the sequence will drift even with a bit-exact LCG port. Confirm the native gate-spawn call site structure before relying on this fixture for end-to-end parity, not just unit-level RNG correctness.
